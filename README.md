## 1. 한 줄 정의

DART 공시와 비즈니스 뉴스를 지식그래프로 결합해, 기업 간 **N차 연쇄 파급 리스크**를
시각화하고 **모든 주장에 원문 근거를 붙여** 답하는 분석 플랫폼.

## 2. 문제와 해법

| 문제 | BizNode의 해법 |
|---|---|
| 공급망 리스크가 2~3단계 건너 오는데 개별 기업만 봐서는 안 보인다 | 지식그래프 + 질의 시점 파급 계산 |
| LLM 요약은 그럴듯하지만 출처를 못 댄다 | **모든 엣지에 원문 문장·기사 URL** (현재 6,523/6,523 = 100%) |
| 2년 전 끝난 계약이 현재 리스크로 표시된다 | 신선도 판정(current/stale/expired) + 종료 관계 탐지 |

## 3. 차별점 — 팩트체크

```
엣지 클릭 → 관계 유형 · subtype 전체 · 방향 · 신선도 · 뒷받침 출처 수
          → 원문 문장 그대로 인용
          → 기사 제목 + URL (또는 DART 접수번호)
          → 검증 이력 (방향 교정 · 유형 재분류 · 근거 검증 결과)
```

추출한 관계는 자동 검사 7종을 거친다. 방향·대칭 병렬언급·양방향 공급·근거 정합성은
현재 뉴스 엣지 **100% 커버리지**이며, 커버율과 사각지대는 `batch/audit/coverage.py`가
매 배치마다 출력한다.

### 4-2. 워크스페이스 ★핵심

> 설계 확정 2026-08-03. 아래 수치는 전부 실측이며 목업으로 5가지 조합에서 검증했다.

```
┌──────────────────────────────┬───────────────┐
│ (중) 그래프 캔버스              │ (우) 패널      │
│                              │               │
│ 담은 기업 (진한 원)             │ 노드 클릭      │
│ 참조 기업 (점선 원)             │  → 요약 카드   │
│ 엣지 = 멤버가 한쪽 끝인 관계만    │ 엣지 클릭      │
│                              │  → 근거·출처    │
└──────────────────────────────┴───────────────┘
```

#### 노드 두 종류 — 「담은 것」과 「참조」

|  | 담은 기업 (member) | 참조 기업 (reference) |
|---|---|---|
| 무엇 | 사용자가 직접 담음. **워크스페이스에 저장** | 규칙이 계산해 그림. **저장하지 않음** |
| 모양 | 꽉 찬 원 | **점선 테두리** |
| 클릭 | 요약 → 상세 페이지 | 요약 + 「담기」 버튼 |
| 언제 바뀌나 | 사용자가 추가·제거 | 멤버가 바뀌면 매번 다시 계산 |

참조를 저장하지 않는 이유 — 멤버를 하나 빼면 참조 목록이 **저절로 달라져야** 한다.
저장하면 「왜 아직 저게 남아 있지?」가 생긴다.

참조 기업은 **담을 수 있는지**로 다시 셋으로 갈린다
(실측: Company 2,331곳 = 시드 64 · 국내 상장 미추출 213 · 국내 비상장 551 · 해외 1,503).

```
시드         + 워크스페이스에 담기 · 0원 · 즉시
국내 미추출   + 담고 수집 · 약 700원 · 30분        → 수집 대기열로
해외          담을 수 없음 (DART에 없음)           → 이름 + 업종 한 줄만
```

해외를 담을 수 없는데도 그리는 이유 — **회사↔회사 엣지 2,883건 중 1,747건(60%)이
해외를 한쪽에 둔다.** 마이크론을 빼면 한미반도체의 사업이 절반만 보인다.

#### 참조 기업을 뽑는 규칙 — 문턱이 아니라 **두 축의 순위**

문턱(「리스크 2건 이상」)은 크게 보도된 1건짜리 사건을 버리고,
두 축을 한 점수로 합치면 가중치가 자의적이다. **축을 따로 두고 각각 상위 K**를 뽑는다.

```
축① 구조   잇는 멤버 수  →  엣지 출처 합(corroboration)
축② 위험   지나가는 사건의 기사 수 합(Event.article_count)  →  사건 수

각 축 상위 5곳 + **5위와 동점이면 함께** (축당 최대 8곳)     ← SQL의 WITH TIES
기본값: 참조 꺼짐. 담은 것만 보는 게 시작점이고 켜는 건 사용자 몫
```

「기사 수」가 위험의 무게다 — **세상이 얼마나 크게 다뤘나.**
사건 수만 세면 「레인보우로보틱스(사건 3·기사 7)」가 「하나마이크론(사건 6·기사 6)」에
밀리는데, 기사 수를 보면 뒤집힌다. **1건짜리라도 대서특필된 사건이면 통과한다.**

구조 축도 마찬가지다 — 「한화세미텍(멤버 2·출처 29)」이 「테스(멤버 3·출처 3)」와
대등하게 겨룬다. 멤버 수만 보면 못 잡는 강도 차이다.

**동점을 끊지 않는 이유** — 실측으로 완전 동점이 여러 조합에서 나왔다:

```
넓게 12곳 구조축     5. 삼성디스플레이 (멤버 3·출처 4)  ·  6. 도쿄일렉트론 (멤버 3·출처 4)
반도체 25곳 위험축   5. SFA반도체 (사건 2·기사 6)      ·  6. 한화세미텍 (사건 2·기사 6)
```

같은 값인데 하나만 넣으면 이름 정렬 순서로 갈린다 —
「왜 도쿄일렉트론은 없나요?」에 답할 수 없다. 동점은 함께 넣고, 상한 8이 폭주를 막는다
(실측상 동점은 최대 3곳이라 상한이 걸린 적은 없다).

**K를 멤버 수에 비례시키지 않은 이유** — 네 가지 공식을 재봤다.
멤버가 늘수록 위험 통로도 멤버 안으로 들어와, 바깥 참조의 값어치는 오히려 줄어든다.
`clamp(멤버 수, 5, 10)`은 25곳에서 참조 15곳·선 96개로 터졌고, 고정 5가 가장 안정적이었다.

실측 — 후보가 몇이든, 멤버가 1곳이든 25곳이든 참조가 **7~11곳**으로 모인다:

| 워크스페이스 | 멤버 | 바깥 이웃 | 참조 | 동점 | 선 | 멤버끼리 선 |
|---|---:|---:|---:|---:|---:|---:|
| 반도체 후공정 | 5 | 35 | 7 | +0 | 24 | **0** |
| 로봇 | 5 | 108 | 11 | +3 | 30 | 1 |
| 메모리(대기업 포함) | 5 | **259** | 9 | +1 | 53 | 14 |
| 대기업 1곳만 | 1 | **195** | 7 | +0 | 17 | 0 |
| 넓게 | 12 | **294** | 10 | +1 | 78 | 28 |
| 반도체 전체 | 25 | **294** | 9 | +1 | 113 | 49 |

**멤버끼리 엣지가 0인 조합이 흔하다** — 후공정 5곳(심텍·하나마이크론·SFA반도체·
테크윙·ISC)은 직접 연결이 하나도 없다. 공급망이 허브-스포크라 서로 거래하지 않고
전부 대기업에 납품하기 때문이다. 참조 없이는 점 다섯 개다.

반대로 멤버가 많으면 참조가 덜 필요하다 — 25곳은 멤버끼리 49건이라 참조를 꺼도 읽힌다.
그리고 **대형사 주변이 빽빽한 것 자체가 인사이트**다(「이 산업은 두 회사 중심이다」).
그래서 기본값이 꺼짐이다.


#### 엣지 규칙

```
① 멤버가 한쪽 끝에 있는 관계만 그린다                     (고정)
     참조끼리의 관계(SK하이닉스↔삼성전자 경쟁 등)는 내 멤버와 무관 — 실측 47건 중 23건
     참조를 담으면 그 순간 멤버가 되므로 그 엣지들이 저절로 살아난다
     → 화면이 「담으면 뭐가 더 보이는지」를 스스로 예고한다 (삼성전자를 담으면 +5줄)
② 같은 쌍의 여러 관계는 한 선으로 묶는다                   (사용자가 켜고 끔)
     선 위에 개수 배지 · 클릭하면 목록으로 펼침 (삼성전자↔엔비디아는 4건)
③ 사건·제품·기관·인물은 노드로 그리지 않는다                (고정)
     사건은 「공동 리스크」 배너로 · 제품은 목록으로
```

③의 근거 — 삼성전자 관계 769건 중 **332건(43%)이 사건·제품·임원**이다.
그건 다른 회사와의 관계가 아니라 이 회사의 속성이라, 그리면 노드가 두 배가 되고
읽히는 건 없다. 다만 **멤버 여럿이 같은 사건에 걸린 경우**(메모리 5곳 기준 42건)는
버리면 안 되므로 그래프 위 배너로 올린다.

#### 배치

힘 기반(Fruchterman–Reingold)이되 **난수를 쓰지 않는다.** 초기 위치를 멤버 안쪽 원 ·
참조 바깥 원으로 정하고 520회만 돌린다 → 유기적으로 보이면서 새로고침해도 같은 그림.
출처가 많은 엣지일수록 세게 당겨 **확실한 관계가 가까이** 붙는다. 노드는 끌어 옮길 수 있다.

**충돌 회피가 따로 필요하다.** 밀어내기(`k²/거리`)는 중심점 거리만 보므로,
삼성전자처럼 차수가 높아 원이 큰 노드는 힘이 만족해도 원이 겹친다.
힘 계산 뒤에 **위치를 직접 밀어** 없앤다:

```
필요 거리 = 반지름A + 반지름B + 13(라벨 여유)
모자라면 양쪽을 (필요-현재)/2 씩 반대로 민다   ← 반복 2회
```

d3-force의 `forceCollide`, Cytoscape fcose의 `nodeRepulsion`이 하는 일이다.
프론트에서 **Cytoscape.js + fcose**를 쓰면 기본 제공되고, 엣지 번들링까지 있어
허브 주변 뭉침이 완화된다.

```
원 크기 = 연결 수      선 굵기 = 출처 수
빨간 점선 = 경쟁·소송   빨간 배지 = 지나가는 사건의 기사 수
```

| 블록 | 출처 | 상태 |
|---|---|---|
| 정체 (이름·시장·업종·대표) | `companies` | ✅ |
| 개요 2~3문장 | `company_profiles` | ✅ 60/64 |
| 재무 3개년 + **비율 4종**(ROE·ROA·영업이익률·부채비율) | `financials` | ✅ 186행 |
| 리스크 요약 (건수 · 최근 사건) | `Event`·`IMPACTS` | ✅ |
| 이 워크스페이스와의 관계 3~5줄 | 엣지 | ✅ |
| 관련 뉴스 3건 | `news_articles` | ✅ |
| 신뢰도 한 줄 (「관계 44건 중 3건 검증 대기」) | `grounding_*` | ✅ |

하단에 `상세 페이지 보기 →`. **참조 기업은 요약이 얇아지고** 그 자리에 담기 버튼이 온다.

> **시장 정보(주가·시가총액·PER·PBR·PSR·거래량)는 넣지 않는다.**
> 갱신 주기가 일 단위다. PER/PBR은 분모(EPS·BPS)만 분기고 **분자가 주가라 매일 바뀐다.**
> 반면 ROE·ROA·영업이익률·부채비율은 재무제표만 쓰므로 갱신 주기가 재무와 같아
> 재무 블록 안에 넣는다.

#### 노드 중복 선택 → 3분할 비교 (최대 2곳)

```
┌──────────┬──────────────┬──────────┐
│  심텍     │  둘의 관계     │ 삼성전자   │
│ 개요·재무  │ ──[공급]──▶   │ 개요·재무  │
│ 리스크 2   │ 근거 2건       │ 리스크 54 │
└──────────┴──────────────┴──────────┘
```

가운데는 엣지 상세를 그대로 재사용한다. **직접 관계가 없을 때가 중요하다** —
그때는 「공통 고객」과 「같이 걸린 리스크」를 보여준다.
셋 이상은 비교가 성립하지 않으므로 Ctrl/⌘+클릭으로 2곳까지, FIFO로 유지한다.

#### 엣지 클릭 → 근거

```
심텍 ──[공급]──▶ 삼성전자        SUPPLIES_TO / 공급

이 관계는 무엇인가   파는 쪽(공급사)은 심텍, 사는 쪽(고객)은 삼성전자
                  ※ 화살표만 쓰면 방향 맹점이 생긴다 — 역할을 말로 쓴다
언제·얼마나 확실한가  신선도 최신(118일) · 확신도 0.9 → 유효 0.9 · 출처 2건
                  (있으면) 계약금액 442억 · 매출 대비 7.66% · 기간 2026-06-08~09-02
근거 문장          ▍"…글로벌 빅5 메모리 칩 메이커를 주요 고객사로 확보"  ev_17ac…
출처 기사          2026-04-06 핀포인트뉴스 …                        ↗ 외부 링크
검증               ✅ 통과 · 기사 전문 재검증까지 확인
```

검증에 걸린 엣지는 판정 이유를 그대로 보여준다(「저장된 근거만으로는 확인되지 않아
화면에서 숨겨진 관계입니다」). 묶인 선을 누르면 **쪼개지 말고 목록**을 먼저 보여준다 —
성격도 시점도 다르므로 나란히 놓고 고르게 한다.

| 인물 | `IS_EXECUTIVE_OF` | ✅ 직위·담당업무·임기 |
| 리스크·사건 | Event (11종 + 리스크 여부) | ✅ 기사 목록 포함 |
| **리스크 파급** | `propagate_risk` | ✅ 공급 차질 + **매출 상실** |
| 관련 뉴스 | `news_articles` | ✅ 본문 없음 · 원문 링크 |
| 공시 | `documents` | ✅ 공급계약 393 · 사업보고서 62 · 합병 9 · 주식취득 5 |
| 지배구조 | `OWNS_STAKE_IN` | ✅ 최대주주·자회사·5%주주 |
| 데이터 완성도 · 검증 상태 | 파생 | ✅ **무엇이 없는지도 정보** |
| ~~주가·시가총액~~ | `market_data` | ❌ 미수집 |
| ~~소액주주 통계~~ | `shareholder_summaries` | ❌ 파싱 미구현 |

공시는 기업마다 편차가 크다(1건 27개사 · 2-3건 15개사 · 10건 이상 13개사).
적은 기업은 목록 대신 **「공시 의무가 없어 개별 계약 공시가 없습니다」**로 이유를 적는다.

**리스크 파급은 채널이 둘이고 감쇠가 다르다:**

```
공급 차질  HOP_DECAY = 0.55   사건사가 우리에게 납품 → 생산이 즉시 막힌다 (급성)
매출 상실  HOP_DECAY = 0.35   사건사가 우리 고객    → 매출이 서서히 준다 (만성)
```

중소형 공급사는 **매출 상실이 유일한 파급 채널**이다 — 심텍은 직접 2건 · 공급사 경유
0건 · 고객 경유 113건이다. 이걸 빼면 「리스크 파급」이 빈 화면이 된다.

**공장·사업부에서 난 사건은 모회사로 올린다** (감쇠 없음 — 홉이 아니라 같은 법인):

```
인도 공장 무기한 파업 → IMPACTS → 삼성전자(인도 공장) → SUPPLIES_TO(공급 차질) → 테슬라
                                        ↑ 어느 공장인지 경로에 남는다
```

기사가 「삼성전자 인도 공장 파업」이라고 쓰면 사건이 **공장 노드**에 붙는다. 그대로 두면
삼성전자의 고객사 어디로도 안 퍼진다 — 실측 4건이 그 상태였다(파업·화재소송·품질문제·적자).
엣지 타입은 12개 고정이라 `PART_OF`를 못 만들어, 노드 속성 `part_of_corp_code`를
**조회할 때** 따라 올린다(전파를 저장하지 않는 원칙 그대로). 합치지 않아 「어느 공장인지」는
남는다. → `batch.repair.business_units`

### 4-3. 뉴스/이슈
최신 뉴스 목록 (7,185건 · 기업·리스크 유형 필터)
※ 수집이 배치라 **「실시간」이 아닌 「최신」**

**기사 본문은 저장하지 않는다.** 화면에는 제목·언론사·날짜와 **그 기사에서 뽑아낸
관계 + 근거 한두 문장**까지만 보여주고, 그 이상은 언론사 원문으로 내보낸다.
크롤러가 robots.txt를 지키는 조건으로 본문을 받아 관계 추출에만 쓰고 버리기 때문이며
([crawler.py](pipeline/extractors/news/crawler.py)), 저작권상 인용 범위와도 맞는다.

```
목록          제목 · 언론사 · 날짜 · 수집 경로 · 관계 N건 · 사건 · 리스크 유형
필터          수집 경로(RSS 1,014 · 네이버 2,974 · 구글 3,197) · 리스크 유형 11종 · 기업
기사 클릭      그 기사에서 나온 관계 + 근거 문장 → 「원문에서 계속 읽기」
```

관련 판정 2,217건 중 **관계가 나온 것은 1,370건(61%)**이다. 나머지 847건은
기업명만 스친 기사라 목록에는 남기되 그래프에는 아무것도 붙지 않는다 —
**「관계 없음」도 숨기지 않는다.** 언론사명은 847건(11%)이 비어 있는데,
URL 도메인으로 이름을 정할 수 없는 매체라 **지어내지 않고 비워 둔다.**

### 4-4. 리서치 보관함 — 인증 없이 「얼린 스냅샷」

**그 시점의 결과를 통째로 얼려** 링크로 공유한다.

```sql
CREATE TABLE research_notes (
    note_id     TEXT PRIMARY KEY,   -- 짧은 랜덤 8자 → /r/{note_id}
    title       TEXT NOT NULL,
    kind        TEXT NOT NULL,      -- company | impact | event | search | workspace
    query       JSONB NOT NULL,     -- 무엇을 물었나 (나중에 다시 실행해 비교)
    snapshot    JSONB NOT NULL,     -- 그때 무엇이 보였나 (결과 + 근거 목록)
    memo        TEXT,
    captured_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**질의가 아니라 결과를 저장하는 이유** — 그래프는 계속 변한다. 오늘 「레인보우로보틱스
압수수색 → 삼성전자 0.90」이 다음 달엔 다르다. 보관함의 목적이 「그때 무엇을 근거로
그렇게 봤나」라면 시점을 얼려야 한다. 저장한 `query`를 다시 돌리면 **「그때와 지금 뭐가
달라졌나」**를 보여줄 수 있고, 그건 freshness 설계가 있어야 가능하다.

API 2개(`POST /notes` · `GET /notes/{id}`) + 프론트 버튼 1개. 인증 0줄.

## 5. 사용자 시나리오

```
1. "SK하이닉스에 생산 차질을 일으킬 만한 일이 있었나?"
     ↓ [그래프] event_type ∈ {사고재해, 공급망} · is_risk=true
2. 사건 3건 — 청주공장 화재 · HBM4 라인 전환 연기 · 담합 피소
     ↓ [벡터DB] evidence_id → 원문 회수
3. 근거 문장 + 기사 URL 제시
     ↓ [그래프] SUPPLIES_TO 하류로 파급 계산
4. "어디까지 번지나" → 애플·구글·엔비디아 (영향도 0.41)
   경로: 청주 화재 → SK하이닉스 → SUPPLIES_TO → 엔비디아
     ↓
5. 워크스페이스 저장 → 스냅샷 + AI 분석 보관
```

**「보도됨」과 「계산」을 구분해 제시한다.** 기사가 말한 파급과 그래프가 추론한 파급을
섞지 않는 것이 신뢰의 핵심이다.

### 확정된 수집 절차 (2026-08-02)

**표준 설정 = 5년 · 월별분할 · 상한 240.** `run_companies`의 기본값에 박아 뒀다.
바꾸면 그 기업만 연결 밀도가 달라져 **다른 기업과 위험도를 비교할 수 없다**
— 리스크 파급이 연결 수에 직접 반응하기 때문이다(허브 감점 `40/(40+차수-1)`).

```bash
# ⓪ 넣기 전 — 시드가 기존 노드에 붙는지 확인 (무료·1분)
python -m batch.audit.graph          # 「시드 추가 시 노드가 갈리는 기업: 0곳」이어야 한다

# ① 표준이 아닌 설정으로 모은 기업을 먼저 맞춘다 (15곳 남음 · 약 10,000원)
#    ★하루에 2곳쯤이 한계다. 구글이 막으면 12시간 뒤에나 다시 된다.
python -m batch.ops.run_companies --recollect 2      # 2곳씩, 며칠에 나눠
python -m batch.ops.finalize

# ② 미진행 기업 확장 (35곳 · 약 45,000원) — 밸류체인 우선순위로 자동 정렬
python -m batch.ops.run_companies --plan 5           # 5곳씩, 며칠에 나눠
python -m batch.ops.finalize                         # 5곳 끝날 때마다

# ③ 다 끝나면 사람이 본다
python -m batch.audit.spot_check --source news
```

> **왜 5곳씩인가** — 5년·월별이면 기업당 60개 질의라, 52곳을 한 번에 돌리면
> 3,000개가 넘어 구글이 막는다(실측: 심텍 480개 질의 전량 503).
> 막히면 `exit 3`으로 끝나고 **대장에 기록하지 않아** 나중에 다시 돌 수 있다.

> **속도가 실제로 효과가 있었다 — 그리고 503을 맞을수록 나빠진다** (2026-08-04~06)
>
> | 질의 간격 | 결과 |
> |---|---|
> | 0.4초 | 5,000회 던지고 차단 |
> | 0.8초 | 400 · 408 · 392 · 368질의에서 차단 (**4회 연속**) |
> | 1.2초 | 1,072질의 · 62분 · **차단 0회** (3곳 연속 완주) |
>
> 그런데 그 뒤로 한 번에 얻는 질의가 계속 줄었다. 원인은 **누적 503 횟수**다:
>
> ```
> 08-04   3,840질의   503  1회
> 08-05  ~1,300질의   503 19회 이상   ← 15분마다 재시도하는 루프를 돌린 날
> 08-06     152질의   503  1회
> ```
>
> 차단당한 클라이언트가 15분마다 다시 두드리는 건 봇의 전형적 행동이라,
> **자동 재시도 루프는 만들지 않는다.** 기본값을 2.5초로 올리고, 기업 사이에도
> 3분을 쉰다(`--pause`) — 몇 시간을 쉼 없이 같은 속도로 두드리지 않기 위함이다.
>
> **회피는 하지 않는다** — IP 로테이션·프록시·라우터 재부팅으로 IP 갈아치우기,
> 브라우저 User-Agent 위장. 실측상 UA는 **효과도 없다**(크롬·사파리·UA없음 전부 같은 503).
> 차단은 IP 기준이므로 UA를 바꿔도 달라지지 않는다.
>
> **네이버로 갈아타는 것도 안 된다** — 실측 대조(유진테크): 네이버가 2,164건을
> 가져왔는데도 구글이 찾은 41건 중 **12건(29%)만** 겹쳤다. 놓친 것이 하필
> 「유진테크 수주공시 — 공급계약 241.4억원」 같은 **공급계약 기사**고, 네이버가
> 더 가져온 2,152건은 대부분 시황·종목나열 기사였다. 원인은 **날짜 범위가 없어
> 최신 쪽에 쏠리는 것** — 2019년 공시가 최신 1,000건 안에 못 들어온다.
>
> **막는 것은 속도 제한이 아니라 「봇 탐지」다** — 503 본문을 열어 보면 구글의
> `/sorry` 페이지다(브라우저에서 CAPTCHA가 뜨는 그 화면):
>
> ```
> HTTP 503  ·  Content-Type: text/html
> "We're sorry... but your computer or network may be sending automated
>  queries. To protect our users, we can't process your request right now."
> ```
>
> 따라오는 성질이 셋이다.
> **① 정해진 할당량이 없다** — 트래픽 패턴을 보는 휴리스틱이라 같은 질의 수라도
> 통과하기도 막히기도 한다(오늘 삼성전자 21,324건은 통과, 이오테크닉스는 390질의에서 차단).
> **② `Retry-After`가 없다** — 언제 풀리는지 구글이 알려주지 않는다. 아래 「12시간」은
> 실측에서 뽑은 값이지 구글이 준 숫자가 아니다.
> **③ IP·네트워크 단위다** — "your computer or **network**". 회선 전체가 걸린다.
>
> 애초에 Google News RSS는 **공식 API가 아니다**(키도 쿼터도 없다). 그럼에도 쓰는
> 이유는 네이버 API의 `start` 상한 1,000 때문에 과거를 못 훑기 때문이다
> (실측: `"삼성전자"` 1,000건 → 커버 0일).
>
> **「이제 풀렸나」를 질의해 보고 판단하지 말 것** — 구글은 막혀 있어도 소량은
> 통과시킨다. 실측(2026-08-03): 탐침 4회가 4회 다 200을 받아 재수집을 시작했는데
> **390질의째 다시 503**이 나 22.8분을 버리고 0건으로 끝났다. 적은 표본은
> 「아직 막혔다」만 증명할 수 있고 「안전하다」는 증명하지 못한다.
> 근거로 쓸 수 있는 건 **경과 시간**뿐이다:
>
> | | |
> |---|---|
> | 07-31 차단 → 08-03 성공 | 약 2일 (삼성전자·한미반도체 통과) |
> | 08-03 05시 차단 → 07:33 재시도 | 2.5시간 — **부족했다** |
> | 하루 처리량 | 대형사 기준 **2곳쯤**에서 막힌다 |
>
> `gnews`가 503을 `data/state/google_block.json`에 남기고, `run_companies`가
> 12시간이 안 지났으면 `exit 3`으로 **시작 자체를 막는다**(`--ignore-block`로 강행).

> **끊기면 이어받는다 — 앞선 질의를 다시 쓰지 않는다** (2026-08-03)
>
> 이오테크닉스 재수집이 두 번 다 **같은 자리**에서 끊겼다:
>
> ```
> 1차  2026-08 → 2022-07   400질의   차단
> 2차  2026-08 → 2022-06   408질의   차단
>         ↑ 둘 다 여기서 시작
> ```
>
> 매번 처음부터 시작하니 이미 쓴 400질의를 또 쓰고 또 같은 자리에서 막힌다 —
> **2022-05 이전에는 영영 못 닿는다.** 480질의를 한 번에 던질 이유가 없으므로,
> 기간을 끝낼 때마다 `data/state/collect/`에 저장하고 다음 실행이 이어받는다:
>
> ```
> 1회차  2026-08 → 2022-06   408질의  💾 저장
> 2회차  2022-05 → 2021-09    72질의  ✅ 완주
> ```
>
> 같은 480질의 · 같은 기사 · **손실 0**. 기간 단위를 늘리거나 질의어 묶음을 줄이는
> 것과 달리 아무것도 포기하지 않는다(그 둘은 실측상 기사를 놓친다 — DB하이텍
> 2026-Q1: 분기 31건 vs 월 합집합 33건). 저장은 **기간 단위**다 — 한 기간의 8묶음이
> 다 돌아야 「봤다」고 할 수 있어서, 묶음 중간에 저장하면 나머지를 건너뛴다.
>
> ```bash
> python -m batch.ops.collect_state              # 어디까지 갔나 · 남은 질의
> python -m batch.ops.collect_state --clear 이오테크닉스   # 처음부터 다시
> ```

> **비용은 상한이 아니라 예상치를 본다** — 추출량은 상한이 아니라
> 「관련 판정을 통과한 기사 수」가 정한다. 29개사 중 상한을 채운 건 3곳뿐이다.
> `run_companies`가 둘 다 찍는다.

`finalize`가 도는 순서(개별 실행도 가능):

```bash
# ① 회귀확인 — 프롬프트를 고쳤다면 여기서 먼저 걸린다 (150원·30초)
python -m batch.audit.selftest                 # 추출기·검증기 양쪽 쏠림 검사

# ② 정리 — 노드·엣지·근거를 제자리로 (대부분 0원)
python -m batch.repair.node_names              # 이름이 불량한 노드 복구
python -m batch.repair.event_names             # 사건 이름 다시 짓기
python -m batch.repair.node_identity           # 정규화키 재계산 → 중복 병합
python -m batch.repair.products                # 제품 표기 통일
python -m batch.repair.edges                   # 엣지 정규화·클러스터링
python -m batch.repair.subtypes                # subtype 수렴
python -m batch.repair.executive_titles        # 근거에서 직위 복원
python -m batch.repair.stake_subtypes          # 최대주주/자회사 라벨 교정
python -m batch.repair.evidence                # 근거 청크 중복 병합 → 고아 삭제
python -m batch.repair.event_sources           # 사건에 관련 기사 목록 채우기
python -m batch.repair.press_names             # 언론사명을 URL 도메인 다수결로 복구
python -m batch.repair.business_units          # 공장·사업부를 모회사에 매달기 ★위험 전파
python -m batch.repair.orphan_nodes            # 엣지 0인 노드 표시 + 검색에서 제외
python -m batch.build.stub_profiles            # stub 정체 한 줄 (신규분만)
python -m batch.build.company_vectors          # 기업 카드 임베딩 (변경분만)

# ③ 검사 — 무엇이 틀렸나 (지우지 않고 표시만)
python -m batch.audit.grounding --llm --apply --all --source news
python -m batch.audit.grounding_fulltext       # 의심분을 기사 전문으로 다시
python -m batch.repair.retypes                 # 유형오류 교정 (매트릭스 통과분만)
python -m batch.audit.dart --apply             # DART 필드 범위 + 원문 대조 (0원)
python -m batch.audit.relations --scope all    # 방향·대칭·양방향·사건성
python -m batch.audit.freshness                # 종료된 관계 (뉴스 + DART 재적재)
python -m batch.audit.graph                    # 구조 무결성
python -m batch.audit.coverage                 # ★무엇을 아직 안 봤나

# ④ 사건 분류 · 진행현황
python -m batch.repair.event_types             # event_type 11종 + is_risk
python -m batch.ops.status --write-doc
```

### 사람이 읽어야 하는 것
```bash
python -m batch.audit.spot_check --source news  # 표본 심층검사
python -m batch.audit.queries                   # 실제 질의로 서비스 가능성 확인
python -m batch.repair.name_overlap             # 이름 겹침 자동 분류 → 남는 것만
python -m batch.repair.person_merge --dry-run   # 동명 Person 병합 후보
python -m batch.ops.lookup <검색어>              # 근거 원문 조회 CLI
```

**`name_overlap`·`person_merge`는 스스로 고치지 않는다.** 합치기·쪼개기는
되돌리기 어렵고 어느 쪽이 맞는지는 근거를 봐야 안다. 사람이 확인한 것만
코드 안 `CONFIRMED_*` 목록에 적어 넣고 `--apply`로 적용한다.

설계 근거·실측·운영 규칙은 **[데이터 수집 방법서](BizNode_데이터수집_방법서.md)** 참조.

## 10. 폴더 구조

**`batch/`는 동사로 나뉜다** — 만든다 / 고친다 / 검사한다 / 돌린다.
파일 이름에 `build_`·`fix_`·`audit_` 접두어를 붙이지 않는다. 디렉터리가 그 역할이다.

```
batch/
  build/     수집·적재 — 데이터를 **만든다**
             graph · disclosures · business_reports · sales_customers
             company_detail · major_reports · news · financials · corp_master
             ownership · subtype_taxonomy · all
  repair/    교정 — 이미 들어온 것을 **고친다** (대부분 LLM 없이 0원)
             node_names · node_identity · edges · subtypes · products
             event_names · event_types · evidence · executive_titles
             stake_subtypes · segment_units · misclassified_edges · retypes
  audit/     검사 — 무엇이 틀렸나 **본다** (지우지 않고 표시만)
             grounding → grounding_fulltext   ← 2단: 저장 문장 → 기사 전문
             dart          DART 전용 (필드 범위 + 원문 XML 대조)
             relations · graph · freshness · coverage · spot_check
             selftest      ★검사기 자체의 회귀 확인
             queries       실제 질의로 서비스 가능성 확인
  ops/       운영 — **돌린다·본다**
             finalize · run_companies · pilot_company · status · lookup · refilter

pipeline/    라이브러리 (CLI 없음)
  extractors/  dart/ · news/ — 수집·파싱
  importer/    정규화 → staging → Neo4j 적재 · 개체해소(ER)
  normalizer/  이름·관계·제품·subtype 정규화
  news/        수집·필터·라우터·트리플 추출
  validators/  matrix.py — 노드-엣지 허용 매트릭스 ★적재 전 최종 방어선
  vectorstore/ ChromaDB 래퍼
  ontology.py  엣지 12종 정의 — 추출기·검증기가 **같은 문장**을 쓴다
  freshness.py 관계 신선도 판정

app/
  core/        설정 · DB 커넥션
  services/    graph_service.py — 신선도·근거 필터 조회 · 파급 계산
  api/         (미구현)

data/
  company_list/ 시드 64개사
  raw_reports/  사업보고서 원문 (재파싱 캐시 · audit.dart가 원문 대조에 씀)
  documents/    공시 원문
```

**의존 방향은 한 방향이다** — `batch/` → `pipeline/` → `app/core`.
`pipeline/`은 CLI를 갖지 않고, `batch/`는 서로를 import하지 않는다
(예외: `ops/finalize`가 다른 배치를 **서브프로세스로** 실행).
