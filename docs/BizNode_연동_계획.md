## 1. 무엇이 되면 끝인가

```
프론트엔드가 화면을 그린다
   ↓ 백엔드 주소 하나만 부름
백엔드가 인증하고 중계한다
   ↓ HTTP
데이터 API가 사실을 돌려준다 — 이미 걸러진 상태로
```

**마지막 줄이 우리 몫**입니다.

### 레포 셋의 경계

| 레포 | 맡는 것 | 맡지 않는 것 |
|---|---|---|
| **Frontend** | 화면 · 그래프 시각화 · 백엔드 호출 | 데이터 API 직접 호출 · 무엇을 숨길지 판단 |
| **Backend** | 인증 · 사용자 DB · 워크스페이스 · 보관함 · 중계 | Cypher · 온톨로지 · 수집 배치 |
| **AI-Data** | 수집 · 마스터 DB · 조회 함수 · HTTP 층 | 로그인 · 워크스페이스 저장 · 화면 |

### 경계를 지키는 규칙 두 줄

- **데이터 API는 사용자를 모른다.** 누가 로그인했는지 알 필요가 없다. 노드 키를 받아 사실을 돌려줄 뿐이다.
- **백엔드는 온톨로지를 모른다.** 엣지 12종도, 근거 검증도, 신선도도 몰라도 된다. 주소와 응답 모양만 알면 된다.

**이 두 줄이 깨지는 순간이 신호입니다.** 백엔드에 Cypher가 등장하거나,
데이터 API가 `user_id`를 받기 시작하면 경계를 다시 봐야 합니다.

## 2. 왜 이 순서인가

보통은 이렇게 합니다.

```
함수 다 만들기 → API 붙이기 → 팀원에게 넘기기
                                  ↑
                     그동안 프론트·백엔드는 대기
```

**반대로 합니다.**

```
가짜로 답하는 서버부터 띄우기 → 팀원 셋 즉시 착수
                            ↓ 그 사이
            가짜를 하나씩 진짜로 갈아끼우기
```

프론트는 응답이 진짜인지 가짜인지 **구분하지 않습니다.** 모양만 같으면 화면을
끝까지 만들 수 있습니다. 그래서 **모양을 먼저 확정하고 내용을 나중에 채웁니다.**

```
[준비]   1단계          응답 계약        1일
[개방]   2단계          스텁 서버        0.5일   ← 여기서 팀이 합류
[채우기] 3~4단계        실제 구현        4~5일
[운영]   5단계          서버 이전        1일
```

## 1단계 · 응답 계약

**소요 1일 · 비용 없음**

### 왜 필요한가

팀원들이 「어떤 주소에 뭘 보내면 뭐가 오는지」를 알아야 각자 코드를 씁니다.
그런데 **문서를 따로 쓰면 코드와 어긋납니다.** 그래서 pydantic으로 씁니다 —
코드가 곧 문서고, FastAPI가 `/docs`를 자동으로 만들어 줍니다.

### ① 무엇을 감출지가 진짜 산출물

조회 함수의 결과에는 **내부 검사 흔적**이 붙어 있습니다. 그대로 내보내면
화면에 새어 나갑니다.

| 내부 표시 | 밖으로 나가는 형태 |
|---|---|
| `grounding_suspect` | 그 관계를 **아예 응답에서 뺀다** |
| `confidence` × 신선도 가중치 | `score` 하나로 합쳐서 |
| 신선도 판정 | `freshness: current \| stale \| expired` |
| `field_suspect` | 그 값을 **안 보낸다** |
| `revenue_trusted=false` | 금액 빼고 비중만 |
| `ratio_trusted=false` | 비중 빼고 금액만 |
| `corp_code`가 못 믿을 때 | `corp_code`를 **안 보낸다** |

### ② 모든 응답에 상태를 싣는다

```json
{
  "key": "00126380",
  "name": "삼성전자",
  "detail_level": "full",        // full | relations_only | none
  "coverage": "complete",        // complete | partial
  "collected_at": "2026-08-15"
}
```

`detail_level`이 있어야 프론트가 **「엔비디아는 재무가 없다」를 오류가 아니라
정상으로** 처리합니다.

```
Company 노드     3,432곳
   재무 있음        477곳   (14%)
   시세 있음        417곳   (12%)   상장사만
   공시·사업부문·개요  64곳   (1.9%)
   나머지 2,900여 곳  이름·업종·관계만
```

### ③ 노드 키 규칙 — 이름을 키로 쓰지 않는다

```
법인 명부 118,535건 중 이름이 겹치는 법인   13,452곳 (11.3%)
   「신우」 11곳 · 「에스엠」 11곳 · 「세원」 10곳
```

| 무엇으로 찾나 | 결과 | 쓰는 곳 |
|---|---|---|
| `corp_code` (있으면) | 정확히 하나 | 상세 · 워크스페이스 |
| `norm_name` (없으면) | 정확히 하나 | 해외·미등록 기업 |
| `also_names` | 병합된 옛 표기도 찾아짐 | 옛 링크 |
| 이름 | **여러 개 나올 수 있음** | 검색 전용 |

마지막 줄이 중요합니다. **`GET /companies/{이름}` 같은 주소는 만들지 않습니다.**
이름은 `/search`로만 받고, 거기서 고른 키를 다시 보냅니다.

> **끝나면 풀리는 것** — 백엔드가 `/docs`를 보고 DTO와 클라이언트를 만들기 시작합니다.
> 사용자 DB의 워크스페이스 표에는 **키 문자열 하나만** 저장하면 됩니다.

## 2단계 · 가짜로 답하는 서버 ★

**소요 반나절 · 비용 없음**

DB를 붙이지 않고 **고정된 답만** 돌려줍니다. 예시 값은 실제 데이터에서 뽑아 씁니다.

이 순간부터 프론트는 화면을 **끝까지** 만들 수 있습니다.

### 반드시 넣어야 할 가장자리

정상 응답만 주면 프론트가 **정상 경우만 만듭니다.**

- 검색 결과 0건
- 검색 결과 여러 건 — 「신우」처럼 동명
- `detail_level = "relations_only"` — 엔비디아처럼 재무가 없는 기업
- 워크스페이스에 **섬이 된 기업** — 아무와도 안 이어진 노드
- `coverage = "partial"` — 수집이 상한에 걸린 기업
- `404` — 없는 키

> **끝나면 풀리는 것** — 세 팀이 동시에 갑니다.

## 3단계 · 가짜를 하나씩 진짜로

**소요 3~4일 · 비용 없음**

화면에서 먼저 쓰이는 순서로 갈아끼웁니다.

| 순서 | 함수 | 지금 | 어려운 점 |
|---|---|---|---|
| 1 | `search` | 없음 | 동명 여러 건 · `also_names`까지 |
| 2 | `relations_of` | **있음** | 응답 변환만 |
| 3 | `company_detail` | 없음 | Neo4j + PG 합치기 · `detail_level` 판정 |
| 4 | `company_summary` | 없음 | **워크스페이스 문맥** |
| 5 | `workspace_graph` | 없음 | **허브 거르기** ← 가장 까다로움 |
| 6 | `relation_detail` | 없음 | Chroma에서 근거 꺼내기 |
| 7 | `events_of` | 없음 | `timeline` 펴서 주기 |
| 8 | `propagate_risk` | **있음** | 감싸기만 |
| 9 | `news_feed` · `risk_events` | 없음 | 필터 3축 |
| 10 | `market_of` | 없음 | 뷰 조회 · 상장사만 있음을 응답에 표시 |
| 11 | `trending` · `recent_insights` | 없음 | 홈 카드 |

### 5번이 제일 까다롭습니다

워크스페이스에 5곳을 담았다고 치고 실제로 재봤습니다.

```
담긴 기업: 삼성전자 · SK하이닉스 · 한미반도체 · 심텍 · 고영

직접 이어진 엣지  13개
   SK하이닉스 ↔ 삼성전자    4
   SK하이닉스 ↔ 한미반도체   4
   삼성전자 ↔ 심텍         2
   삼성전자 ↔ 한미반도체     2
   SK하이닉스 ↔ 심텍        1
   고영 ↔ 아무데도          0   ← 혼자 떨어짐
```

한 칸 건너 이으려고 보면:

```
「고영」을 나머지와 잇는 중간 노드
   삼성자산운용 [금융기관, 연결 32]  → 심텍
```

**자산운용사가 양쪽에 지분이 있을 뿐**이지 두 회사가 관계있다는 뜻이 아닙니다.
이런 걸 다리로 쓰면 펀드 하나가 모든 회사를 이어버립니다. 더 심한 것도 있습니다.

```
슈퍼노드(연결 150 초과)  14곳
```

삼성전자를 다리로 허용하면 거의 모든 쌍이 이어져 **의미가 0인 그래프**가 됩니다.

```python
def workspace_graph(keys, *, expand=True, max_nodes=150) -> dict:
    """① 담긴 기업끼리 직접 이어진 엣지        언제나 포함
       ② 섬이 된 기업만 골라 한 칸 건너 잇기     허브는 다리로 안 씀
       ③ 그래도 못 이으면 섬으로 두되 표시       억지로 잇지 않음
    """
```

**세 번째가 중요합니다. 없는 관계를 그리는 것보다 없다고 말하는 게 낫습니다.**

다리를 거르는 기준은 이미 있습니다 — `graph_service._hub_penalty()`가
차수가 클수록 그 노드를 지나는 경로를 약하게 봅니다. 파급 계산에서 쓰는 걸
여기서도 씁니다.

응답에 `role`을 넣어 **담은 기업과 다리 노드를 구분**합니다. 프론트가 다리를
흐리게 그리면 「내가 담은 건 이거고, 이어주려고 딸려온 건 저거」가 한눈에 보입니다.

### 4번 — 워크스페이스 문맥

`company_summary`는 **담긴 기업 목록을 함께 받습니다.**

```
POST /workspace/summary
{ "key": "00126380", "workspace_keys": ["00126380", "00164779", ...] }
```

「이 워크스페이스와의 관계」는 담아 둔 *다른* 기업들과 어떻게 이어지는지라,
기업 키만으로는 답이 안 나옵니다.

## 4단계 · 챗봇 접점

**추론 담당과 함께**

```
추론 담당은 HTTP를 거치지 않고 app/services/ 를 그대로 import
   같은 레포·같은 프로세스라 한 바퀴 돌 이유가 없음

POST /ask 라우트는 추론 담당이 작성
답변에 근거 ID를 반드시 함께 반환 (규약)
```

조회 함수의 **소비자가 둘**인 셈입니다 — 안에서는 추론, 밖에서는 백엔드.

### 챗봇 질의가 흐르는 모습

```
Frontend   "SK하이닉스에 생산 차질을 일으킬 만한 일이 있었나?"
   ↓
Backend    POST /ask 로 중계 — 내용은 보지 않음
   ↓
추론       사건 질문으로 판단 → 어떤 조회가 필요한지 결정
   ↓
조회 함수   events_of()      → 화재 · 라인 전환 연기 · 담합 피소
조회 함수   propagate_risk() → 한미반도체 0.71 (경로 포함)
   ↓
추론       받은 사실로 답변 생성 + 근거 링크
   ↓
Frontend   답변과 근거를 나란히 표시
```

## 5단계 · 서버 이전

**소요 1일 · 예산 5~10만원/월**

### 사양 — 실제로 재서 산정

| 구성 | 데이터 | 메모리 |
|---|---|---|
| Neo4j | 약 850MB | **2~3GB** ← 병목 |
| PostgreSQL | 110MB | 512MB |
| ChromaDB | 약 10MB | 512MB |
| Redis | 작음 | 256MB |

**2 vCPU · 8GB RAM · 50GB SSD 한 대.** 세 DB를 한 대에 몰아 넣습니다 —
지금 `docker-compose`가 그대로 올라가고 팀원은 IP 하나만 받으면 됩니다.

### 클라우드 — AWS · NCP · KT 중

우리가 쓰는 건 **「리눅스 VM + Docker」뿐**이라 어느 쪽이든 구성이 같습니다.
관리형 서비스를 안 쓰므로 **나중에 옮기기도 쉽습니다.**

| | 장점 | 주의 |
|---|---|---|
| AWS | 자료가 압도적 | 프리 티어 1GB로는 **Neo4j가 안 뜸** |
| NCP | 한국어 지원 · 국내 리전 | 자료가 적음 |
| KT | 한국어 지원 · 교육 프로그램 | 커뮤니티 자료가 가장 적음 |

**지원 크레딧이 가장 큰 곳**을 권합니다. 여유가 남으면 **8GB → 16GB**가
가장 효과적입니다(병목이 Neo4j 메모리).

### 보안 — 반드시 셋

1. DB 포트(7687·5432·8001)를 **인터넷에 열지 않는다.** 백엔드 서버에서만 접근
2. Neo4j·PostgreSQL **기본 비밀번호를 바꾼다** — 지금 개발용 값
3. `.env`는 **서버에 직접 넣고 저장소에 안 올린다**

### 운영 규칙 — 갱신 배치를 언제 돌리나

**규칙은 하나가 아니라 둘입니다. 배치가 어느 DB를 건드리느냐로 갈립니다.**

```
Neo4j 를 건드리는 배치   서비스 시간 밖에만
PostgreSQL 만 쓰는 배치   서비스 중에 돌려도 된다
```

뉴스 추출은 마스터 그래프에 **직접 씁니다.** 조회 중에 노드 병합이 일어나면
반쯤 반영된 그래프를 봅니다. 반면 시세·재무·공시는 표에 `UPSERT`만 하므로
조회와 충돌하지 않습니다.

| 항목 | 주기 | 명령 | 대상 DB | 서비스 중 |
|---|---|---|---|---|
| 주가·거래량·등락률 | 매일 18:00 | `batch.build.market_data --months 1` | PG | ○ |
| 공시 목록 | 매일 07:00 | `batch.build.disclosures` | PG | ○ |
| 재무 | 분기 (3·5·8·11월) | `batch.build.financials` | PG | ○ |
| 유통주식수 | 연 1회 (3~4월) | `batch.build.market_data --shares-only` | PG | ○ |
| 사업 개요 | 연 1회 (3~4월) | `batch.build.business_overview` | PG | ○ |
| 정합성 감사 | 주 1회 | `batch.audit.*` | 읽기만 | ○ |
| **뉴스 수집·추출** | **수동** | `batch.ops.run_companies` | **Neo4j** | **×** |

**위 여섯은 서버에 올린 뒤 cron 에 걸면 끝납니다.** 전부 비용 0원이고,
같은 명령을 다시 돌려도 이미 받은 것은 건너뜁니다(증분).

```cron
0 18 * * 1-5   python -m batch.build.market_data --months 1
0  7 * * *     python -m batch.build.disclosures
0  3 15 3,5,8,11 *  python -m batch.build.financials
0  4 * * 0     python -m batch.audit.graph
```

**뉴스만 cron 에 못 겁니다.** Google News RSS 가 연속 호출을 차단하고,
`run_companies` 가 차단 기록을 보고 12시간 안에는 시작조차 막습니다(`exit 3`).
**우회하지 않기로 했으므로**(IP 교체·프록시·UA 위장 전부 안 씀) 사람이
보면서 돌립니다. 자동 재시도 루프도 만들지 않습니다 — 15분마다 다시 두드리는
건 봇의 전형적 행동이라 차단이 더 길어집니다.

### 온디맨드 갱신은 하지 않습니다

사용자가 기업을 열 때마다 새로 받는 방식은 **쓰지 않습니다.**

| 항목 | 온디맨드로 안 하는 이유 |
|---|---|
| 주가 | 장중 실시간은 무료로 못 구한다. 마감 후 확정 종가면 화면에 충분하다 |
| 뉴스 | 한 기업에 수 분 + 90원. 화면이 기다릴 수 없다 |
| 재무·공시 | 사업보고서는 연 1회다. 지금 받아도 어제와 같은 값이다 |

대신 **응답이 언제 받은 값인지 밝힙니다** — 시세는 `trade_date`,
재무는 `bsns_year`·`fs_div`, 관계는 `last_seen` 과 신선도 판정.

> 「갱신 버튼」이 필요해지면 **뉴스 확장에만** 붙입니다. 백엔드가 요청을
> 큐에 넣고, 배치가 서비스 시간 밖에 처리한 뒤 알림을 보내는 방식입니다.
> 즉시 끝나는 일이 아니라는 걸 화면이 알려야 합니다.

## 팀에 미리 알려야 할 것

### ① 기업마다 데이터 양이 크게 다릅니다

```
Company 3,432곳 중
   재무      477곳
   시세      417곳   상장사만
   공시       64곳
   나머지 2,900여 곳은 이름·업종·관계만
```

프론트가 이걸 「데이터 없음 오류」로 처리하면 안 됩니다. `detail_level`을 보고
화면이 갈라져야 합니다.

### ② 같은 이름 회사가 있습니다

명부 118,535건 중 **11.3%가 동명**입니다. 검색 결과에 여러 건을 보여줘야 합니다.

### ③ `corp_code`가 없는 회사가 3분의 2입니다

```
corp_code 보유   1,164곳
없음            2,268곳   해외이거나, 동명이라 못 좁힘
```

어느 쪽이든 **DART 연결을 하지 않고** `norm_name`으로 식별합니다.

### ④ `company_attributes`에 행이 없는 회사가 있습니다

해외 기업은 DART 상세가 애초에 없습니다. **`LEFT JOIN`으로 짜야 하고
Neo4j 노드가 마스터**입니다.

### ⑤ 시가총액·PER·PBR·PSR은 저장돼 있지 않습니다

`market_metrics` **뷰**가 조회할 때 계산합니다. 저장하면 원본과 어긋나기
때문입니다(엣지에서 실제로 겪었습니다 — `ratio_change` 1,306건 중 15건 불일치).

응답에는 값과 함께 **기준**이 나갑니다 — `trade_date`, `fin_year`, `fs_div`.
「PER 12.3」만 주면 화면이 근거를 못 밝힙니다.

한 곳은 뷰에서 빠집니다. DART가 LS에코에너지 주식수를 30조 주로 주는데
(회사가 공시에 단위를 잘못 적었습니다) 그대로 두면 시총 순위가 통째로
뒤집힙니다. `listed_shares.suspect = true`로 **표시하고 지표에서만 뺐습니다.**

## 무엇이 잘못될 수 있나

| 위험 | 언제 | 대비 |
|---|---|---|
| 사용자가 담은 노드가 병합돼 사라짐 | repair 실행 시 | `also_names`에 옛 표기 유지 |
| 사용자가 담은 노드가 삭제됨 | `purge_unfounded` | `purged_nodes`에 기록 · 404 + 사유 |
| 조회 중 배치가 그래프를 고침 | 뉴스 추출·정리 중 | Neo4j를 쓰는 배치는 서비스 시간 밖 |
| 공시 단위 오류로 시총 순위가 뒤집힘 | 주식수 갱신 시 | `_MAX_SHARES` 상한 · `suspect` 표시 후 뷰에서 제외 |
| 잘못된 `corp_code` | 동명 법인 | 못 믿으면 **아예 안 보냄** |
| 근거 없는 관계가 파급에 섞임 | 항상 | `grounding_suspect`가 조회에서 뺌 |
