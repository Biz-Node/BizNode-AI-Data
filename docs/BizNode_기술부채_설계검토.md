## 4. LLM/프롬프트 품질 관련 검토 사항

`/ask`는 구조적 안전성(화이트리스트 검증·인젝션 방어·실패 구별)만 검증됐고, **답변의
내용 품질은 아직 아무도 채점한 적이 없습니다.** 이 절이 그 격차를 추적합니다.
★①·②는 [0절](#0-다음-개발-순서)의 첫 두 단계입니다 — 이 문서 전체에서 **가장 먼저** 진행합니다.

| 항목 | 상태 | 우선순위 | 왜 |
|---|---|---|---|
| **① SEMANTIC 결과 가중치** — 설계서 §11 "SEMANTIC 결과를 같은 무게로 말하지 않는다"를 시스템 프롬프트가 못 지킴 | `[DONE]` | **최우선** | **결정: `RetrieveResponse`에 `match_type`(`EXACT`/`SEMANTIC`)을 노출한다.** 작업은 두 단계다 — (1) 데이터 흐름부터: Retrieve Layer는 이미 어떤 경로로 찾았는지 안다(`SearchQuery.mode`) — 이 값을 `RetrieveResponse`(또는 관련 엔드포인트)까지 흘려보낸다. (2) 그다음 `AnswerService`의 `_fact_lines`/시스템 프롬프트가 `match_type`을 보고 다르게 말하도록 반영한다. **②의 선행 작업** — 순서를 반대로 하면 검증할 데이터가 없다 |

### 9-1. `/ask` 는 무엇인가 — 셋의 **결합**이고, 순서가 정해져 있다

셋 중 하나가 아닙니다. 셋 전부이되 **순서가 고정된 3단 구조**입니다.

| 층 | `/ask` 에서 맡는 역할 | 대답하는 질문 | 담당 코드 | 빼면 무슨 일이 나나 |
|---|---|---|---|---|
| **① Graph QA** | 답의 **범위를 정한다** — 어떤 기업·관계·사건이 이 질문에 걸리는가 | 「무엇이 관련 있는가」 | `search/` + `retrieve_service` | 재료가 질문과 무관해진다 (실측: 「메모리 가격 담합」에 하나마이크론 불성실공시) |
| **② Evidence-grounded RAG** | 그 범위를 **근거로 가둔다** — 인용 가능한 원문을 붙이고 인용을 화이트리스트로 제한 | 「그 말이 어디 적혀 있는가」 | `evidence_selector` · `_evidence_block` · `_sources_from` | 답이 그럴듯하지만 출처를 못 댄다 |
| **③ Graph 기반 AI Insight** | 그 안에서만 **해석한다** — 여러 사실을 겹쳐 질문에 의미를 붙인다 | 「그래서 무슨 뜻인가」 | `_SYSTEM_PROMPT` + LLM | 그래프 덤프일 뿐 답변이 아니다 |

★**한 줄 정의** — `/ask` 는 **Graph QA 가 범위를 정하고, Evidence-grounded RAG 가 그 범위를
근거로 가두고, Insight 가 그 안에서만 해석하는 3단 구조**다.

★**순서를 바꾸면 안 되는 이유** — Insight 를 먼저 하고 근거를 나중에 찾으면 「결론을 정해
놓고 근거를 고르는 것」이 된다. 지금 구조가 이미 이 순서를 강제한다(`AnswerService.ask()` 가
`retrieve()` 를 **먼저** 부른다) — 이 순서는 **유지 대상**이다.

★**「문서 RAG 챗봇이 아니다」가 실제로 뜻하는 것** — 검색의 1차 단위가 문서가 아니라
**그래프 노드**다. 말로만이 아니라 측정된 사실이다: `evidence_selector` 모듈 독스트링의
실험 ① 이 정확히 「근거 원문을 질문과 임베딩 비교」(= 전형적 문서 RAG)를 해 본 것인데,
「안전사고」 질의에서 정작 사고 근거(TMAH·인산 노출)가 82건 중 **최하위(0.155)** 로 밀렸다.
근거 단편에 기업명이 없어 질문의 기업명이 유사도를 지배했기 때문이다. **문서 RAG 방식이 이
데이터에서 실패한다는 것은 이미 실측돼 있다.**

### 9-2. 데이터 계층의 책임 — 원칙 4개를 코드·실데이터와 대조

먼저 원칙을 그대로 옮기고, 그 옆에 **코드가 실제로 그렇게 하고 있는지**를 붙입니다.

| 원칙 | 실제 구현 | 대조 결과 |
|---|---|---|
| **Graph** — 「어떤 기업과 어떤 기업 사이에 어떤 관계가 있는가」 | Neo4j 엣지 12종 · 11,060건 · **근거 보유율 100%** · `graph_service._relation()` 이 신선도·근거검증·점수를 적용해 거른다 | ✅ **일치.** 관계는 그래프에만 있고 다른 곳에서 만들어지지 않는다 |
| **Event** — 「기업과 관련해 어떤 사건이 발생했는가」 | `Event` 1,058개 · `event_type` 12종 · `is_risk` 별개 축 · **여러 기업이 공유**(2곳 이상 85건) · 기업별 연결은 `HAS_EVENT` | ✅ **일치.** 사건은 사건이고, 「이 기업이 어떻게 엮였나」는 엣지에 있다 |
| **Evidence** — 「Graph Fact 또는 Event 를 어떤 자료가 뒷받침하는가」 | ChromaDB `evidence` 10,510건 + PG `news_articles`(언론사·보도일)·`documents`(공시 제목). id 가 세 저장소에서 같은 값 | ✅ **일치.** 원문은 우리가 요약하지 않은 것이다 |
| **LLM** — 「검색된 구조와 근거를 바탕으로 설명한다」 | `AnswerService` 가 `RetrieveResponse` 만 재료로 받고 새 조회를 하지 않는다 | ✅ **일치.** 다만 「구조」가 프롬프트까지 온전히 안 간다 — 아래 표 |

**노드·엣지별 책임 — 확정**

| 것 | 대답하는 것 | 대답하면 안 되는 것 |
|---|---|---|
| `Company` | 「누구인가」 — 식별·업종·시장 | 「이 기업이 어떤가」(판단) |
| `Relationship`(엣지 12종) | 「A 와 B 사이에 무엇이 있는가」 | 「그래서 위험한가」 |
| `Event` | 「무슨 일이 있었나」 — 날짜를 댈 수 있는 일 | 「그 일이 어떤 영향을 주나」 |
| `Relationship metadata`(`subtype`·`amount`·`ratio`·`freshness`·`confidence`·`corroboration`·`symmetric`) | 「그 관계가 **어떤** 관계인가」 | 관계의 존재 자체 — 그건 엣지가 말한다 |
| `Event metadata`(`event_type`·`is_risk`·`role`·`occurred_at`·`article_count`·`timeline`) | 「그 사건에 이 기업이 **어떻게** 엮였나」 | 사건의 인과 |
| `Evidence` | 「그 말이 **어디에** 적혀 있나」 | 그래프에 없는 관계·사건 |
| `IMPACTS.sign` · `propagate_risk()` | 「그래서 어디까지 번지는가」 — **우리 계산** | **사실.** `stated=False` 는 아무도 그렇게 말한 적이 없다는 뜻이다 |

★**검증 결론** — 원칙 4개는 데이터 구조와 맞는다. **어긋나는 것은 원칙이 아니라 「그 구조를
프롬프트가 어디까지 전달하느냐」다.** 아래가 전수 대조 결과다.

**프롬프트에 실리는 것과 실리지 않는 것** (대조 2026-08-23 · `answer_service._fact_lines()`·`_evidence_block()` 전수)

| 원천 | 프롬프트에 **가는** 것 | **안 가는** 것 | 안 가서 생기는 일 |
|---|---|---|---|
| Company | `name`·`key` | `ksic`·`market`·`is_stub`·`entity_kind` | stub(이름만 아는 곳)과 시드 기업을 LLM 이 구분 못 한다 |
| Relation | `edge_id`·양끝 이름·`type`·`subtype`·`freshness`·`score`·`evidence_id` | **`symmetric`**·`amount`·`ratio`·`corroboration` | ★아래 ⓐ |
| Event | `event_id`·`name`·`event_type`·`occurred_at`(보도일로 명시)·`is_risk`·`evidence_ids` | **`role`**·`article_count`·`timeline` | ★아래 ⓑ |
| Propagation | `target`·`hops`·`stated`·`path` | `score`·`channel`·`key` | `channel`(공급 차질/매출 상실)이 `path` 문자열 안에만 있다 |
| Evidence | `evidence_id`·`source_type`·`published_at`·원문 | **`press`**·`source_doc` | 「어느 언론이 보도했나」를 답할 수 없다 |

ⓐ **`symmetric` 이 안 간다** — `PARTNERS_WITH`·`COMPETES_WITH` 는 Neo4j 가 무방향을 저장
못 해 **키 작은 쪽 → 큰 쪽으로 고정한 인공 방향**이다(ERD §2-1). 그런데 `_fact_lines()` 는
`A --PARTNERS_WITH(-)--> B` 로 화살표를 찍는다. LLM 이 이것을 방향 있는 관계로 읽으면
「A 가 B 에 협력한다」처럼 **없는 방향을 만든다.** 엣지 1,615건(협력 1,410 + 경쟁 205)이
대상이다. `Relation.symmetric` 필드는 이미 있고 값도 채워진다 — 프롬프트가 안 쓸 뿐이다.

ⓑ **`role` 이 안 간다** — `HAS_EVENT.role` 은 `subject` 953 / `counterparty` 69 /
`mentioned` 65 로 「이 기업이 당사자인가 그냥 언급된 것인가」를 가르는 유일한 값이다.
프롬프트는 셋을 똑같이 「사건 …」으로 찍는다. **`role=mentioned` 인 134건이 당사자 사건처럼
답변에 나갈 수 있다.** `Event.role` 필드도 이미 있고 `company_service.events_of()` 가
채워서 올린다 — 여기서도 프롬프트가 안 쓸 뿐이다.

★ⓐ·ⓑ 둘 다 **새 조회도 스키마 변경도 필요 없다.** 재료는 이미 `RetrieveResponse` 안에 있다.

### 9-3. 권장 최종 flow — 단계별 책임

```text
Question
  │
  ├─① Query Understanding   질문이 무엇을 묻는가          ← ★지금 계층으로 존재하지 않는다
  ├─② Search                후보 노드                     ← Search Layer (무수정)
  ├─③ Graph Context         기업 · 관계 · 사건 확정        ← Neo4j 재조회
  │     ├─④a Relationship selection   ← ★지금 없다
  │     └─④b Event selection          ← Step2 에서 생김 (evidence_selector)
  ├─⑤ 기업별 Evidence Scope  HAS_EVENT 엣지 단위          ← Step1 에서 생김
  ├─⑥ Evidence Selection    인용 가능한 원문으로 좁힘
  ├─⑦ Context Builder       [확인된 사실] / [계산된 파급] / [근거] 로 **갈라서** 조립
  ├─⑧ LLM Insight           문장 생성
  ├─⑨ Claim Extraction      주장 단위로 쪼갬              ← Step4a 에서 생김
  └─⑩ Claim Validation      타입별로 원천에 대조           ← ★타입 구분이 아직 없다
```

| 단계 | 입력 | 출력 | 책임 | **절대 하면 안 되는 것** | 현재 |
|---|---|---|---|---|---|
| ① Query Understanding | 질문 문자열 | 앵커 유무 · 질의 종류(기업/관계/주제) · 의도 키워드 · `edge_types`·`direction` | 「이 질문이 **무엇을** 묻는가」를 한 번만 판정하고 아래 전부가 그 판정을 쓴다 | 그래프를 조회하지 않는다. 후보를 고르지 않는다 | 🔴 **계층으로 없다.** 조각이 3곳에 흩어져 있다 — `QueryRouter`(Search 안), `AnchorExtractor`(Search 안), `evidence_selector.intent_of()`(Retrieve 안) |
| ② Search | `SearchRequest` | `SearchQuery` + `SearchResult` | 후보 엔티티와 순서 | 재료를 완성하지 않는다. 관계를 지어내지 않는다 | ✅ 완료 · **무수정** |
| ③ Graph Context | `companies[]` | `relations[]` · `events[]` | 그래프의 **정확한 값**으로 관계·사건을 확정 | 근거 원문을 읽지 않는다 — 여기는 **구조**만 본다 | ✅ 있음 |
| ④a Relationship selection | `relations[]` + ① | 질문이 물은 관계 우선 | 질문 의도에 맞는 관계를 위로 | 관계를 **지우지** 않는다(없는 것으로 읽힌다) | 🔴 **없다.** 점수순 상위 10건일 뿐 |
| ④b Event selection | `events[]` + ① | 질문 의도에 맞는 사건 | 규칙 티어 → 임베딩 유사도 순 | scope 를 정하지 않는다(그건 ⑤) · 전역 검색을 하지 않는다 | ✅ Step2 |
| ⑤ Evidence Scope | `HAS_EVENT` 엣지 | 기업별 근거 id | **남의 근거가 이 기업에 붙지 않게** | Event 노드의 `evidence_ids` 합집합으로 메우지 않는다 | ✅ Step1 |
| ⑥ Evidence Selection | 근거 id 합집합 | `Evidence[]` | 한 번에 모아 조회 · `missing` 을 지우지 않고 표시 | 못 꺼낸 근거를 조용히 빼지 않는다 | ✅ 있음 |
| ⑦ Context Builder | `RetrieveResponse` | 프롬프트 문자열 | **사실 / 계산 / 근거를 갈라서** 준다 · 델리미터 무결성 | 계산값을 「사실」이라는 이름의 블록에 넣지 않는다 | ⚠ **`[사실]` 한 블록에 섞여 있다** |
| ⑧ LLM Insight | 프롬프트 | `answer` + `evidence_ids` + `claims` | 재료 안에서만 해석 | 재료 밖 사실·인과·전망을 만들지 않는다 | ✅ 있음(규칙 12개) |
| ⑨ Claim Extraction | `answer` | `claims[]` | 사실 주장을 문장 단위로 쪼갬 | 인용 없는 문장을 숨기지 않는다 | ✅ Step4a · **내부 관측용** |
| ⑩ Claim Validation | `claims[]` | 상태 + 점수 | **타입별로 다른 원천에 대조** | 판정하지 않는다(임계값 미확정) | ⚠ 타입 구분 없이 한 점수로 잰다 |

★**「관계를 찾는 단계(③)」와 「근거를 확인하는 단계(⑥)」를 혼동하지 않는 규칙 — 확정**

```text
③ Graph Context      Neo4j 만 본다.  근거 원문을 읽지 않는다.
                     여기서 나온 것은 「사실」이다 — 그래프에 그렇게 적혀 있다.

⑥ Evidence           ChromaDB·PG 만 본다.  관계를 만들지 않는다.
                     여기서 나온 것은 「인용문」이다 — 누군가 그렇게 썼다.

⑩ Validation         ③ 이 만든 사실과 ⑥ 이 만든 인용문을 **대조**한다.
                     대조는 검증이지 생성이 아니다.
```

이 셋이 섞이면 「그래프에 없는 관계를 근거 원문에서 읽어내 답하는」 경로가 생긴다.
지금은 안 섞여 있고, **섞이지 않게 유지하는 것이 이 절의 결론 중 하나다.**

### 9-4. Relationship 과 Event 는 **같은 파이프라인이면 안 된다**

두 대표 질문으로 현재 설계를 검증했습니다.

**A. 「삼성전자가 납품하는 기업은?」 — Relationship 이 답이다**

```text
QueryRouter   "납품" → SUPPLIES_TO,  조사 "가" → OUTGOING          ✅ 잡는다
GraphSearcher 앵커=삼성전자로 그 엣지를 타고 **상대편**을 hit 으로  ✅ 정확하다
              → hits = [SFA반도체, 원익IPS, 세메스, …]
RetrieveService
  companies[] = 상대편 기업들                                       ⚠ 앵커(삼성전자)가 없다
  events_of(상대편) × 5                                             🔴 질문과 무관하다
  relations_of(상대편, limit=10)  ← 점수순 8종 전체                 🔴 의도를 안 본다
  evidence  ← hit.evidence 로 그 SUPPLIES_TO 근거는 살아남는다      ✅
```

★**대조로 확인한 것 셋** (`retrieve_service.py`·`company_service.py`·`graph_searcher.py`)

1. **`SearchQuery.edge_types`·`direction` 을 Retrieve 가 버린다.** `retrieve()` 는 `query` 를
   받아 놓고 `resolved_entities` 만 쓴다(grep: `retrieve_service.py` 에 `edge_types` 0회).
   질문이 무슨 관계를 물었는지가 **Retrieve 경계에서 사라진다.**
2. **`_relations_of()` 에는 의도 필터가 없다.** `company_service.relations_of(key, limit=10)` 는
   8종(`SUPPLIES_TO`·`PARTNERS_WITH`·`COMPETES_WITH`·`ACQUIRES`·`SUES`·`DEPENDS_ON`·
   `OWNS_STAKE_IN`·`REGULATES`) 전체를 **점수순으로 잘라** 준다. 사건에는 Step2 가 의도
   선택을 붙였는데 **관계에는 아직 없다** — 비대칭이다.
3. **검색이 찾아낸 바로 그 엣지가 `relations[]` 에 들어간다는 보장이 없다.**
   `SearchHit.relations` 는 `edge_id` 를 들고 있지만 `_relations_of()` 가 이를 의도적으로
   버리고 재조회한다(설계서 §8 — `freshness`·`score`·`corroboration` 이 없어서다. 이유 자체는
   타당하다). 재조회는 점수순 10건이므로, 관계가 10건을 넘는 기업에서는 **질문이 물은 그
   엣지가 빠질 수 있다.** 근거(`hit.evidence`)는 살아남으므로 답 자체는 나오지만,
   **[사실] 블록에 구조가 없고 [근거] 블록에 원문만 있는 상태**가 된다 — 그러면 LLM 이
   관계를 원문에서 **읽어내야** 하고, 그건 ③과 ⑥을 섞는 일이다(9-3 규칙 위반).

**B. 「SK하이닉스의 노조 관련 리스크는?」 — Event 가 답이다**

```text
QueryRouter   관계 키워드 없음 → edge_types 없음                     ✅
EntityResolver "SK하이닉스" 1건 확정 → mode=NAME                     ✅
RetrieveService
  events_of + evidence_selector  「노무」 티어 + 임베딩               ✅ Step2 가 푼 문제
  relations_of(SK하이닉스, limit=10)  ← 점수순 8종                    ⚠ 노조와 무관한 관계 10건
  propagation  ← is_risk 사건에서 계산                                ⚠ 9-6 참고
```

★**결론 — 같은 파이프라인으로 처리하면 안 된다.**

| | Relationship 질의 (A) | Event 질의 (B) |
|---|---|---|
| 무엇이 답인가 | **엣지 자체** — 「누가 누구에게」 | **사건** — 「무슨 일이」 |
| 어디서 오나 | 검색이 이미 그 엣지를 찾았다 | 기업 scope 안에서 다시 골라야 한다 |
| 선택 신호 | `edge_types` + `direction` (**규칙 · 결정론적**) | `event_type` 티어 + 임베딩 유사도 (**확률적**) |
| 상한을 걸면 | 질문이 물은 엣지가 빠질 수 있다 → **의도 우선 정렬이 필요** | 무관한 사건이 프롬프트를 먹는다 → **상한이 필요** |
| 곁가지 재료 | 사건은 대개 **불필요** | 관계는 대개 **불필요** |
| 현재 구현 | 🔴 없음 | ✅ Step2 |

★**제안 — `relation_selector` 를 `evidence_selector` 와 대칭으로 신설한다.**
Search Layer 는 건드리지 않는다. **필요한 신호는 이미 `SearchQuery` 가 들고 Retrieve 손에
와 있다** — `edge_types`·`direction` 을 읽어 정렬 키로 쓰기만 하면 된다. `evidence_selector`
가 이미 증명한 원칙을 그대로 쓴다: **규칙이 티어를 정하고, 자르되 버린 개수를 로그로 남기고,
「다른 종류라서」 지우지 않는다.**

★**곁가지 재료(A의 사건, B의 관계)는 지우지 말고 「분량」으로 다룬다.** 질의 종류에 따라
상한을 다르게 주는 것으로 충분하다 — 0 으로 만들면 「그 기업에 사건이 없다」로 읽힌다.
이건 Step2 가 사건에서 이미 내린 판단과 같은 것이다.

### 9-5. Claim 을 5종으로 가른다 — 검증 원천이 서로 다르기 때문이다

`claims[]` 는 지금 **한 종류**로 취급되고 한 가지 방법(근거 원문과의 낱말 겹침)으로 채점됩니다.
그런데 답변 문장의 **원천이 다섯 가지**이고, 그중 넷은 근거 원문이 아닙니다.

| claim type | 예 | 검증해야 할 원천 | 검증 방법 | 인용할 `evidence_id` 가 있나 |
|---|---|---|---|---|
| **① Relationship claim** | 「SFA반도체는 삼성전자에 납품한다」 | Graph 엣지 + 그 엣지의 `evidence_id` | 엣지 존재 확인 → 근거 원문 대조 | ✅ `Relation.evidence_id` |
| **② Event claim** | 「SK하이닉스에 노조가 설립되었다」 | Event 노드 + **이 기업의** `HAS_EVENT.evidence_id` | 사건 존재 확인 → 근거 원문 대조 | ✅ `Event.evidence_ids` (Step1 로 기업별 분리됨) |
| **③ Metadata claim** | 「지분율 67.96%」·「계약 규모 442억원」·「2026-06 이후 갱신 없음」·「이 기업은 당사자가 아니라 언급됨」 | Graph **속성값** (`ratio`·`amount`·`freshness`·`role`·`sign`·`subtype`) | **속성값과 문자열/수치 대조** — 근거 원문 대조가 아니다 | △ 엣지의 근거는 있으나 **그 값이 원문에 없을 수 있다**(예: `freshness` 는 우리가 계산한 것) |
| **④ Evidence-derived claim** | 「기사는 인산 누출로 2명이 부상했다고 보도했다」 | 근거 원문 | **낱말 겹침** — 지금 `claim_check` 가 재는 것 | ✅ |
| **⑤ Insight / inference claim** | 「마이크론의 공급 차질로 심텍은 매출 상실 리스크가 있다」 | `IMPACTS.sign` + `propagate_risk()` 결과 (**`stated=False`**) · 또는 여러 Fact 의 조합 | **원천이 evidence 가 아니다.** 대조 대상은 「우리가 그렇게 계산했나」다 | ❌ **없다.** 파급 줄에는 `evidence_id` 가 아예 없다 |

★**핵심 — 다섯 중 넷은 검증 원천이 있고, ⑤ 하나만 없다.** 그리고 실측상 **낮은 겹침 점수의
대다수가 정확히 그 ⑤ 다**: v2 채점에서 `≤0.5` 인 11건 중 **7건**이 파급·영향 문장이었고,
못 맞춘 토큰도 부정·긍정·중립·영향으로 반복됐다(커밋 `f06ec81`).

★**그래서 지금 보이는 「낮은 점수」의 상당 부분은 채점 실패가 아니라 분류 실패다.**
⑤ 를 ④ 의 잣대로 재고 있다. ⑤ 는 근거 원문에 없는 것이 **정상**이다 — 원문에 있으면
그건 ⑤ 가 아니라 ② 나 ④ 다.

★**타입은 LLM 이 자기 신고하게 하는 것이 가장 싸다.** `claims[].text` 옆에 `claim_type` 을
받으면 새 호출도 새 조회도 없다(같은 스키마 안). 다만 **자기 신고는 신뢰 대상이 아니다** —
서버가 교차 확인할 수 있는 값이 이미 있다:

```text
evidence_ids 가 비어 있다        →  ③ 또는 ⑤ 일 확률이 높다 (④ 는 인용이 있어야 한다)
문장이 파급 대상 기업명을 담는다  →  ⑤ 후보 (propagation[].target 과 대조)
문장이 엣지 양끝을 둘 다 담는다   →  ① 후보 (relations[] 와 대조)
문장이 event.name 을 담는다      →  ② 후보
```

★**아직 정하지 않은 것** — 자기 신고를 쓸지, 서버 규칙만 쓸지, 둘을 대조해 불일치를 신호로
쓸지. [9-13](#9-13-이-절이-새로-연-결정-항목) 에 `[DECIDE]` 로 올린다.

### 9-6. 「사실 / 관측된 인과 / 전망 / Insight」의 경계 — 4등급

네 문장은 **같은 등급이 아닙니다.** 등급마다 원천이 다르고, 허용되는 표현이 다릅니다.

| 등급 | 예 | 데이터 원천 | 허용 표현 | 지금 무엇이 강제하나 |
|---|---|---|---|---|
| **① 사실** | 「노조가 설립되었다」 | Event + `evidence_id` | **단정.** 단, 날짜는 보도 시점으로 | ✅ **구조적** — `_sources_from()` 화이트리스트 |
| **② 관측된 인과** | 「노조 설립으로 공급 차질이 발생했다」 | **근거 원문이 그렇게 말할 때만** | 단정하되 반드시 그 근거를 인용 | ⚠ 프롬프트 규칙 8 **뿐** |
| **③ 계산된 전망 / 파급** | 「노조 설립으로 공급 차질이 발생할 수 있다」 | `IMPACTS.sign` + `propagate_risk()` · `stated=False` | **「저희가 공급망으로 계산한 것」을 반드시 밝히고** 가능성으로만 | ⚠ 프롬프트 규칙 5 **뿐** |
| **④ Insight / 분석** | 「이 사건은 공급망 리스크를 높인다」 | 여러 Fact·Event·Evidence 의 **조합** | 해석임을 밝히고, 조합한 사실을 함께 제시 | 🔴 **아무것도 없다** |

★**이 표가 말하는 것 하나** — **①만 서버가 강제하고 ②③④는 전부 프롬프트 준수에 걸려
있다.** 프롬프트 규칙 5·8·9·11 이 발생률을 낮췄지만 없애지 못한다는 것은 실측돼 있다
(4절 `stated=False` 항목).

★**`stated` 가 ①과 ③을 가르는 유일한 구조적 신호다. 그런데 지금 `[사실]` 블록 안에 있다.**

```text
현재 — answer_service._fact_lines()

    [사실]
    검색 방식: EXACT — …
    기업: 심텍(…)
    사건 evt_…: … (공급망, 보도 2026-06-12, 위험사건) 근거: ev_…
    관계 5:…: 마이크론 --SUPPLIES_TO(-)--> 심텍 (freshness=current, score=0.9) 근거: ev_…
    파급: 심텍 (2홉, stated=False, 경로: … → IMPACTS(negative) → 마이크론 → SUPPLIES_TO(공급 차질) → 심텍)
      ↑ 블록 이름이 「사실」인데 이 줄은 사실이 아니다. 인용할 evidence_id 도 없다.
```

★**LLM 은 블록 이름을 믿는다.** 「매출 상실」·「공급 차질」이라는 **말 자체가 경로 문자열
안에 들어 있어서**, 규칙을 지키더라도 그 낱말을 문장으로 옮기기 쉽다. 실측으로 나온
「심텍은 매출 상실의 리스크가 존재한다」(겹침 0.12)·「…에 공급 차질이 발생할 수 있는 상황에
직면해 있다」(0.29)가 정확히 이 경로다.

★**설계 방향(확정 아님 — [9-13](#9-13-이-절이-새로-연-결정-항목))** — 블록을 **이름으로 가른다.**

```text
[확인된 사실]     그래프에 그렇게 적혀 있는 것.        인용 가능.
[계산된 파급]     우리가 계산한 것. stated=False.      ★인용할 근거가 없다고 명시.
[근거]            원문. 인용 대상.
```

블록 이름을 가르면 ③이 ①과 물리적으로 분리되고, 「이 블록의 문장은 근거를 못 단다」를
LLM 에게 **위치로** 가르칠 수 있다. 지금은 같은 표현을 규칙 문장 하나로만 가르치고 있다.

★**`IMPACTS.sign` 을 어떻게 쓸지도 여기서 정해야 한다.** `sign` 은 `negative` 585 /
`positive` 452 / `neutral` 46 으로 채움률 100% 인데, 지금 프롬프트에는 **구조화된 필드로
가지 않고 `path` 문자열 안의 `IMPACTS(negative)` 조각으로만** 들어간다. 「부정적 영향을
미친다」류 저겹침 문장의 출처가 이것이다. `sign` 은 **①이 아니라 ③**이다 — 기사가 「악영향」
이라고 쓴 것이 아니라 우리 추출기가 붙인 라벨이다.

### 9-7. Anchor 없는 질의 — **Query Understanding 이 풀 문제다**

앵커 없는 질의는 **한 종류가 아니라 세 종류**입니다. 지금은 셋이 서로 다르게 망가집니다.

| 경우 | 예 | 지금 가는 길 | `match_type` | 무엇이 문제인가 |
|---|---|---|---|---|
| **ⓐ 주제 질의** — 관계 키워드도 앵커도 없음 | 「메모리 가격 담합」·「반도체 업계 파업 위험」 | `edge_types` 없음 → 해소 실패 → **SEMANTIC** | `SEMANTIC` | 무관 기업이 `companies[]` 를 채운다. `intent_of()` 가 지울 앵커가 없어 **질문 전체가 의도**가 된다 (4절·5절 기록) |
| **ⓑ 앵커 없는 관계 질의** — 관계 키워드는 있고 앵커가 없음 | 「납품 단가 압박」·「최근 인수 사례」 | `edge_types` 있음 → `_search_anchorless()` → source 5 + target 5 슬롯을 **점수순으로 아무거나** | 🔴 **`EXACT`** | ★**새로 발견.** `_MATCH_TYPE_BY_MODE[RELATIONSHIP] = EXACT` 라 프롬프트가 「정확히 일치한 결과입니다」라고 말한다. 앵커 없이 슬롯을 채운 것인데 **헤지가 아예 안 걸린다** — ⓐ보다 나쁘다 |
| **ⓒ 앵커가 있는데 못 뽑음** | §4-4·§4-6 (조사 잔여·별칭) | 앵커 실패 → ⓐ 로 떨어짐 | `SEMANTIC` | **다른 문제다** — [5절](#5-검색-레이어-및-성능-관련-기술-부채) `AnchorExtractor` 항목 |

★**어느 계층에서 풀 것인가 — Query Understanding 이다.** 나머지 둘을 배제한 이유:

- **Retrieve 에서 못 푼다.** 기업별 상한을 조여도 「무관한 기업 3곳」이 「무관한 기업 1곳」이
  될 뿐이다. **관련성 문제를 개수로 풀 수 없다.**
- **Evidence Selection 에서 못 푼다.** `intent_of()` 는 앵커가 없으면 지울 것이 없어 질문
  전체를 의도로 삼는다. 여기에 유사도 컷오프를 걸면 **의도가 없는 질의(「SK하이닉스」)까지
  같이 잘린다** — 「앵커가 없어서 의도가 질문 전체」인 경우와 「앵커만 있어서 의도가 없는」
  경우를 구분할 신호가 selection 안에 없다. 실제로 `intent_of()` 는 후자에 대해 빈 문자열을
  돌려주도록 이미 특별 처리돼 있는데, 전자에는 그런 처리가 없다.
- **Query Understanding 에서 풀린다.** 「이 질의에 기업 앵커가 있는가」는 **이미 답이 나와
  있다** — `SearchQuery.resolved_entities` 가 비었는지 보면 된다. 새 조회도, Search Layer
  수정도 필요 없다.

★**그리고 앵커 없는 질의를 기업 질의와 같은 방식으로 처리하면 안 된다 — 답변의 종류가
다르기 때문이다.**

| | 기업 질의 | 주제 질의 (앵커 없음) |
|---|---|---|
| 사용자가 원하는 것 | 「이 기업에 대해 **답하라**」 | 「이 주제에 해당하는 것이 있으면 **찾아 보여라**」 |
| 답변 형태 | 서술 | **목록** — 「A 에 이런 건이, B 에 이런 건이 있습니다」 |
| 재료가 약할 때 | 「근거가 없습니다」 | 「이 주제로는 다음이 걸렸습니다 — 질문과 직접 관련은 확인되지 않았습니다」 |
| 지금 하는 것 | 서술 | 🔴 **서술.** 무관한 기업 3곳으로 하나의 서사를 쓴다 |

★지금 가장 나쁜 것은 「답이 틀린 것」이 아니라 **「재료가 약하다는 사실이 사용자에게 안
간다」**는 점이다. `match_type` 이 EXACT/SEMANTIC 을 가르는 것과 **같은 종류의 문제**이고,
같은 방식(응답에 신호를 실어 화면이 배지를 붙일 수 있게)으로 풀 수 있다.
4절의 `AskResponse.match_type` `[DECIDE]` 와 **묶어서 결정하는 것이 옳다.**

### 9-8. Claim-Evidence validation 재설계

**지금의 문제를 한 줄로** — 점수 하나가 **서로 다른 세 질문**에 동시에 답하려 하고 있다.

```text
"이 문장이 근거 원문에서 왔나"       ← 낱말 겹침이 맞는 질문        (④ Evidence-derived)
"이 문장이 그래프 값에서 왔나"       ← 속성값 대조가 필요한 질문      (③ Metadata)
"이 문장이 우리 계산에서 왔나"       ← 원천이 evidence 가 아닌 질문   (⑤ Insight)
```

★**재설계 원칙 — 타입을 먼저 가르고, 타입마다 다른 원천에 대조한다.**

| claim type | 대조 원천 | 방법 | 낱말 겹침을 쓰나 | 낮은 값의 뜻 |
|---|---|---|---|---|
| ① Relationship | `relations[]` 의 `edge_id`·양끝·`type` | 엣지 **존재 확인**(집합 대조) + 근거 원문 대조 | 근거 대조 단계에서만 | 「그래프에 없는 관계를 말했다」 = **실제 의심** |
| ② Event | `events[]` 의 `event_id`·`name` + 그 기업의 `evidence_ids` | 사건 **존재 확인** + 근거 원문 대조 | 근거 대조 단계에서만 | 「없는 사건」 또는 「남의 사건」 = **실제 의심** |
| ③ Metadata | 엣지·노드 **속성값** | 수치·문자열 직접 대조 (`ratio`·`amount`·`role`·`sign`·`freshness`) | ❌ **쓰면 안 된다** | 지금은 「의역」과 구분이 안 된다 |
| ④ Evidence-derived | 인용한 `evidence` 원문(+`published_at`) | **낱말 겹침** | ✅ **여기가 제자리** | 「근거에 없는 낱말을 썼다」 = 1차 의심 |
| ⑤ Insight / 파급 | `propagation[]` (`target`·`path`·`stated`) | 「우리가 그렇게 계산했나」를 대조 · **근거 대조 대상이 아님** | ❌ | 지금은 무조건 낮게 나온다 (정상인데 의심으로 읽힌다) |

★**lexical grounding(`pipeline/token_overlap`)의 올바른 위치 — 확정**

```
④ Evidence-derived claim 전용 1차 의심 필터.

  ✅ 맞다   답변 문장이 인용한 근거 원문 안의 낱말을 쓰고 있는가
  ❌ 아니다 의미가 맞는가 (의역·동의어에 걸린다 — 모듈 독스트링이 이미 못박음)
  ❌ 아니다 그래프 속성값과 맞는가 (③ — 값 대조가 필요하다)
  ❌ 아니다 계산된 파급이 타당한가 (⑤ — 원천이 evidence 가 아니다)
```

★**배치 위치 셋 — 어디에 무엇을 둘지**

| 위치 | 지금 | 최종 아키텍처에서 | 왜 |
|---|---|---|---|
| 요청 경로 (`answer_service.ask()`) | 관측 로그만(`claim.grounding …`) · 응답 무영향 | **그대로.** 타입 분류가 붙어도 여전히 관측 | 요청 경로에서 문장을 지우려면 임계값이 필요한데, 임계값을 정할 근거가 아직 없다 |
| 배치 (`batch/audit/claim_grounding.py`) | 20개 대표 질문 분포 수집 | **그대로 + 타입별로 나눠 본다** | 타입을 섞어 보면 분포가 거짓말을 한다 — v2 의 `≤0.5` 11건 중 7건이 ⑤ 였다 |
| 응답 계약 (`AskResponse`) | 없음 | **아직 아니다** | 타입 분류가 먼저다. 지금 내보내면 「낮은 점수 = 의심」이라는 **틀린 해석을 화면에 고정**하게 된다 |

★**임계값을 아직 정하지 않는 이유가 바뀌었다.** 전에는 「분포를 더 봐야 해서」였는데,
이제는 **「타입을 안 가르고 정한 임계값은 어차피 틀리기 때문」**이다. ⑤ 를 섞은 채로 컷을
잡으면 정상인 파급 문장을 의심으로 세고, 그 비율에 맞춰 컷이 낮게 잡힌다.
**타입 분류가 임계값의 선행 조건이다.**

★**LLM judge 는 여전히 도입하지 않는다.** 위 표에서 ①②③⑤ 는 전부 **결정론적 대조**로
풀린다 — 집합 확인·값 비교이지 의미 판정이 아니다. 의미 판정이 필요한 것은 ④ 하나이고,
거기에는 이미 낱말 겹침이라는 무료 1차 필터가 있다. 판정기가 필요해지는 시점은
「④ 의 거짓 양성이 실제로 답변을 훼손한다」가 측정된 뒤다.

### 9-9. 현재 구현의 분류 — 유지 / 수정 필요(보류) / 후속 구현

**A. 그대로 유지 — 되돌리지 않는다**

| 무엇 | 왜 유지인가 |
|---|---|
| **Step1** — 기업별 evidence scope 를 `HAS_EVENT` 엣지에서 (`_own_evidence_ids`) | 최종 아키텍처의 ⑤단계 그 자체다. 실측으로 사건 85건 중 71건이 섞일 수 있었다 |
| **Step2** — 사건 의도 선택 (`evidence_selector`) | ④b 그 자체다. 규칙 티어 + 임베딩 · 하드 필터 아님 · 잘라낸 개수 로그 — 이 세 원칙은 `relation_selector` 에도 그대로 쓴다 |
| **Step3** — 인과 금지·보도일 명시 (규칙 8·10) | 9-6 의 ②등급을 막는 유일한 장치다. 서버 강제가 아니라는 한계가 있을 뿐, 없애면 더 나빠진다 |
| **Step4a** — `claims[]` 관측 · 판정 없음 · 외부 계약 무변경 | 9-8 의 결론이 「타입 분류가 먼저」이므로, **판정하지 않은 것이 옳았다.** 임계값을 박았으면 지금 되돌려야 했다 |
| **Step4b** — 조사 분리·날짜 정규화·문장 불용어 (`sentence_tokens`) | 채점 잡음을 걷어냈고, 그 덕에 **남은 저점수가 ⑤ 한 부류로 수렴**해서 이 절의 진단이 가능해졌다 |
| `_MAX_PROPAGATION_LINES=15` + 「몇 곳을 뺐는지 적는다」 | 조용히 자르지 않는 원칙. 재료 상한 전반에 계속 적용한다 |
| `pipeline/token_overlap.tokens()` 기본 경로 불변 | `batch/audit/grounding.py` 의 `0.34` 가 이 동작에 맞춰 잡힌 값이다 |
| `AnswerService.ask()` 가 `retrieve()` 를 먼저 부르는 순서 | 9-1 의 3단 순서를 코드가 이미 강제한다 |
| `_sources_from()` 화이트리스트 · `missing` 제외 · `failed` 구별 | 9-6 ①등급의 **유일한 구조적 강제**다 |

**B. 설계상 수정이 필요하지만 지금은 구현하지 않는다**

| 무엇 | 무엇이 어긋났나 | 왜 지금 안 하나 |
|---|---|---|
| `_fact_lines()` 가 `[사실]` 한 블록에 계산값을 섞는다 | 9-6 — 블록 이름이 내용과 다르다 | 블록을 가르면 프롬프트 규칙 5·7·8 문구도 같이 바뀐다. **9-11 ①(architecture freeze) 이후 한 번에** |

| `role`·`symmetric` 이 프롬프트에 안 간다 | 9-2 ⓐⓑ — 없는 방향·없는 당사자성을 만들 수 있다 | 재료는 이미 있어 **싸다.** 다만 `_fact_lines()` 를 손대는 작업이라 위 항목과 **같은 커밋에 묶는 것이 맞다** |

| `_evidence_block()` 이 `press` 를 안 싣는다 | 9-2 — 「어느 언론이 보도했나」를 못 답한다 | 사소하고 독립적이다. `_fact_lines()` 손볼 때 같이 |
| `score={relation.score}` 를 척도 설명 없이 LLM 에 준다 | 값이 1.0 을 넘을 수 있는데(3절) 프롬프트에 척도가 없다 | 「신뢰도 90%」로 읽힐 소지. 블록 재설계 때 같이 판단 |

### 9-10. 파일별 책임 — 최종 아키텍처에서 적절한가

### 9-12. 이 설계가 기존 구현과 충돌하는 지점

「고쳐야 한다」가 아니라 **「이대로 가면 어긋난다」**를 미리 적어 둡니다.

| 충돌 | 기존 구현 | 이 설계 | 어떻게 풀 것인가 |
|---|---|---|---|
| **`RetrieveResponse.companies` 의 뜻** | 스키마 설명은 「질문에서 찾아낸 기업」 | RELATIONSHIP 모드에서 실제로 담기는 것은 **앵커가 아니라 상대편 기업**이다(`_search_anchored`) | 스키마 설명을 사실에 맞추거나, 앵커를 별도 필드로 싣는다. **계약 변경이라 결정 필요** |
| **`_relations_of()` 재조회** | 설계서 §8 이 「`SearchRelation` 에 값이 없어 재조회한다」로 정당화 | 재조회 자체는 옳지만 **검색이 찾은 엣지가 결과에 들어간다는 보장이 없다** | 재조회는 유지하되 **검색이 준 `edge_id` 를 우선 정렬 키로** 쓴다. 새 조회 없음 |
| **`match_type` 의 이분법** | EXACT/SEMANTIC 둘뿐 | 앵커 없는 관계 질의(ⓑ)가 EXACT 로 분류돼 헤지를 못 받는다 | `match_type` 을 늘리기보다 **앵커 유무를 별도 신호로.** 4절 `AskResponse.match_type` `[DECIDE]` 와 묶는다 |
| **`[사실]` 블록 이름** | 규칙 5 가 「파급은 계산한 것」이라고 문장으로 가르침 | 블록 **이름**이 규칙과 반대를 말한다 | 블록을 가른다(9-11 ④). 규칙 5 는 남기되 문구를 블록 이름에 맞춘다 |
| **`claims[]` 를 한 종류로 봄** | Step4a 가 의도적으로 판정을 안 함 | 5종으로 갈라야 임계값을 논할 수 있다 | **Step4a 의 선택이 옳았으므로 되돌릴 것이 없다.** 위에 타입을 얹는다 |
| **`evidence_selector` 라는 이름** | 사건을 고르는데 이름은 evidence | ④b 는 event selection 이다 | 순수 리네임. 언제든 싸다 |
| **주제 질의를 서술로 답함** | 프롬프트가 질의 종류를 구분하지 않음 | 주제 질의는 목록형이어야 한다 | 새 ③ 에서 신호를 만들고 새 ④ 에서 표현을 가른다 |

### 9-13. 이 절이 새로 연 결정 항목

| **앵커 없는 질의에 「재료가 약하다」를 응답으로 내릴 것인가** | (a) 별도 필드 (b) `match_type` 확장 (c) 답변 문장으로만 | `AskResponse` 계약 변경이면 백엔드/프론트 협의가 필요하다. 4절 `AskResponse.match_type` `[DECIDE]` 와 **묶어서 한 번에 정하는 것이 옳다** |
| **주제 질의의 답변 형태(목록형)를 도입할 것인가** | (a) 도입 (b) 서술 유지하고 헤지만 강화 | 화면에 어떻게 보일지의 문제라 프로덕트/프론트와 맞춰야 한다. 4절 「답변 형식/톤/길이」 `[DECIDE]` 와 같은 자리 |
