## 1. 개발 개요

### 1-1. 무엇을 했나

고정 파이프라인이던 `/ask` 를 **LangGraph 그래프로 옮기고, 그 안에 Agent 루프를 넣고, Agent 가 무엇을 얼마나 쓰는지 재는 평가셋을 만들었습니다.**

```text
2026-08-27  Phase 0     선행 정리 — ★LangGraph 코드는 한 줄도 없음
            Phase 1     /ask 를 그래프로 이식 — ★출력이 똑같아야 한다
2026-08-28  Phase 1.5   fetch_* 를 도구 시그니처로 — ★재료가 똑같아야 한다
            Phase 1.75  기준선 비결정성 제거 · provenance 자리 · 사본 통합
            Phase 2     Agent 도구 5종 · 인용 규칙 · ★Agent 루프 · 평가셋
            Phase 8     ★측정 → 문제 발견 → 수정 → 재측정
```

### 1-2. ★전 과정을 관통한 원칙 — 「한 번에 하나씩 바꾼다」

각 Phase 의 성공 기준이 **「좋아졌다」가 아니라 「똑같다」**였습니다.

| Phase | 성공 기준 | 검증 |
|---|---|---|
| 0 | 계약이 갈린 자리를 맞춘다 · **동작 무변경** | `/ask`·`/retrieve` 무변경 · `search/` 무수정 |
| 1 | **출력이 바이트 단위로 같다** | 20질문 대조 — 20/20 동일 |
| 1.5 | **재료 집합이 같다** (표기는 붙으므로 바이트 대조 불가) | 20질문 — 예상 밖 차이 0 |
| 1.75 | 흔들림의 뿌리를 **규명**한다 | 4실험 · 가설 반증 |
| 2 | Agent 가 도구를 고르되 **방어선은 그대로** | 계약 7 · 금지 17 · 평가셋 |
| 8 | Agent 가 **무엇을 얼마나 쓰나** | 20/20 PASS + 관측치 |

★**이 원칙 덕분에 「그래프로 옮기다가 뭔가 바뀌었나」를 매 단계 대조로 배제할 수 있었습니다.** 마지막에 한꺼번에 바꿨다면 Phase 8 에서 나온 수치가 무엇 때문인지 가릴 수 없었을 것입니다.

## 3. 주요 Architecture Decision Records

### ADR-1. `get_propagation` 을 Agent Tool 이 아닌 내부 primitive 로 유지

| | |
|---|---|
| **문제** | 파급(propagation)은 답변의 핵심 재료인데, Agent 가 부를 수 있게 할 것인가 |
| **고려 사항** | ① 도구로 열면 Agent 가 필요할 때만 계산 → 비용 절감<br>② 열지 않으면 파급 재료가 통째로 사라짐<br>③ `get_propagation(event_ids)` 는 **주어진 사건**의 파급을 계산하는 함수 — 사건 목록을 Agent 가 정하면 파급 범위도 Agent 가 정하는 셈 |
| **결정** | ★**도구로 열지 않는다**(`FORBIDDEN_TOOL_NAMES`). 대신 `fetch_propagation` 노드가 **Agent 뒤에서** 결정론으로 계산한다 |
| **이유** | 파급은 **그래프를 타고 번지는 계산**이라, 입력 사건을 LLM 이 고르면 「어디까지 번졌다고 볼지」를 LLM 이 정하게 됩니다. 그것은 재료 범위를 고르는 일입니다 (도구 4원칙 ①) |
| **결과** | 파급이 `evidence_validation` **뒤**에 계산됩니다 — 거기서 사건이 dedup 된 뒤라야 파급이 중복 없이 나옵니다. `is_risk` 사건만, 최대 3건 |
| **trade-off** | ① 파급이 필요 없는 질문에도 계산이 나갑니다 (「삼성전자 시가총액」에도)<br>② 예산 카운터가 루프 **뒤에** 채워져 `budget_exhausted` 플래그의 뜻이 갈렸습니다 → §4-4 로 이어짐 |

### ADR-2. `explore_impact` 를 Phase 2-B 로 미룸 — ★지시서 전제 정정

| | |
|---|---|
| **문제** | 그래프를 **걸어 다니며** 탐색하는 도구를 지금 만들 것인가 |
| **고려 사항** | ① 만들면 Agent 가 관계를 따라 재료를 넓힐 수 있음<br>② 만들면 「어디까지 걸었나」가 새 예산 항목이 됨<br>③ 만들면 `provenance` 에 `explored` 값이 생겨 **재료의 출처가 두 갈래**가 됨<br>④ Phase 2 는 「도구 선택을 LLM 에게 넘긴다」가 목표인데, 탐색까지 넘기면 **한 번에 두 가지를 바꾸는 것** |
| **결정** | ★**만들지 않는다.** Phase 2-B 로 미룬다 |
| **이유** | Phase 원칙 「한 번에 하나씩 바꾼다」. 도구 선택의 효과를 먼저 재고, 탐색은 그 위에서 판단합니다 |
| **결과** | 코드에 **자국 셋**이 남았습니다 — `budget.MAX_HOPS`(6, 아무도 안 씀) · `provenance` 의 `"explored"` 값(만드는 코드 없음) · `test_provenance` 의 「`explored` 가 나타나면 실패」 테스트. ★**자리를 미리 둔 이유는 그때 State·로그·테스트를 한꺼번에 고치지 않기 위해서**입니다 |
| **trade-off** | 미사용 예산 항목과 미사용 enum 값이 코드에 남습니다. 그 대가로 **2-B 착수 때 배선만 하면 됩니다** |

> ★**작업 지시서는 「`explore_impact` 를 Agent Tool 로 제공한 결정」을 ADR 로 요구했으나, 실제 결정은 「제공하지 않기로 한 것」입니다.** 코드 기준으로 정정해 기록합니다.

| **고려 사항** | ① hard filter — 워크스페이스 밖은 버림 → **질문이 물은 사례를 버림**<br>② 랭킹 문맥 — 순서만 정함<br>③ material anchor — 재료 수집의 출발점으로도 씀 |

| **이유** | 「워크스페이스는 필터가 아니라 랭킹 문맥」이 설계서 §3 의 원 결정입니다. 2026-08-25 정책 개정 표에도 **「무변경」**으로 기록돼 있습니다. 바뀐 것은 **「받은 `workspace_keys` 로 무엇을 하는가」**입니다 |
| **결과** | 코드에서 `workspace_keys` 가 쓰이는 자리 넷 — ① 입구 게이트 ② 앵커 판정 ③ 링 계산 ④ Search Layer 랭킹 |
| **trade-off** | ★**도구 범위는 `workspace_keys` 가 아닙니다** — 「서버가 이 질문의 재료로 고른 것」(`companies` + 앵커)입니다. 워크스페이스를 그대로 넣으면 도구가 재료 밖 기업을 조회할 수 있게 됩니다 |

> ★**지시서는 「hard filter → ranking signal 로 변경」을 ADR 로 요구했으나, 그런 변경 이력은 문서에 없습니다.**

### ADR-4. `SearchResult` 의 책임 범위 — Search Layer 를 안 고친다

| | |
|---|---|
| **문제** | Agent 가 붙으면서 검색 결과에 무엇을 더 담아야 하나 |
| **고려 사항** | ① `SearchResult` 에 재료를 더 담아 Agent 가 바로 쓰게 함<br>② `SearchQuery` 에 이미 있는 신호(`edge_types`·`direction`)를 Retrieve 쪽에서 쓰기 |
| **결정** | ★**`search/` 를 한 줄도 안 고친다.** 필요한 신호가 **이미 `SearchQuery` 에 있고 Retrieve 손에 와 있습니다** |
| **이유** | `SearchResult` 는 「무엇이 관련 있는가」에 답하는 계약입니다. 재료 조립까지 담으면 **검색과 재료의 경계가 사라집니다.** 게다가 이 계약은 백엔드에 나가 있어 바꾸면 두 번째 진실이 생깁니다 |
| **결과** | Phase 0~2 전 구간에서 `search/` 무수정. `relation_selector` 는 `app/services/` 에 신설했습니다 |

### ADR-5. `edge_types`·`direction` 을 Agent 인자가 아니라 `ToolContext` 로

### ADR-7. 평가셋에서 도구 선택을 개별 정답으로 고정하지 않음

| | |
|---|---|
| **문제** | Agent 의 탐색 총량을 어떻게 제한할 것인가 |

| **결정** | ★**호출할 때마다 누적치를 더하고, 소진되면 예외가 아니라 마감으로 전이한다** |

## 4. 문제 발견과 해결 사례

### 4-1. Ring 0 이 점수순 절단에서 통째로 사라진다

| | |
|---|---|
| **현상** | 워크스페이스 안쪽 관계(Ring 0)가 프롬프트에 하나도 안 실림 |
| **원인** | 관계를 **점수순으로 정렬해 상위 N 개만** 잘랐는데, Ring 0 의 점수가 높다는 보장이 없음 |
| **조사 방법** | 삼성전자 관계 **526건**의 순위에서 Ring 0 이 몇 번째인지 전수 확인 (2026-08-25) |
| **결과** | ★**Ring 0 은 137 · 225 · 414 번째.** 상위 10건만 받으면 **하나도 안 남습니다** |
| **해결** | ★**링으로 먼저 줄을 세운 뒤에 자른다.** `ring_of` 로 0~3 분류 → 링 순 → 링 안에서 정렬 → `ordered[:limit]` |
| **검증** | Phase 8 실측 — R0 는 본 것 9건이 **전부 kept**, 최종 인용 1건 |

★**「hard filter 가 아니다」를 지켰습니다** — Ring 3(워크스페이스와 안 닿음)도 **버리지 않고** 순서만 뒤로 보냅니다.

### 4-2. 링 안의 의도 정렬이 예외도 로그도 없이 꺼져 있었다

**★이 프로젝트에서 가장 값어치 있는 발견 사례입니다.**

| | |
|---|---|
| **현상** | 없음 — ★**아무 증상이 없었습니다.** 예외도, 경고도, 로그 변화도 없이 정렬이 입력 순서를 그대로 돌려주고 있었습니다 |
| **원인** | Phase 1.5 의 `fetch_relations` 는 `edge_types`·`direction` 을 **인자로** 넘겼는데, Phase 2 Agent 배선에서 도구 4원칙 ① 을 지키려고 **인자에서 빼고 `ToolContext` 로 옮기지 않았습니다.**<br>`matched = frozenset(edge_types or ())` → 언제나 빈 집합<br>`if not matched: return ordered` → 정렬이 통째로 꺼짐 |
| **조사 방법** | ★**증상이 아니라 「상속 확인」으로 찾았습니다.** 「1.5차가 옮긴 세 단계(링 분류 · 링 순 줄세우기 · 정렬 뒤 자르기)가 Agent 배선 뒤에도 남아 있나」를 코드로 하나씩 확인했습니다 (현황서 §8-18)<br>① `ring_of` 를 거치나 → **거친다**<br>② 링 로그가 찍히나 → **찍힌다 (다만 이름이 `tools.relations rings` 로 달라져 `/ask` 로그를 `relations.rings` 로 grep 하면 0건)**<br>③ 자르기가 정렬 뒤인가 → **뒤다**<br>④ `workspace_keys` 가 도구까지 오나 → **온다**<br>→ ★**빠진 것은 링이 아니라 「링 안의 의도 정렬」** |
| **영향 규모** | `edge_types` 는 `QueryRouter` 의 **결정론적 키워드 규칙**이 채웁니다. Search 평가셋 20질의를 라우터에 먹여 보니 **12건(60%)에서 잡혔습니다** |
| **해결** | `ToolContext` 에 두 자리 신설 → `_scope_of()` 가 `state["query"]` 에서 실어 보냄 → `agent_tools.get_relations` 가 `ctx` 에서 읽어 넘김.<br>★**바꾼 파일은 셋뿐**이고 `graph_tools.py`·`relation_selector.py` 는 **무수정** — 받는 쪽은 처음부터 멀쩡했고 **비어 있던 건 보내는 쪽**이었습니다.<br>★**Agent 인자는 안 늘렸습니다** — 4원칙 ① 을 안 깹니다 |
| **검증** | 실 Neo4j · 삼성전자 526관계 · **LLM 미호출** · 라우터가 `edge_types` 를 잡는 고유 질의 11건<br>`1.5차 경로 vs 고친 경로 → 순서까지 11/11 동일` ← ★**개선이 아니라 복구**<br>`1.5차 경로 vs 고치기 전 → 8건에서 순서가 다름` ← 회귀의 크기<br>회귀 테스트 **6건** 신설 (`tests/graph/test_relation_intent_order.py`) |

**★배운 것 둘**

1. **인자를 Context 로 옮기는 설계는 「옮기는 것을 잊으면 조용히 죽는다」는 대가가 있습니다.** 그래서 테스트가 필수입니다
2. ★**수정을 측정 앞에서 했습니다** — 측정 뒤에 고치면 순서가 바뀌어 `ordered[:limit]` 의 자르는 지점이 바뀌고, **평가셋을 두 번 재게 됩니다**

### 4-3. 그런데 고쳤더니 R2 가 안 살아났다 — ★가설 반증

| | |
|---|---|
| **현상** | 정렬 복구 후 재측정했더니 **R2 는 전후 모두 kept 0** |
| **착수 전 예상** | 정렬이 켜지면 `IS_EXECUTIVE_OF`·`REGULATES`·`HAS_EVENT` 가 R2 **안에서** 앞으로 올라와 R2 가 살아난다 |
| **조사 방법** | 평가셋 20 케이스 재실행 → 링 분포를 before/after 로 나란히 봄 |
| **원인** | ★**구조적입니다** — 정렬은 링 **안에서만** 순서를 바꾸고, 자르기는 링 **순서대로** 먹습니다. **R1 이 혼자 746건**이라 상한을 다 채우고 끝나므로 R2 는 **애초에 차례가 오지 않습니다** |
| **실제 효과** | ★**「몇 개가 남나」가 아니라 「무엇이 남나」**입니다. `order()` 는 길이를 보존하는 순열이고 `[:limit]` 은 프리픽스 컷이라, **링 안 순서는 링별 kept 개수를 바꿀 수 없습니다.** LLM 없이 한 대조에서 **순서까지 11/11 동일**이 나왔고 달라진 것은 어떤 엣지가 남나뿐이었습니다 |
| **결론** | 현황서 §5-17(비-Company 관계가 Ring 2 로 밀려 잘린다)은 이 수정으로 **닫히지 않았습니다.** ★**링 사이 배분(fair-share) 문제**로 남습니다 |
| **상태** | **미결정** `[DECIDE]` — 링별 최소 할당 규칙이 없으면 정렬을 어떻게 바꿔도 R2·R3 는 0 |

★**처음에는 「실제 효과 = kept 개수 변화(126→110 · R1 109→101 · R3 8→0)」로 적었는데, 그것도 틀렸습니다.** 그 개수 차이는 수정의 효과가 아니라 **계측 오귀속**이었습니다 → §4-9.

> ★**재평가가 없었다면 §5-17 을 닫힌 것으로 오해했을 것입니다.** 「고쳤으니 좋아졌겠지」가 아니라 **「고쳤는데 안 바뀌었고, 그 이유가 다른 곳에 있다」**를 수치로 확인한 것이 이 단계의 성과입니다.

### 4-9. ★링 수치가 관계가 아니라 「호출 × 관계」였다 — 계측기 안의 귀속 문제

**§4-3 의 결론을 뒷받침하던 숫자가 다시 뒤집힌 사례입니다.**

| | |
|---|---|
| **현상** | 재측정에서 링별 kept 개수가 `R1 109→101 · R3 8→0 · kept 126→110` 으로 바뀐 것을 `41bb1bb` 의 효과로 적었습니다 |
| **의심의 출발** | ★**그럴 수가 없다**는 구조적 논증입니다. `relation_selector.order()` 는 `ordered = list(rows)` 뒤 `sort()` 만 하므로 **길이를 보존하는 순열**이고, `kept = ordered[:limit]` 은 프리픽스 컷입니다. 링별 kept **개수**는 블록 크기와 `limit` 만으로 정해지므로 **링 안 순서는 개수에 영향을 줄 수 없습니다** |
| **원인** | `observe.record_rings()` 가 `get_relations` **호출마다** 불리는데 `edge_id` 중복을 안 접고 더했습니다 — `ring_seen` 이 「관계 몇 개」가 아니라 ★**「호출 × 관계」**였습니다 |
| **왜 흔들렸나** | ★**몇 번 부를지는 LLM 이 정합니다.** 실측: 같은 20 케이스의 `get_relations` 호출이 한 실행은 **7회**, 다른 실행은 **3회** |
| **조사 방법** | 세 시점(`a7925ae` · `41bb1bb` · `9ae14c4`)의 링 수치와 **`get_relations` 호출 횟수를 나란히** 놓았습니다 → 부풀어 있던 것은 **호출 7회짜리 실행 하나뿐**(R1 +8 · R3 +13) |
| **해결** | `record_rings` 가 `edge_id` 로 중복을 접습니다. ★`cut` 만은 **안 접습니다** — 같은 관계가 한 호출에서 남고 다른 호출에서 잘릴 수 있어 「어느 쪽이 참인가」가 없고, 자른 **횟수**로 읽어야 하는 값입니다 |
| **검증** | `tests/graph/test_observe_rings.py` **8건** 신설 — 특히 `test_call_count_does_not_change_ring_numbers`(같은 입력을 1회 넣든 5회 넣든 링 수치가 같다). 953 → **961 passed**<br>재측정(`9ae14c4`): 도구 호출 총계가 **34 → 35** 로 흔들렸는데 ★**링 수치는 안 움직였습니다** |

**★이것은 §4-5(임베딩 드리프트)와 같은 종류의 귀속 문제입니다 — 다만 있던 자리가 다릅니다.**

```text
§4-5   결함이 데이터에 있었다      → 영속 캐시로 막았다
§4-9   결함이 계측기에 있었다      → 도구 선택 쪽에는 그 장치가 없었다
```

2차의 완료 기준이 평가셋 점수인데, **점수 차이를 랭킹에 귀속시킬지 도구 선택에 귀속시킬지 못 가르면 기준 자체가 성립하지 않습니다.**

★**얻은 것은 「수치가 바뀐 것」이 아니라 「안 바뀐다가 보장된 것」입니다.** 정정 뒤에도 정본 수치는 `R1 746 / 101 · kept 110` 그대로인데(그 실행들에 겹치는 호출이 없었으므로 dedup 이 접을 것이 없었습니다), 이제 **링 분포의 변화를 랭킹에 귀속시킬 수 있습니다.**

★**두 번의 정정을 다 견딘 결론** — **R2 는 세 시점 모두 kept 0** 이고 이유는 구조적입니다. §5-17 은 안 닫혔고 **링 사이 배분** 문제로 남습니다.
