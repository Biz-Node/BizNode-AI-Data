# Part I. 스키마

## 1. 설계 원칙 3

**① 노드는 개방형, 엣지는 12종 고정, 적재 전 정규화.**
관계 표현(납품/공급/부품을 댐)이 각각 다른 엣지가 되면 다중 홉 경로가 끊긴다.
엣지 타입이 유한해야 N차 리스크 추론이 가능하다.

**② DART 먼저, 뉴스 나중.**
뉴스 개체해소(ER)의 1단계가 `corp_code` 정확 매칭이다. DART 골격이 먼저 있어야
뉴스 개체가 붙으면서 들어온다.

**③ 저장은 전부, 임베딩은 선별.**
원문은 다 보관하되 Vector DB에는 관계 근거·기업 요약만 넣는다. 전문 임베딩은
비용뿐 아니라 검색 정확도를 떨어뜨린다.

## 2. 노드 5종

| 노드 | 식별자 | 비고 |
|---|---|---|
| `Company` | **corp_code** (DART) — 없으면 `norm_name` | stub은 norm_name이 식별자 |
| `Person` | `이름\|생년월` 또는 `이름@corp_code` | |
| `Organization` | `norm_name` | 공정위·금융위 등 비기업 |
| `Product` | `norm_name` (정규화 명칭) | 기술을 Product에 흡수 |
| `Event` | `event_id` = 해시(이름 + 연월) | |

- **Sector는 노드가 아니라 `Company.sector` 속성** — 노드로 두면 슈퍼노드가 생겨
  추론 시 무관한 기업까지 리스크 영향권으로 끌려온다.
- 판단 기준: **관계의 능동적 주체인가.** 공정위는 「규제한다」의 주체라 노드,
  반도체 섹터는 「속하는」 대상이라 속성.

## 3. 엣지 12종 — 노드-엣지 허용 매트릭스

**이 표가 스키마 견고함의 핵심이다.** 적재 전 `pipeline/validators/matrix.py`가
이 표로 검증해 잘못된 조합을 차단한다.

| Category | Edge Type | 허용 방향 (Source → Target) | 성격 | 주 소스 |
|---|---|---|---|---|
| 소유·지배 | `OWNS_STAKE_IN` | Company/Person/Org → Company | 상태 | DART API |
| 소유·지배 | `IS_EXECUTIVE_OF` | Person → Company/Org | 상태 | DART API |
| 거래·협력 | `SUPPLIES_TO` | Company → Company | 상태 | 공급계약공시·사업보고서·뉴스 |
| 거래·협력 | `PARTNERS_WITH` | Company/Org ⇄ Company/Org | 상태(대칭) | 사업보고서·뉴스 |
| 거래·협력 | `ACQUIRES` | Company → Company | 사건 | 주요사항보고서·뉴스 |
| 리스크·분쟁 | `SUES` | Company/Person/Org → 동일 | 사건 | 뉴스 |
| 리스크·분쟁 | `COMPETES_WITH` | Company/Product ⇄ 동일 | 상태(대칭) | 뉴스 |
| 리스크·분쟁 | `REGULATES` | Organization → Company/Product | 상태 | 뉴스 |
| 제품·기술 | `DEVELOPS` | Company → Product | 상태 | 사업보고서·뉴스 |
| 제품·기술 | `DEPENDS_ON` | Company/Product → Product | 상태 | 사업보고서·뉴스 |
| 이벤트·영향 | `HAS_EVENT` | Company/Product → Event | 사건 | 뉴스 |
| 이벤트·영향 | `IMPACTS` | Event → Company/Product | 사건 | 뉴스 |

**⇄ 대칭 엣지** — Neo4j는 무방향을 저장 못 하므로 **키 작은 쪽 → 큰 쪽 단방향 고정**,
조회는 화살표 없는 패턴(`-[:COMPETES_WITH]-`).

**3계층 구조**
```
L1 Category (5)    프론트 필터·범례
L2 Edge Type (12)  Cypher 탐색·다중홉 추론 ← 유한해야 함
L3 Subtype (개방)   상세 패널 표시. 관리 목록으로 수렴 (subtype_registry)
```

**리스크·분쟁은 본질적으로 뉴스 영역이다.** 시드 64개사 최근 3년 주요사항보고서를
전수 조회한 결과 소송 1건·부도 0·회생 0이었다. 건강한 상장사는 이런 공시를 안 낸다.

## 4. 엣지 속성

```cypher
(A)-[:SUPPLIES_TO {
    // 의미
    subtype: "공급계약",  subtypes: ["공급계약","exclusive"],  // 클러스터링 시 보존
    direction: "outbound",         // outbound / symmetric
    sign: null,                    // IMPACTS 전용: positive/negative/neutral

    // 시점 — 3층으로 분리
    valid_from: "2024-03-01",      // 관계 시작 (사건 발생일)
    valid_until: null,             // 명시적 종료일 (공급계약 등)
    last_seen: "2026-07-24",       // 최근 관측 = 공시·기사 날짜
    loaded_at: "2026-08-01T...",   // 우리가 적재한 때 ★재적재 누락 판정용
    is_current: true,              // false = 종료 확인됨
    refresh_cycle_days: 365,       // 소스별 예상 갱신 주기

    // 근거·신뢰
    confidence: 1.0,               // DART=1.0, 뉴스=LLM 점수
    corroboration: 3,              // 뒷받침 출처 수 ★품질 지표
    source_type: "dart",           // dart / dart_filing / news
    source_doc: "20251219000123",
    source_docs: [...],            // 클러스터링 시 누적
    evidence_id: "ev_12345",       // ChromaDB FK
    evidence_ids: [...],           // 클러스터링 시 누적

    // 검증 이력
    direction_checked_at, parallel_checked_at, grounding_checked_at,
    grounding_suspect, grounding_verdict, retyped_from, direction_corrected
}]->(B)
```

**`last_seen`과 `loaded_at`을 혼동하면 안 된다.** `last_seen`은 공시 날짜(사건이
일어난 때), `loaded_at`은 우리가 본 때다. 국민연금 2024년 공시를 오늘 적재하면
각각 2024년·오늘이다. 「재적재에서 사라졌나」는 `loaded_at`으로만 판정된다.

> **`loaded_at`은 그래프에 남겨야 한다.** 검사 사유·이력 37종을 PostgreSQL
> `edge_audits`로 내릴 때 이것까지 같이 옮겼다가 되돌렸다 — `audit/freshness.run_dart`가
> 이 값으로 재적재 누락을 판정하는데, 옮기니 「적재시각 있는 것 0건」이 되어
> 검사가 통째로 멈췄다.

## 4-2. subtype(L3) — 무엇을 담고 무엇을 담지 않나

**subtype은 근거에서 읽어낸 「무엇을」이다.** 엣지 타입이 이미 하는 말을
되풀이하지 않고, 다른 필드가 이미 담고 있으면 비운다.

이 원칙은 실측에서 나왔다(2026-08-11). subtype이 **엣지 타입 이름을 되풀이하기만
하는 비율**을 재 보니 출처에 따라 극단으로 갈렸는데, 잘 되는 둘(`OWNS_STAKE_IN`·
`IS_EXECUTIVE_OF`)의 공통점이 **LLM이 만들지 않는다**는 것이었다. 그리고
`ontology.py`가 `COMPETES_WITH`에만 「**무엇을** 두고 다투는가를 근거에서 집어
적어라」라고 물었는데, 그 타입의 값이 「HBM 시장」·「TV 시장」 — 정확히 원하는
형태였다. **물어본 타입만 답이 옳았다.**

**A군 — 양 끝이 회사·인물. subtype이 「무엇을」을 맡는다 (8종)**

| 엣지 타입 | 담을 것 | 예 |
|---|---|---|
| `SUPPLIES_TO` | 무엇을 파는가 | 반도체 PCB · TC 본더 · 카메라모듈 |
| `PARTNERS_WITH` | 무엇을 함께 하는가 | 합작법인 설립 · MOU · 공동 연구 |
| `SUES` | 무엇을 두고 다투는가 | 특허침해 · 손해배상 · 가처분 |
| `COMPETES_WITH` | 무엇을 두고 겨루는가 | HBM 시장 · NAND 점유율 |
| `REGULATES` | 무엇을 하는가 | 압수수색 · 과징금 · 수출규제 |
| `ACQUIRES` | 무엇을 인수하는가 | 경영권 · 사업부문 · 지분 일부 |
| `OWNS_STAKE_IN` | 어떤 성격의 지분 | 최대주주 · 자기주식 |
| `IS_EXECUTIVE_OF` | 어떤 직위 | 대표이사 · 사외이사 |

**B군 — 노드나 다른 필드가 이미 말한다 (4종)**

| 엣지 타입 | 이미 말하는 것 | subtype |
|---|---|---|
| `HAS_EVENT` | `e.name` + `e.event_type` | **비움** (대신 `role`) |
| `IMPACTS` | `e.name` + `sign` | **비움** |
| `DEVELOPS` | Product 이름 | **비움** |
| `DEPENDS_ON` | Product 이름 | `공급의존` / `매출의존` 둘 중 하나 |

### 값을 정하는 순서

```
1순위  근거에 나온 말을 **그대로**       "카메라모듈"  ← 번역 금지
2순위  근거의 핵심을 짧은 명사구로       "성과급 협상"
3순위  그래도 없으면 **빈 문자열**        타입 이름 금지
```

**3순위가 핵심이다.** 비워야 「정보 없음」이 통계로 잡히고 프롬프트를 고칠 근거가 된다.
`_DEFAULT_SUBTYPE`으로 빈 값을 채우던 것을 없앤 이유이기도 하다 — 채우면
「영향」 899건처럼 **아무도 안 읽는 값**이 쌓인다.

### 정규화 사전은 영문·쓰레기값만 접는다

| | 처리 |
|---|---|
| 남김 | 영문 → 한글 (`vendor`→공급 · `patentinfringement`→특허침해) |
| 남김 | 쓰레기값 접기 (`other` · `test` · `synergy` · `/`) |
| **제거** | 한글 설명어 접기 — 설명을 지우고 타입 이름으로 되돌리고 있었다 |

`OWNS_STAKE_IN`·`IS_EXECUTIVE_OF`는 **건드리지 않는다.** 규칙 기반이라 이미 잘 된다.

### 검토했다가 폐기한 안 — 다시 꺼내지 않기 위해

| 안 | 폐기 이유 |
|---|---|
| subtype에 `SUPPLIES_TO`용 「무엇을」 칸을 따로 신설 | subtype이 그 일을 맡으면 칸을 더 만들 이유가 없다. **한 칸 한 가지 일** |
| 「`SUPPLIES_TO`인데 subtype에 공급어가 없으면 오류」 검사 | 적용했다 되돌림. 97건 중 **90건이 멀쩡한 관계**였다 — 타입이 이미 `SUPPLIES_TO`인데 subtype에도 「공급」을 요구하는 중복이었다. 금지어 기반(공사·매각·전환사채)으로 뒤집어 3건 잡는 검사로 교체 |
| `IMPACTS`에 `severity`(high/medium/low) 신설 | **근거에 안 쓰여 있다.** 「8명 병원 이송」이 high인지 medium인지는 판단이고 기사마다 흔들린다. 닫힌 값은 **틀려도 그럴듯해서** 전파 계산이 그대로 믿는다 |
| `DEVELOPS`에 `revenue_share` 신설 | `DEPENDS_ON/매출의존`과 같은 사실을 두 군데 적게 된다. 어긋나면 어느 쪽이 맞는지 알 수 없다 |
| `raw_expression`을 엣지에 적재 | 넣었다 되돌림. 이 필드는 원래 **12종에 안 맞는 관계의 탈출구**다 — `map_other`가 보고 되살리고, 실패하면 `unmapped_relations`에 쌓여 무엇을 놓치는지 추적한다. **적재에 성공한 엣지에는 답할 질문이 없다** |

## 5. Event 속성

```cypher
(:Event {
    event_id, name, title,
    event_type,   // 11종 고정 enum (아래)
    is_risk,      // 기업의 사업·재무·평판에 부정적인가
    confidence, source_doc, classified_at
})
```

**event_type 11종** — 리스크 조회를 가능하게 하는 축
```
사고재해 · 노무 · 규제수사 · 분쟁소송 · 품질 · 실적
공급망 · 사업확장 · 자본거래 · 제품기술 · 기타
```

**유형과 `is_risk`는 별개 축이다.** 같은 유형이라도 방향이 갈린다:
「특허 소송 패소」=risk true / 「승소」=false, 「공장 화재」=true / 「신공장 착공」=false.
실측: 분쟁소송 57건 중 리스크 39건, 사업확장 225건 중 7건.

# Part II. 저장소 구조

## 6. 경계선 — 무엇이 어디로

| 데이터 성격 | 저장소 |
|---|---|
| 관계·구조 (다중홉 탐색) | **Neo4j** |
| 정량·서술 속성 (한 기업에 종속) | **PostgreSQL** |

## 7. PostgreSQL — 27표 + 뷰 1

**빈 표는 없다.** 예전엔 「스키마가 곧 계획서」라며 미구현 표를 남겨 뒀는데,
계획이 실현되거나 폐기되면서 전부 정리됐다(2026-08-15).

```
기업 마스터·상세
  corp_code_master   DART 전체 법인 (118,535 · pg_trgm GIN으로 ER 블로킹)
  company_attributes 기업 상세 (node_key PK — corp_code 또는 norm_name)
  company_aliases    별칭 사전 (source 우선순위 hand > dart > llm > first_seen)

숫자와 원문
  financials         연도별 재무 (corp_code+bsns_year+reprt_code PK · fs_div로 연결/별도)
  business_segments  사업부문 매출·비중 + 단위 신뢰 플래그
  business_overview  사업보고서 「사업의 내용」 원문 그대로
  company_profiles   같은 절의 LLM 요약 (역할이 다르다 — 아래)
  documents          공시 원문 메타 (rcept_no PK · raw_path)

시장 정보
  market_data        일별 시세 (stock_code+trade_date PK · pykrx · 무료)
  listed_shares      유통주식수 (발행총수 − 자기주식 · 보통주만 · suspect 플래그)
  market_metrics     ★뷰 — 시총·PER·PBR·PSR을 조회할 때 계산

뉴스와 적재
  news_articles      뉴스 메타 (url PK · 본문은 저장 안 함 · extracted_at ★중복방지)
  staged_edges       적재 전 스테이징 ★권위(source of truth)
  vector_chunks      ChromaDB 청크 레지스트리

레지스트리 — 판정을 쌓아 명부 노릇을 하게 한다 (7)
  edge_subtypes · event_merge_verdicts · name_verdicts · product_names
  name_merge_verdicts · corp_code_verdicts · person_merge_verdicts

스스로에 대한 기록 (5)
  edge_audits · purged_edges · purged_nodes · extraction_runs · unmapped_relations
```

**계산되는 값은 저장하지 않는다.** `market_metrics`가 표가 아니라 뷰인 이유다.
저장하면 원본이 갱신될 때 어긋난다 — 엣지에서 실제로 겪었다(`ratio_change`
1,306건 중 15건이 `ratio − previous_ratio`와 안 맞았다). 그래서 파생 속성 6종을
엣지에서도 걷어냈다.

**같은 절을 두 표에 담는 이유** — `company_profiles`는 LLM 요약이라 챗봇이
검색하고, `business_overview`는 원문이라 화면이 인용한다. 요약만 있으면
**「사업보고서에 이렇게 적혀 있습니다」라고 인용을 못 한다** — 우리가 쓴 문장은
근거가 되지 못한다.

**「무덤」 표를 두는 이유** — 사용자가 담아 둔 노드가 검사에 걸려 사라질 수 있다.
그때 조회는 404가 아니라 **「검증 결과 제외됐습니다」 + 사유**로 답해야 한다.

## 8. ChromaDB — 컬렉션 = 벡터 공간

```
evidence     관계 근거 청크 (10,510) — 원문 문장 + 기사 제목 + URL
company      기업 소개 카드 (2,432) — 개요 + 제품 + 거래처
```

**둘뿐이다.** 스키마 주석에 `profile`·`document`도 적혀 있었지만 만들지 않았다 —
원문 전체 임베딩은 비용뿐 아니라 **검색 정확도를 떨어뜨린다**(설계 원칙 ③).

**레코드 형태**
```
id       ev_<결정적 해시>
document "근거 문장\n\n— 「기사 제목」 URL"
metadata edge_type · subtype · source_corp · target_corp · rcept_no · occurred_at
```

**임베딩 모델은 공유**하되 컬렉션을 나눈다 — 성격이 다른 텍스트가 한 공간에 있으면
검색 정확도가 떨어진다.

## 9. 크로스-DB 쓰기 순서 (분산 트랜잭션이 없으므로)

```
① PostgreSQL  staged_edges + documents          ← 권위
② Neo4j       노드·엣지 MERGE                    ← 파생 (재생성 가능)
③ ChromaDB    evidence 청크 upsert               ← 파생
④ PostgreSQL  vector_chunks 레지스트리            ← 파생 추적
⑤ PostgreSQL  staged_edges.loaded_at = now()     ← 커밋 마커 (맨 마지막)
```

- `loaded_at`을 마지막에 찍어, 어디서 죽어도 `loaded_at IS NULL` = 미완료로 재처리 큐에 남는다
- ②③④는 전부 멱등이라 재실행이 안전하게 이어진다
- **Neo4j·Chroma는 staged_edges로부터 재생성 가능** (DART 재호출 없이 그래프 재구축)

**`evidence_id`는 결정적이어야 한다.** 랜덤 UUID면 크래시 후 재실행에서 다른 id가
생겨 엣지-청크 고아가 발생한다. → `결정적 해시(source_doc + 엣지 식별자)`.

## 10. MERGE 식별자

```
노드   Company: corp_code (없으면 norm_name) · Person: person_key
       Product: norm_name · Event: event_id · Organization: norm_name
엣지   (출발, 도착, 타입, subtype)
```

**★사건 엣지를 `source_doc`으로 식별하면 안 된다.** 기사마다 새 엣지가 생겨
「삼성전자 -ACQUIRES-> 레인보우로보틱스」가 32개까지 늘었다(실측).
subtype 기준으로 MERGE하고, 여러 근거는 `evidence_ids` 배열에 누적한다.

## 11-2. 일일 갱신 파이프라인 — 수집과 추출을 가른다

위 §11이 **처음 모을 때**의 이야기라면, 여기는 **모은 뒤 매일 이어 가는** 쪽이다.

### 왜 갈라야 했나

`batch.build.news`가 RSS 수집부터 관계 추출·Neo4j 적재까지 한 덩어리로 돌았다.
그런데 화면이 필요로 하는 것과 돈이 드는 것이 다르다.

```
뉴스 화면에 필요한 것    제목·언론사·발행일·링크·어느 기업 기사인가
                      → 무료 · 8초 · PostgreSQL 만
관계 추출               본문 크롤링 → LLM
                      → 14.7원/기사 · Neo4j 를 쓴다
```

붙어 있으면 **화면을 갱신하려고 관계 추출까지 돌게 된다.** 그건 매일 돌릴 것이
못 된다. 그래서 무료·PG 전용 구간만 `batch/build/news_feed.py`로 떼어 냈다.

### 갱신 주기 — 어느 DB 를 건드리느냐로 갈린다

주기보다 **DB**가 먼저다. Neo4j 를 고치는 배치가 조회 중에 노드를 병합하면,
그 노드를 보던 사용자는 없는 키를 보게 된다.

| 단계 | DB | 비용 | 시각 | 서비스 중 |
|---|---|---|---|---|
| ① 뉴스 수집 | PG | 무료 | 매일 07:30 | **가능** |
| ② 시세 | PG | 무료 | 평일 16:00 | **가능** |
| ③ 관계 추출 | Neo4j | 14.7원/기사 | 매일 02:00 | 불가 |
| ④ 근거 검증 | Neo4j | 1차 무료·2차 유료 | ③ 직후 | 불가 |

`batch/ops/daily.py`가 넷을 순서대로 부른다. 크론은 이 한 줄만 부르면 된다.
③이 실패하면 ④를 건너뛴다 — 검증할 새 엣지가 없다.

### 수집 → 추출을 잇는 자리

```
전   news_feed → PG 저장      news → RSS 를 다시 받음   ← DB 를 안 봤다
후   news_feed → PG 저장      news → PG 미처리분을 읽음
```

RSS 는 최근 것만 뱉으니, 수집 배치가 어제 저장한 기사를 추출 배치가 오늘 돌면
**못 찾고 지나갔다.** 실측(2026-08-18): 규칙을 통과했는데 추출이 안 된 기사가
**6,403건** 쌓여 있었다. `idx_news_pending` 인덱스는 만들어져 있는데 읽는
코드가 없었다. `collector.pending_articles()`가 그 자리다.

본문은 저장하지 않으므로(§8) **추출 직전에 다시 크롤링**한다.

### 어떤 수집 방식이 일일 갱신에 맞나

우리가 하는 일은 **아는 기업의 새 기사를 받는 것**이지 새 기업을 찾는 게 아니다.
그 기준으로 보면 방향이 갈린다.

| 방식 | 방향 | 일일 갱신 적합성 |
|---|---|---|
| 언론사 RSS | 매체가 고른 기사 → 우리 기업이 있나 | **부족.** 실측: 551건 중 우리 기업 98건, 덮은 기업 18곳/477곳 |
| **네이버 검색** | **우리 기업 → 새 기사가 있나** | **맞다.** 대상을 우리가 정한다 |
| 구글 뉴스 RSS | 기간 지정(`after:`/`before:`) | 과거를 메울 때만. 원문 URL 을 안 주고 차단 시 12시간 |
| 빅카인즈 | 104개 언론사 | **전재·복제·배포 금지.** 피드로 재배포 불가 |
| 딥서치 | 국내 150·해외 50 | 유료·가격 비공개 |

국내는 뉴스 저작권 때문에 **무료 API 가 사실상 없다.** 미디어스타트업 지원사업
선정사에만 열린다. 그래서 우리가 모은 기사로 화면을 만든다 — 본문은 저장하지
않고 원문은 언론사 링크로 보내므로 저작권 문제가 없다.

### 네이버로 증분을 만드는 법

날짜 필터가 없는 게 여기서는 문제가 아니다.

```
최신순으로 받다가 이미 아는 URL 을 만나면 그 기업은 끝
```

`naver.search_latest()`가 그것이다. 따라잡을 수 있는 폭은 **질의당 1,000건**이
정한다. 실측(2026-08-18) —

```
삼성전자·SK하이닉스   하루 100건 이상   → 1,000건 ≈ 열흘치
심텍                하루 20건 안팎    → 1,000건 ≈ 50일치
```

**2~3주 방치하면 대형주에 구멍이 난다.** 조용히 넘기지 않고 못 따라잡은 기업
이름을 돌려준다 — 그때는 구글 뉴스 RSS 로 그 기간만 메운다.

### 정확도를 위해 두 겹을 더 걸었다

**하나 · 제목에 기업명이 있어야 한다.** 네이버로 기업명을 검색하면 시황 기사가
딸려 온다. 「코스피 마감시황」이 본문에서 심텍을 스치듯 언급하는데, 규칙 게이트는
「매수·거래」 같은 관계 키워드에 걸려 통과시킨다. 실측: 새 기사 59건 중 규칙
통과 5건, 그중 3건이 수급 기사였다.

**둘 · `title_hash` 로 전재 중복을 뺀다.** 같은 사건을 여러 매체가 그대로 싣는다
(뉴시스→서울신문→조선비즈). 실측: 440건 중 28건이 여기서 빠졌다.

### 남은 문제 둘 — 상한을 정하기 전에 풀어야 한다

실측(2026-08-18, 60곳 훑음, 네이버 439건) —

```
시황·수급 기사          91건 (21%)   제목에 기업명이 있어 제목 필터를 통과한다
                                   [거래소 외국인] · 특징주 · 장중 · 마감시황
의역 중복               6개 묶음     제목이 조금씩 달라 title_hash 가 못 잡는다
                                   「LG전자, 엔비디아와 로보틱스…」 5건
```

**같은 사건 5건을 추출하면 73원을 쓰고 관계는 한 벌 얻고, 시황 91건을 추출하면
1,337원을 쓰고 관계는 0건이다.** 상한을 걸기 전에 이 둘을 줄이는 게 순서다.

```
가  시황 패턴을 규칙에서 제외    무료 · 즉시 · 21% 감소
나  추출 전 사건 묶기           제목 유사도. 무료 · 구현 필요
다  추출 상한                  위 둘을 하고 남은 것에 건다
```

### 추출 상한 — 아끼려는 게 아니라 최악을 알려는 것

특정 이슈로 같은 내용이 쏟아지는 날이 있다. 상한이 있으면 **하루 최대 비용이
정해진다.** 넘친 분은 다음 날로 밀린다.

「가」·「나」를 적용했다고 보면 추정치는 이렇다(60곳 기준).

```
하루 수집 440 − 시황 91 − 중복 20 ≈ 330건
  → 규칙·라우터 통과 ~55% → 추출 ~180건 → 2,650원/일

상한 후보    100건  1,470원/일 · 월 4.4만원   자주 밀린다
            200건  2,940원/일 · 월 8.8만원   평소엔 안 걸린다  ← 권장
            300건  4,410원/일 · 월 13만원    여유
```

**단, 이는 60곳만 훑은 값이다.** 477곳 전부로 늘리면 다시 재야 한다.
상한은 감이 아니라 **며칠 돌려 실측한 뒤** 확정한다.

### 비용이 드는 곳은 한 군데다

```
라우터        0.25원/기사   gpt-4o-mini 관련성 판정
관계 추출     14.7원/기사   gpt-4o
```

라우터가 이미 대부분을 걸러 낸다. 실측(2026-08-18): 미처리 6,403건 중
라우터 탈락이 4,610건이라 **실제 추출 대상은 1,493건**(약 22,000원)이었다.
「미처리 건수 × 14.7원」으로 계산하면 4배 넘게 부풀려진다.


## 12. DART 수집 경로

```
경로 A  정형 API      최대주주·임원·타법인출자 → OWNS_STAKE_IN · IS_EXECUTIVE_OF
경로 B  공급계약 공시  단일판매·공급계약 → SUPPLIES_TO (매출 5% 이상만 공시 대상)
경로 C  사업보고서    II-2 주요제품 → Product·DEVELOPS
                     II-4 매출및수주상황 → SUPPLIES_TO ★거래처
                     II-6 주요계약 → PARTNERS_WITH·DEPENDS_ON
                     IX  계열회사현황 → OWNS_STAKE_IN
```

**II-4를 놓치면 거래처가 통째로 빈다.** 공급계약 공시는 대형 계약만 나오므로
소액 다수 거래 기업은 0건이 된다(리노공업 공시 0건 → 기업 연결이 기관투자자뿐).
62개 보고서 조사: 섹션 없음 3 · **고객사 언급 23(37%)** · 언급 없음 36.

**문자열 매칭으로 넣지 않는다** — 섹션에 「삼성전자」가 나온다고 전부 고객사가 아니다
(「대비 점유율」 맥락, 자기 이름 매칭). 뉴스와 같은 검증 체계를 태운다.

걸러낼 두 유형:
- **집단 서술** — 「삼성전자및삼성전자의종속회사」는 회사가 아니다
- **익명 표기** — 128건 중 31건(24%)이 「A사」「customer1」. 노드로 만들면
  클로봇의 A사와 삼현의 A사가 한 노드가 되어 거짓 연결이 생긴다.
  패턴은 좁게 — `^[a-z]{1,3}$`로 잡으면 `PTI`·`ASE`(실제 업체)를 오판한다.

## 13. 뉴스 파이프라인 — 8단 깔때기

비용 순서로 배치한다. 돈은 ⑦에만 든다.

```
① 수집        구글 뉴스 RSS · 8개 키워드묶음 × 기간분할     무료   14,883
② 규칙 필터   시드명 AND (관계어 OR 리스크어) — 제목만      무료    4,327 (29%)
③ 선별·배분   우선순위 + 기간 균등배분 (CAP × resolve)     무료      900
④ URL 해석    네이버 제목 재검색 → 원문 URL                무료      601 (67%)
⑤ 본문 크롤링 trafilatura (robots.txt 준수)               무료      463 (77%)
⑥ LLM 라우터  gpt-4o-mini — 관계/리스크 2트랙 판정      0.25원/건   333 (72%)
⑦ 트리플 추출 gpt-4o — 본문 통째로 읽고 (주어·관계·목적어) 14.7원/건  300
⑧ 적재        매트릭스 검증 → staged → Neo4j              -      1,417엣지
```

**②가 제목만 보는 이유** — 구글이 본문을 안 준다. 본문이 필요한 판정(⑥)은
④⑤를 거친 뒤에야 가능하다.

### 확정 설정

```bash
python -m batch.ops.run_companies --plan N \
    --years 5 --limit 240 --month-split --bucket month --resolve-factor 4
```

| 설정 | 값 | 근거 |
|---|---|---|
| `--years` | 5 | 4~5년차가 공급의 32% · 2021년부터 급감 |
| `--limit` (CAP) | 240 | 순증 88%로 포화 없음 · 예산이 상한 |
| `--resolve-factor` | 4 | 대형사 깔때기 생존율 27% (3으로는 240→193 미달) |
| `--month-split` | 켬 | 수집 편향 19배 → 2.1배 |
| `--bucket` | month | 기간 균등배분 |
| `_DELAY` | 0.8초 | 0.4=차단당함 · 1.2=안전확인 · 0.8=균형 |

**전 기업 동일 적용.** 결과가 다른 건 정책 차이가 아니라 공급 차이다
(대형은 상한에 걸리고, 중소형은 공급이 모자라 미달한다).

### 추출 우선순위

```
1위  리스크        화재·파업·과징금·압수수색 …   뉴스가 유일 경로
2위  부족 엣지     경쟁·점유율·소송·특허침해 …    뉴스가 유일 경로
3위  시드 2개 이상
4위  기타
```

「시드 2개↑」가 원래 1위였으나 실측이 가정을 반박했다 — 네 등급의 기사당 엣지가
3.40/2.92/3.46/2.82로 사실상 같았다. 그런데 시드2개↑ 기사가 매달 수십 편이라
**저밀도에서 리스크를 밀어냈다**(상위 3편만 뽑으면 리스크가 밀려나는 달 11/12).

**고정 할당은 쓰지 않는다** — 그 달에 리스크만 5건이면 5건 다 뽑혀야 하는데
할당은 억지로 다른 유형을 끼운다. 순서만 바꾸면 공급이 쏠린 달에도 대응된다.

### 기간 균등배분 (`allocate_by_period`)

정렬 2차 키가 최신순이라 예산이 최근에 전부 소진됐다:
```
분기        규칙통과   실제추출
2024-Q1        65        1
2024-Q2        73        0     ← 73건 있는데 0건
2026-Q2       512       37
```
공급이 없어서가 아니라 **선별이 쏠려서** 과거가 비었다. 월분할 수집으로는 안 고쳐진다.
→ 기간별 라운드로빈. 공급 적은 기간은 있는 만큼만, 남는 예산은 큰 기간으로 흐른다.

### 중복 방지

`extracted_at`을 기록하지 않아 재실행마다 같은 기사를 다시 뽑았다
(news_articles 5,618건 중 표시 154건인데 실제 추출은 700건 초과).
→ 추출 완료 표시 + 선별에서 제외. **순증률 34% → 88%**.

### 구글 속도 제한

2시간 반에 5,000질의를 던져 503 차단. 심텍의 480질의가 전부 실패했는데도
멈추지 않고 계속 던져 73분을 버렸고, **수집 0건인 채로 대장에 「완료」로 남아**
다시 돌지 않게 됐다.

→ ① 연속 8회 실패 시 `RateLimited` ② 지수 백오프(3→60초) ③ 수집 0건이면
대장 기록 안 함(종료코드 3) ④ 배치가 코드 3을 만나면 전체 중단 ⑤ 실패 질의 누적

**적응형 분할(분기 먼저 → 상한 걸린 분기만 월)은 실측으로 폐기했다.**
가정은 「상한 미만이면 전부 준다」였으나:
```
가온칩스 2025-Q4   분기 19 · 월 합집합 19   일치
DB하이텍 2026-Q1   분기 31 · 월 합집합 33   월에만 9 · 분기에만 7  ← 불일치
```
31건은 상한에 한참 못 미치는데도 갈렸다. 구글은 질의마다 다른 부분집합을 준다.

## 15-2. DART는 뉴스와 **다른 검사**를 써야 한다

DART 엣지의 「근거」는 API 필드를 문장으로 조립한 **템플릿**이다:

```
"국민연금공단은(는) 심텍의 5%이상주주로 지분 6.09%를 보유하고 있다."
"심텍 개발·생산 — Package Substrate (제품) … 출처: 사업보고서"
```

여기에 뉴스와 같은 LLM 근거 검증을 돌리면 **자기가 쓴 문장을 자기가 채점**하는
꼴이라 무조건 통과한다. 커버율 숫자만 오르고 잡히는 게 없다.

DART가 틀리는 방식은 **문장 해석이 아니라 필드 처리**다. 그래서 둘로 나눈다:

| 출처 | 건수 | 검사 | 실측 결과 |
|---|---|---|---|
| 구조화 필드 (지분·임원·계약공시) | 2,206 | `audit_dart_fields` — 값 범위·구조 | 이상 120 → 교정 후 13 |
| 사업보고서 본문 파싱 | 542 | `audit_dart_parsed` — **원문 XML과 문자 대조** | 528건(97%) 확인 |

본문 대조는 원문이 `data/raw_reports/`에 있어 **DART 재호출도 LLM도 없다.**

**필드 검사가 잡은 것 — LLM으로는 절대 못 잡는 유형:**

```
최대주주 76건    「최대주주 및 특수관계인 현황」 API가 그룹 전원을 주는데 전부
                 「최대주주」로 붙었다. relate가 「본인」인 행만 최대주주다.
                   현대글로비스 -최대주주-> 현대모비스  지분 0.72%  relate=계열회사
자회사 14건      상법상 자회사는 지분 50% **초과**인데 `>=`로 판정해 정확히 50%인
                 합작(JV)이 자회사가 됐다. 현대모비스 → Beijing Hyundai Mobis 50.0%
주식 종류 4건    DART는 같은 주주를 보통주·우선주 **행으로 나눠** 준다. MERGE가
                 뒤 행으로 덮어써 삼성생명의 삼성전자 지분이 **우선주 0.01%**로
                 남고 보통주 8.51%가 사라졌다. 의결권 있는 보통주를 남긴다.
```

세 건 다 **로더를 고쳤다**(`shareholder_normalizer` · `investment_normalizer`).
기존 데이터는 `fix_stake_subtypes`로 맞췄고, 주식 종류 건은 DART 재적재 때 반영된다.

**근거 정합성 판정은 4단이다.** 예/아니오 둘로는 후속 처리를 못 한다.

| 판정 | 뜻 | 다음 처리 |
|---|---|---|
| `supported` | 근거가 뒷받침한다 | 통과 |
| `wrong_type` | 관계는 있는데 유형·방향이 다르다 | `apply_retypes`가 고친다 |
| `unfounded` | 근거를 봐도 그 관계가 없다 | 사람이 본다 |
| `insufficient` | 근거가 잘려 판단 불가 | 기사 전문 재검증 |

**증분 실행** — 엣지에 `*_checked_at`을 남겨 다음 실행이 신규분만 본다.
비용이 그래프 크기가 아니라 늘어난 양에 비례한다. 무료 검사(구조 감사·토큰 대조)는
회귀 탐지를 위해 항상 전수로 돌린다.

**엣지 유형의 정의는 `pipeline/ontology.py` 한 곳에 있다.** 추출기·1차 검증기·전문
재검증기가 같은 문장을 import한다. 세 곳에 따로 적었더니 **서로 어긋났다** —
추출기는 "COMPETES_WITH는 같은 시장에서 다투는 경우만"인데 재검증기는 "1·2위로
비교되면 경쟁으로 봅니다"였다. 그래서 「SK하이닉스 영업이익률 71.5%로 엔비디아를
앞질렀다」는 **수익률 비교 문장**에서 만들어진 경쟁 관계가 「검증됨」으로 통과했다.

## 16. 검사 설계 원칙

**① 삭제보다 표시.** 「전문을 봐도 근거 없음」이 나와도 지우지 않고 표시한다.
전문 재검증에서 **66~76%가 「저장된 문장이 좁았을 뿐」**으로 확인됐다(3배치 일관).

**② 매트릭스가 최종 방어선.** LLM이 재분류를 제안해도 매트릭스에 안 맞으면 기각한다.
실측: 제안 28건 중 21건이 위반이었다(「한미반도체 -SUPPLIES_TO-> HBM4 본딩 장비」).

**③ 대칭 → 방향 전환은 위험하다.** `PARTNERS_WITH`는 저장된 방향에 뜻이 없다.
`SUPPLIES_TO`로 바꾸면 무의미한 방향을 물려받는다. 재분류 시 `direction_checked_at`을
지워 방향 검사가 다시 보게 한다.

**④ 조용한 실패를 막는다.** LLM 호출 실패를 `supported=true`로 돌려주면 통과와
구별되지 않는다. `failed` 표시를 달아 검사 완료로 기록하지 않는다.

**⑤ 커버리지를 측정한다.** `coverage_report`는 「무엇이 걸렸나」가 아니라
**「무엇을 아직 안 봤나」**를 본다. 정의해 둔 검사를 다 돌렸다는 것과 그래프가
정확하다는 것은 다르다.

**⑥ 검사기를 고칠 때는 회귀 테스트로 먼저 잰다.** 프롬프트를 고칠 때마다 전량
(3,775건·1,600원·12분)을 돌리면 **한쪽으로 쏠린 것을 늦게 발견한다.** 실측:
거짓 음성을 고치려고 실패 사례를 넣었더니 거절률이 **8% → 49%**가 됐다.
「로보티즈는 자기주식을 매각했다」를 두고 *"'사건'이라는 표현이 없어서"* HAS_EVENT를
부정했다. `verifier_selftest`는 실제 근거 20건(받아들일 것 13 · 물리칠 것 7)을
**양쪽 다** 재고, 한쪽 정확도만 좋으면 「쏠렸습니다」라고 알린다. 40원·15초다.

**⑦ 판정을 물으려면 기호가 아니라 문장으로 묻는다.** `(A) -[SUPPLIES_TO]-> (B)`를
그대로 주면 모델이 화살표를 「관계가 있다」로만 읽고 방향을 무시한다. 실측:
「SK하이닉스가 ASML에 공급한다」를 두고 *"SK하이닉스가 ASML에 공급**받는** 관계가
성립합니다 → 뒷받침됨"*이라고 했다. 역할을 이름표로 못 박은 한국어 문장
(「파는 쪽은 A이고 사는 쪽은 B이다」)으로 바꾸고, 판정 전에 **근거가 말하는 역할을
먼저 적게**(`finding` 필드를 `verdict`보다 앞에) 하니 잡혔다.

**⑧ 검사 조건이 다른 배치 때문에 무력화되지 않는지 본다.** 사건성 검사는
`WHERE event_type = '뉴스이슈'`였는데, `classify_events`가 11종 유형을 붙이면서
그 값이 그래프에서 사라졌다. 검사는 계속 「0건 점검」을 출력했고 **아무도 안 보는
통과**로 보였다. 검사 대상은 다른 배치가 바꾸는 값이 아니라 **자기 검사 시점 표시**로
정한다.

**⑨ 표시했으면 조회에서 걸러야 한다.** 「삭제보다 표시」는 조회 쪽이 그 표시를
볼 때만 성립한다. 실측: 재검증이 821건을 의심으로 표시했는데 `relations_of()`가
`grounding_suspect`를 안 봐서 **화면에 그대로 나갔다.** 그것도 confidence가 높아
상위에 떴다(SK하이닉스 -COMPETES_WITH-> 엔비디아, 0.9).
판정마다 다루는 법이 다르다:

```
unfounded · insufficient   숨긴다 — 관계가 있다고 말할 수 없다
wrong_type                 숨기지 않고 **점수만 깎는다**(×0.5) — 관계 자체는 실재한다
```

파급 계산(`propagate_risk`)도 같은 엣지를 타므로 **거기도 막아야 한다.** 조회만
막으면 같은 오류가 파급 결과로 샌다.

**⑩ 「제안이 틀렸다」가 「원래가 맞다」는 뜻은 아니다.** 매트릭스가 재분류 제안을
기각할 때 원래 유형의 의심까지 자동으로 걷으면 안 된다. 실측: 기각된 DEVELOPS
104건을 근거별로 갈랐더니 둘이 섞여 있었다.

```
공동개발형 89건  "한미반도체 역시 SK하이닉스와 협력하며 하이브리드본더를 개발 중"
                 → DEVELOPS가 맞다. 의심 해제.
공급계약형 15건  "SK하이닉스가 HBM 핵심 제조장비 **발주**에 나섰다"
                 → SK하이닉스는 **사는 쪽**이다. 여기서 걷으면 진짜 오류가 묻힌다.
```

근거에 「만든다·개발한다·양산한다」가 있는지로 가른다.

**⑪ 병합은 스칼라를 배열로 바꾼다.** `apoc.refactor.mergeNodes`의
`properties: 'combine'`은 값이 다르면 **배열로 합친다**. 근거를 안 버리는
장점이 있지만, 스칼라로 읽던 코드가 죽는다:

```
n.name = ['어플라이드머티어리얼즈코리아', '어플라이드머티어리얼즈']
r.source_doc = ['20260319001000', 'https://zdnet.co.kr/…']
   → TypeError: unhashable type: 'list'
```

병합 직후 되돌린다 — 대표값을 스칼라로 두고 목록은 `*_variants`에 남긴다.
**노드와 엣지를 둘 다** 봐야 한다(엣지만 고쳤다가 `n.name`에서 또 죽었다).

## 17. 개체해소 (ER)

### Event ER — 유형어 2등급

```
UNIQUE   화재·폭발·파업·과징금·소송·갈등·난항 …
         한 기업에 같은 달 두 번 나기 어렵다
         → 기업 + 유형어 일치 · 기간 ±2개월
           (같은 달은 무조건, 1~2개월은 이름 유사도 0.6 이상 요구)

RECURRING 공급계약·수주·양산·증설·투자 …
         같은 달에 여러 건이 실제로 있을 수 있다
         → 기업 + 연월 + 유형어 + 이름 유사도 0.6

유형어 없음  기업 + 연월 + 이름 유사도 0.8 (더 엄격)
```

**기간을 풀면 이름 검사를 붙여야 한다.** ±2개월만 허용하고 이름을 안 보면
「블랙웰 결함 ← 엑시노스 보안 결함」이 붙는다(유사도 0.50).

**토큰은 영숫자를 붙여서 자른다.** 음차 지원을 넣으며 `[A-Za-z]+|[0-9]+`로 쪼갰더니
`HBM4`가 `HBM`+`4`가 되어 세대 구분이 사라졌다.

**음차 사전은 좁게.** 문자 종류가 다르다는 것만으로 짝지으면 12쌍 중 11쌍이
무관했다(「메모리 반도체 생산 확대」~「CXMT 상장」). 사전에 있는 것만 변환한다.

### Person ER
`이름 + 생년월` 일치 시 병합. 생년월이 다르면 동명이인으로 보류.

### Product 정규화
```
1층 괄호 병기   「고대역폭메모리(HBM)」 → HBM (괄호가 **끝에 있을 때만**)
2층 전체 별칭   D램=DRAM · 낸드플래시=NAND Flash · TC본더=열압착본더
3층 토큰 치환   「서버 D램」→「서버 DRAM」 (낱말 경계 유지)
```
**부분일치 금지** — HBM3≠HBM4, 범용DRAM≠DRAM, 비메모리≠메모리.
자기검사 15쌍(must_differ 10 · must_equal 5)이 import 시점에 확인한다.

# Part V. 서빙

## 18. 관계 유효성 — 지우지 않고 약화한다

```
is_current=false 또는 valid_until 경과  → expired  (가중 0.3)
last_seen ≤ 갱신주기 × 1.5              → current  (1.0)
초과                                    → stale    (0.6)
날짜 없음                                → unknown  (0.7)
```

**왜 지우지 않는가** — 「2년간 언급 없음」은 종료의 증거가 아니라 정보 없음이다.
뉴스는 관계의 시작은 보도해도 종료는 보도하지 않는다. 그래서 뉴스만으로는 알 수 없다.

```
지금:  "삼성전자는 세메스로부터 공급받는다"        ← 근거 없는 현재형
바꿔:  "2024-06에 그렇게 보도됨 (25개월 미갱신)"   ← 관측 사실
```

**종료를 알 수 있는 세 경로**
```
① 근거가 소멸을 말함        「전량 매각」「생산 영구 중단」 → detect_ended_relations
② DART 재적재에서 누락      작년 보고서엔 있고 올해 없음 → expire_missing_dart
③ 오래됨                    알 수 없음. 가중치만 낮춤
```

## 19. 리스크 파급 — 저장하지 않고 질의 시 계산

사건 569건 중 **81%가 IMPACTS 0~1개**다. 기사가 파급을 명시하지 않기 때문이고,
데이터를 더 모아도 안 고쳐진다.

```
[기사가 말한 것]   청주 화재 -IMPACTS-> SK하이닉스
[그래프가 아는 것]  SK하이닉스 -SUPPLIES_TO-> 엔비디아
─────────────────────────────────────────
[계산한 것]        청주 화재 → 엔비디아 (2홉, 감쇠 적용)
```

**저장하지 않는 이유** — 섞이면 근거를 구분할 수 없다. 결과에 항상 경로를 함께 낸다.

```
감쇠 = 홉(0.55) × 신선도 × 허브 페널티(40/(40+차수-1))
```

**허브 페널티는 IDF와 같은 원리** — 「삼성전자를 안다」는 거의 모두가 그러하므로
정보량이 적다.

## 20. 허브 문제는 질의 설계 문제다

```
2홉 도달 (한미반도체 기준)
  모든 엣지            604개
  공급 엣지만          147개   ← 76%↓
  공급 엣지 + 방향 유지   33개   ← 95%↓
```

삼성전자 차수 833 중 `SUPPLIES_TO`는 120(14%)뿐이다. **무차별 순회가 문제**이지
허브 자체가 결함이 아니다. 허브는 사실이므로 지우지 않고 질의에서 처리한다.

**탐색 프로파일** — 질의 유형별로 엣지를 제한한다

| 질의 유형 | 허용 엣지 |
|---|---|
| 공급망 리스크 | `SUPPLIES_TO` · `DEPENDS_ON` · `DEVELOPS` |
| 경쟁·반사이익 | `COMPETES_WITH` · `IMPACTS` |
| 지배구조 | `OWNS_STAKE_IN` · `IS_EXECUTIVE_OF` · `ACQUIRES` |
| 법적·규제 | `SUES` · `REGULATES` · `IMPACTS` |

**Organization·Event는 경유지 금지** — 끝단으로만.

## 21. 추론 계층 — 남은 과제

`app/services/graph_service.py`에 조회·파급 계산은 있으나 **자연어 질의를 받는
부분이 없다.** 실제 질의를 손으로 조립해보고 드러난 것:

**① NL → 탐색 프로파일 변환 (핵심)**
```
"생산 차질"  → event_type ∈ {사고재해, 공급망} · 엣지 SUPPLIES_TO/DEPENDS_ON
"규제 리스크" → event_type ∈ {규제수사, 분쟁소송} · 엣지 SUES/REGULATES
```

**② 사건 단위 중복 제거** — 같은 Event에 여러 엣지가 붙어 같은 사건이 두 번 조회됐다.
엣지가 아니라 Event 노드 기준으로 묶어야 한다.

**③ 파급 신뢰도 문턱** — 파급 대상이 모든 사건에서 동일했다(SK하이닉스 고객사 목록이
그대로). `corroboration ≥ 2` 같은 문턱이 필요하나, 근거 2건 이상이 5%뿐이라
회수량과 맞바꿔야 한다.

**④ 심각도 점수** — `is_risk`는 있으나 정도가 없다. 화재와 전략적 연기가 같은 무게다.
```
심각도 = is_risk × 유형 가중 × log(근거 수) × 신선도
```

**이미 갖춰진 것 (다시 만들지 말 것)**

| 기능 | 위치 |
|---|---|
| 신선도 판정 | `pipeline/freshness.py` |
| 신선도 적용 조회 | `graph_service.relations_of()` |
| 리스크 파급 계산 | `graph_service.propagate_risk()` |
| 사건 유형·리스크 | Event의 `event_type`·`is_risk` |
| 근거 회수·의미검색 | ChromaDB `evidence` 컬렉션 |

## 21-2. 코드 배치 — 도구가 늘어나는 것을 관리한다

문제를 하나 고칠 때마다 배치 스크립트가 하나씩 늘었다. 52개가 되자 **「그 검사가
어디 있더라」**를 매번 찾게 됐고, 옛 프로토타입과 살아 있는 코드가 섞였다.

**동사로 나눈다.** 접두어(`build_`·`fix_`·`audit_`)를 파일 이름에서 떼고
디렉터리가 그 역할을 하게 했다 — 같은 정보를 두 곳에 쓰지 않는다.

```
batch/build/    수집·적재 — 데이터를 **만든다**
batch/repair/   교정 — 이미 들어온 것을 **고친다** (대부분 0원)
batch/audit/    검사 — 무엇이 틀렸나 **본다** (지우지 않고 표시만)
batch/ops/      운영 — **돌린다·본다**
pipeline/       라이브러리 — CLI를 갖지 않는다
```

**의존은 한 방향** — `batch/` → `pipeline/` → `app/core`.
`batch/` 스크립트끼리는 서로 import하지 않는다(`ops/finalize`만 서브프로세스로 실행).

### 병합 기준 — 「같이 도는가」

파일이 많다고 무조건 합치면 무관한 코드가 한 파일에 섞여 더 나빠진다. 셋을 다
만족할 때만 합쳤다: **항상 같이 돈다 · 개념이 하나다 · 합쳐도 400줄 이내.**

| 합친 것 | 왜 |
|---|---|
| `audit/selftest` ← 추출기+검증기 테스트 | 같은 목적·같은 출력, 언제나 같이 돈다 |
| `audit/dart` ← 필드 검사+원문 대조 | 「DART가 맞나」 하나의 질문 |
| `audit/freshness` ← 뉴스 종료+DART 누락 | 둘 다 `is_current=false`를 만든다 |
| `repair/evidence` ← 중복 병합+고아 삭제 | 벡터DB 위생, 순서가 정해져 있다 |
| `repair/node_identity` ← 키 재계산+중복 병합 | 「같은 것을 하나로」, 재계산 뒤라야 병합이 보인다 |
| `validators/dart` ← 주주·임원·출자 검증기 3개 | 하는 일이 같고 헬퍼를 공유한다 |

**합치지 않은 것도 있다.** `audit/grounding`과 `audit/grounding_fulltext`는 2단계
검사지만 합치면 622줄이고 동작 방식이 다르다(저장된 청크 조회 vs 기사 크롤링).
`repair/`의 `executive_titles`·`stake_subtypes`·`segment_units`도 항상 같이 돌지만
**도메인이 서로 무관**해 한 파일에 넣으면 읽기 나빠진다.

### 지운 것 — 옛 3단계 경로

`fetch_dart_to_json` → `normalize_json` → `import_json_to_neo4j`가 `build.graph`
(staging → graph_loader)로 대체됐는데 남아 있었다. 종속 모듈까지 **10파일·1,032줄**.
어디서도 import되지 않고 문서에도 없어 「죽었다」가 확실했다.

## 22. 표본 심층검사 — 자동 검사가 못 잡는 것

자동 검사는 「정해둔 실패 방식」만 잡는다. 정의되지 않은 실패는 사람이 근거를 읽어야
드러난다. 실제로 한 기업 쌍을 정독한 것만으로 결함 4건이 나왔고, 그 중 3건이 영구
검사가 되어 전체 엣지에 적용됐다.

```bash
python -m batch.audit.spot_check --per-type 1 --source news --seed 42
```

**층화 무작위로 뽑는다** — 대기업 쌍만 보면 「대형사·대칭 엣지」 유형만 나온다.
엣지 유형마다 골고루, 그 안에서는 무작위로.

각 표본에 묻는다:
```
1. 이 근거가 정말 이 관계를 말하는가?  2. 방향은?  3. 유형은?
4. 노드 이름은 근거에서 나왔나?
5. ★자동 검사가 못 잡았다면, 어떤 검사가 있어야 했나?
```

**5번이 이 도구의 존재 이유다.** 발견을 영구 검사로 바꾸지 않으면 다음에 또 놓친다.

## 25. 사업보고서 표의 단위 — 추출이 아니라 대조로 푼다

품목별 매출 표는 「(단위: 백만원)」이 **표 밖 캡션**에 있어 본문만 보는 LLM이
자주 틀린다. 실측(2026-08-01): 56개사 중 **39개사(70%)**의 부문 매출이 1,000배
또는 100만배 어긋나 있었다. 프롬프트로 "천원 단위면 ×1000 하세요"라고 부탁해도
지켜지지 않았다.

**LLM에게 환산을 시키지 않는다.** 전사 매출액을 `financials`에서 이미 정확히
알고 있으므로 배수를 역산한다:

```
배수 = 전사매출 / 부문합  →  {1, 1000, 1_000_000} 중 가까운 값으로 스냅
스냅 후 오차가 ±25~35% 안일 때만 적용. 아니면 값을 그대로 두고 못 믿는다고 표시.
```

`batch/repair/segment_units.py` — 31개사·97개 부문 교정(교정 후 오차 대부분 0%).
**8개사는 어떤 배수로도 안 맞아 판단을 보류했다.** 틀린 값을 다른 틀린 값으로
바꾸는 것이 제일 나쁘다.
