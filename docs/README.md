## 1. 한 줄 정의

DART 공시와 비즈니스 뉴스를 지식그래프로 결합해, 기업 간 **N차 연쇄 파급 리스크**를
시각화하고 **모든 주장에 원문 근거를 붙여** 답하는 분석 플랫폼.

## 2. 문제와 해법

| 문제 | BizNode의 해법 |
|---|---|
| 공급망 리스크가 2~3단계 건너 오는데 개별 기업만 봐서는 안 보인다 | 지식그래프 + 질의 시점 파급 계산 |
| LLM 요약은 그럴듯하지만 출처를 못 댄다 | **모든 관계에 원문 문장·기사 URL** (11,060/11,060 = 100%) |
| 2년 전 끝난 계약이 현재 리스크로 표시된다 | 신선도 판정(current/stale/expired) + 종료 관계 탐지 |
| 같은 사건이 기사마다 다른 이름으로 흩어진다 | 사건 병합 + `timeline`으로 국면 보존 |

## 4. 서비스 구성 — 화면 여섯

목업의 화면 구성입니다. 각 화면 아래 **필요한 조회 함수**를 적어 뒀고,
이 목록이 그대로 [연동 계약](#7-연동-경계)이 됩니다.

```
좌측 메뉴   홈 · 워크스페이스 · 뉴스/이슈 · 리서치 보관함 · 마이페이지
상단 고정   통합 검색 · 알림 · 프로필
            (워크스페이스 화면에서만 워크스페이스 전환기가 켜짐)
```

### 4-1. 홈

처음 온 사용자와 쓰던 사용자에게 **다른 것**을 보여줍니다.

| 영역 | 내용 |
|---|---|
| 검색 | 기업명·이슈 키워드 통합 검색. 첫 화면의 **할 일은 이것 하나** |
| 트렌드 | 최근 많이 언급된 기업·이슈 |
| 인사이트 | 「이 회사에 이런 일이 있었다」 요약 카드 + 왜 그렇게 봤는지 |
| 최근 활동 | 내가 최근 본 기업·워크스페이스 |
| (신규) | 온보딩 4단계 — 검색 → 워크스페이스 만들기 → 기업 담기 → 그래프 보기 |

**필요한 함수** — `search(q)` · `trending()` · `recent_insights()`

### 4-2. 워크스페이스 ★핵심 화면

세로 3분할입니다. **가운데 그래프에서 무엇을 클릭했느냐에 따라 왼쪽이 바뀝니다.**

```
┌── 좌 패널 ──┬──── 그래프 캔버스 ────┬── 챗봇 ──┐
│  요약       │  노드·선을 클릭        │  질의    │
│  (선택 대상)│  필터 칩으로 걸러 봄    │  근거인용 │
└────────────┴──────────────────────┴──────────┘
```

**좌 패널은 두 모드입니다. 이게 「기업 상세」와 다른 지점입니다.**

| 노드를 클릭하면 — **기업 요약** | 선을 클릭하면 — **관계 상세** |
|---|---|
| 기본 정보 (업종·시장·설립) | 관계 개요 (유형·방향) |
| 개요 한 줄 | 관계 상세 (subtype·금액·지분율) |
| 재무 (억원·연결) | **근거 원문** — 그대로 인용 |
| 리스크 요약 | 유효 기간 (신선도) |
| **이 워크스페이스와의 관계** | **리스크 전파** — 이 연결을 타고 닿는 위험 |
| 관련 뉴스 | 데이터 검증 (근거검증 통과 여부) |
| 신뢰도 | |
| → **「상세 페이지로 가기」** | |

**필요한 함수** — `company_summary(key, workspace)` · `relation_detail(edge_id)` ·
`neighbors(keys, depth)` · `retrieve(question)`

> `company_summary`는 **워크스페이스 문맥을 받습니다.** 「이 워크스페이스와의 관계」는
> 담아 둔 다른 기업들과 어떻게 이어지는지라서, 기업만으로는 답이 안 나옵니다.

### 4-3. 기업 상세 ★워크스페이스 좌 패널과 다른 화면

좌 패널이 **「지금 보고 있는 그래프 안에서의 이 회사」**라면,
상세 화면은 **「이 회사 자체의 전부」**입니다. 워크스페이스 없이도 열립니다.

| 블록 | 내용 | 출처 |
|---|---|---|
| 시장 정보 | 시장·종목코드·주가·등락률·거래량·시가총액·PER·PBR·PSR | PG `market_metrics` (뷰) |
| 재무 3개년 + 비율 | 매출·영업이익·순이익·부채비율 | PG `financials` |
| 사업 개요 | 사업보고서 「사업의 내용」 원문 | PG `business_overview` |
| 사업부문 | 부문별 매출과 비중 | PG `business_segments` |
| 제품·기술 | 만드는 것 | `DEVELOPS` |
| 연관 기업 | 공급·협력·경쟁 상대 | `SUPPLIES_TO`·`PARTNERS_WITH`·`COMPETES_WITH` |
| 기업 관계 그래프 | 이 회사 중심 1~2차 그래프 | Neo4j |
| 리스크·사건 | 사건 목록 (시계열 포함) | `HAS_EVENT` + `timeline` |
| 리스크 파급 | 이 회사에서 시작되는 파급 경로 | `IMPACTS` + `SUPPLIES_TO` |
| 관련 뉴스 | 근거가 된 기사 목록 | PG `news_articles` |
| 공시 | DART 공시 목록 | PG `documents` |
| 인물 | 임원 | `IS_EXECUTIVE_OF` |
| 지배구조 | **이 회사를 소유한 쪽** / **이 회사가 소유한 쪽** | `OWNS_STAKE_IN` 양방향 |

**필요한 함수** — `company_detail(key)` · `company_graph(key, depth)` ·
`events_of(key)` · `propagate_risk(event)` · `news_of(key)` · `filings_of(key)` ·
`market_of(key, days)`

> 지배구조가 **양방향**인 것에 주의해야 합니다. 같은 `OWNS_STAKE_IN`을
> 들어오는 방향과 나가는 방향으로 나눠 보여줍니다.

> **시가총액·PER·PBR·PSR은 저장하지 않고 조회할 때 계산합니다.** 남의 API에서
> 받아 오면 연결인지 별도인지, 어느 분기 실적인지를 모릅니다. 우리는
> 종가 × 유통주식수와 우리 `financials`로 직접 내므로 화면에
> **「2025년 연결 기준」이라고 밝힐 수 있습니다.**

### 4-4. 뉴스 / 이슈

필터를 **세 축으로 나눕니다.** 한 줄에 몰면 「위험만」과 「내 워크스페이스」가
서로 배타적인지 겹쳐 쓸 수 있는지 알 수 없습니다.

```
축 1   전체 · 공급망 · 지분 · 규제 · 사건        (주제)
축 2   전체 · 내 워크스페이스                    (범위)
축 3   최신순 · 영향도순                         (정렬)
```

「최근 위험 사건」은 `IMPACTS.sign = negative`인 사건을 영향받는 기업 수로 정렬합니다.

**필요한 함수** — `news_feed(filters, sort)` · `risk_events(limit)`

### 4-5. 리서치 보관함

워크스페이스 상태를 **얼린 스냅샷**으로 저장합니다. 나중에 그래프가 바뀌어도
그때 본 것이 그대로 남습니다. 인증 없이 링크로 공유합니다.

**필요한 함수** — 없음. **백엔드 소관**입니다(스냅샷 저장·조회는 사용자 데이터).

### 4-6. 마이페이지

계정 · 알림 설정 · 내 워크스페이스 관리.

**필요한 함수** — 없음. **백엔드 소관**입니다.

## 5. 이 데이터가 가진 것

화면 설명에 반복해서 나온 「믿을 만한 이유」입니다. 넷 다 **수집 단계에서 넣어 둔
장치**라 나중에 붙일 수 없습니다.

### ㄱ. 모든 관계에 근거가 붙어 있습니다

```
관계   한미반도체 ─SUPPLIES_TO→ SK하이닉스
근거   「한미반도체는 SK하이닉스와 단일판매·공급계약을 체결하였다.
       계약금액은 44,200,000,000원이다. 최근 매출액 대비 7.66%에 해당한다.」
출처   DART 공시 접수번호 20260608800436
```

관계마다 `evidence_id`가 있고, 그 id로 ChromaDB에서 원문을 꺼냅니다.
Neo4j 엣지 속성 · PostgreSQL `vector_chunks` · ChromaDB 문서 id가 **같은 값**입니다.

### ㄴ. 오래된 관계를 지우지 않고 「언제 관측됐는지」로 말합니다

뉴스는 관계의 시작은 보도해도 **종료는 보도하지 않습니다.** 그래서 오래된 관계를
지우면 살아 있는 관계를 잃고, 그대로 두면 끝난 관계를 현재형으로 말하게 됩니다.

```
✗  "삼성전자는 세메스로부터 공급받는다"          근거 없는 현재형
✓  "2024-06에 그렇게 보도됨 (25개월 미갱신)"     관측 사실
```

판정은 산수입니다 — 모델을 안 부릅니다(`pipeline/freshness.py`).

| 판정 | 조건 | 가중치 |
|---|---|---|
| `expired` | `is_current=false` 또는 `valid_until` 경과 | 0.3 |
| `current` | `last_seen`이 `refresh_cycle_days × 1.5` 이내 | 1.0 |
| `stale` | 그 이상 | 0.6 |
| `unknown` | 날짜 정보 없음 | 0.7 |

**실효 신뢰도 = `confidence` × 가중치.** DART는 주기가 365일이라 547일까지 `current`입니다
— 사업보고서가 연 1회라 11개월 미갱신이 정상이기 때문입니다.

### ㄷ. 사건의 국면이 한 노드에 모입니다

```
「파업 리스크」                    「TC본더 갈등」
  2022-03  삼성전자 노조 파업 위기     2025-04  SK하이닉스와의 갈등
  2024-05  전국삼성전자노동조합 파업    2025-05  TC본더 특허권 침해 소송
  2024-09  인도 공장 무기한 파업       2025-07  TC본더 4 양산
  2025-02  노조 리스크
```

현재 193개 사건이 이렇게 묶여 있습니다. 흩어진 기사가 아니라 **하나의 줄거리**로 보여줍니다.

### ㄹ. 근거 없는 관계는 화면에 안 나옵니다

추출한 관계를 다시 검증합니다. 1차는 저장된 근거 문장만 보고, 걸린 것은 2차로
기사 전문까지 읽습니다. 걸린 관계는 **조회에서 제외**되고 파급 계산에도 안 들어갑니다.

> 파급은 「이 관계가 있다」를 전제로 계산하므로, 근거 없는 관계 하나가
> **없는 파급을 만들어 냅니다.**

## 6. 아키텍처 — 저장소 셋

같은 사실을 세 곳에 나눠 담습니다. **무엇을 묻느냐**로 갈 곳이 정해집니다.

| 저장소 | 맡는 질문 | 담긴 것 | 규모 |
|---|---|---|---|
| **Neo4j** | 누가 누구와 어떤 관계인가 — 경로를 따라가는 질문 | 노드 5종 · 관계 12종. 화면에 띄우거나 탐색에 쓰는 값만 | 7,755노드 11,060엣지 |
| **PostgreSQL** | 숫자와 이력 — 한 건씩 들여다보는 질문 | 재무 · 시세 · 기업 상세 · 공시 메타 · 검사 기록 | 26표 + 뷰 1 · 110MB |
| **ChromaDB** | 말로 찾기 — 챗봇이 인용할 원문 | 근거 문장 · 기업 소개문 | 12,942청크 |

**셋을 잇는 열쇠는 두 개입니다.**

- `corp_code` — DART 8자리 기업 번호. **해외 기업에는 없어서** 그 경우 `norm_name`이 대신합니다.
- `evidence_id` — 근거 문장 하나의 id. 관계에서 원문으로 가는 유일한 다리.

### 노드에 두는 것과 PG에 두는 것

```
Neo4j 에    그래프 위에서 쓰는 것 — 노드·엣지를 가르거나, 탐색 중 거르거나,
            카드에 바로 띄우는 값
            Company 11가지: name · norm_name · entity_kind · is_stub
            · first_seen · last_seen · corp_code · stock_code · market
            · ksic · also_names

PostgreSQL 에  한 건씩 들여다보는 것 — 상세 화면에서 조회할 뿐 탐색에 안 쓰는 값,
            그리고 시계열 전체
            대표자 · 설립일 · 영문명 · 업종 설명 · 연도별 재무 · 검사 이력
```

> **Neo4j에는 「빈칸」이 없습니다.** 속성에 `null`을 넣으면 저장되는 게 아니라
> **속성이 삭제됩니다.** 다만 읽을 때는 구분되지 않으므로(없는 속성도 `null`),
> 프론트는 신경 쓸 필요가 없습니다.
>
> 그래서 **판정 결과는 반드시 채웁니다** — 속성이 없으면 「아니다」와
> 「아직 안 봤다」가 조회에서 똑같이 `null`이 되기 때문입니다.
> `name`·`norm_name`·`is_stub`·`entity_kind`·`first_seen`·`last_seen`이 전부 100%입니다.

## 7. 연동 경계

**데이터 팀은 세 저장소를 합쳐 「답」을 만들고, 백엔드는 그 답을 HTTP로 감쌉니다.**

백엔드가 Cypher를 직접 짜면 신선도 판정과 근거 검증을 매번 다시 구현해야 하고,
그러면 화면마다 결과가 달라집니다. 그래서 **그래프를 읽는 통로를 하나로** 둡니다.

```
프론트엔드 ──HTTP──▶ 백엔드 ──?──▶ 데이터 서비스 계층 ──▶ Neo4j / PostgreSQL / ChromaDB
                              ↑
                    여기를 어떻게 잇느냐가 아래 세 안
```

| 안 | 방식 | 조건 | 평가 |
|---|---|---|---|
| **A** | 데이터 레포가 **내부 HTTP API**를 띄우고 백엔드가 호출 | 언어 무관 | **권장.** 레포 셋을 나눈 이유와 맞고 배포가 독립적 |
| B | 데이터 레포를 **파이썬 패키지**로 설치해 백엔드가 `import` | 백엔드도 파이썬이어야 함 · 같은 서버 배포 | 네트워크 홉이 없지만 배포가 묶임 |
| C | 백엔드가 **DB에 직접** 접근 | — | 권장하지 않음. 검증·신선도 로직이 중복되고 화면마다 결과가 갈림 |

> 같은 VM 안에서 통신하므로 **A의 네트워크 비용은 무시할 수준**입니다.
> 백엔드가 파이썬이면 B도 가능하니, 이건 백엔드 담당이 정하면 됩니다.

### 조회 함수 목록

| 함수 | 돌려주는 것 | 쓰는 화면 | 상태 |
|---|---|---|---|
| `search(q)` | 이름·별칭으로 기업 찾기 | 전 화면 | 해야 함 |
| `company_summary(key, ws)` | 워크스페이스 문맥의 기업 요약 | 워크스페이스 좌 패널 | 해야 함 |
| `company_detail(key)` | 기업 자체의 전부 | 기업 상세 | 해야 함 |
| `relation_detail(edge_id)` | 관계 + 근거 원문 + 전파 | 워크스페이스 좌 패널 | 해야 함 |
| `neighbors(keys, depth)` | N칸 이웃 그래프 | 워크스페이스 캔버스 | 해야 함 |
| `company_graph(key, depth)` | 한 기업 중심 그래프 | 기업 상세 | 해야 함 |
| `relations_of(key)` | 관계 목록 (신선도·검증 적용) | 여러 곳 | **있음** |
| `events_of(key)` | 사건 목록 (시계열 포함) | 상세 · 워크스페이스 | 해야 함 |
| `propagate_risk(event)` | 파급 경로와 점수 | 상세 · 워크스페이스 | **있음** |
| `news_feed(filters, sort)` | 뉴스 목록 | 뉴스/이슈 | 해야 함 |
| `risk_events(limit)` | 최근 위험 사건 | 뉴스/이슈 · 홈 | 해야 함 |
| `news_of(key)` · `filings_of(key)` | 기업별 기사·공시 | 기업 상세 | 해야 함 |
| `market_of(key, days)` | 주가·등락률·시총·PER·PBR·PSR | 기업 상세 · 요약 | 해야 함 |
| `trending()` · `recent_insights()` | 홈 카드 | 홈 | 해야 함 |
| `retrieve(question)` | 질문 관련 근거 + 그래프 조각 | 챗봇 | 해야 함 |

### 역할

| 담당 | 맡는 것 |
|---|---|
| **데이터** | 세 저장소 운영 · 위 함수 · 스키마 문서 · 수집 배치 |
| **백엔드** | HTTP 엔드포인트 · 인증 · **워크스페이스** · **리서치 보관함** · 캐시 |
| **추론** | `retrieve()`가 준 재료로 프롬프트 구성 · 답변 생성 · 인용 붙이기 |
| **프론트** | 그래프 시각화 · 화면 상태 |

> **워크스페이스와 보관함은 백엔드 것입니다.** 「사용자가 어느 기업을 담아 뒀나」는
> 그래프가 아니라 사용자 데이터입니다. 백엔드 DB에 두고, 그래프 쪽에는
> 기업 키 목록만 넘겨 조회합니다.

### 백엔드가 알아야 할 것

- `company_attributes`에 **행이 없는 회사가 538곳** 있습니다(해외 기업). `LEFT JOIN`으로 짜야 하고 **Neo4j 노드가 마스터**입니다.
- `corp_code`가 없는 회사가 3분의 2(2,268곳)입니다. 해외이거나, 동명이 여럿이라 못 좁힌 경우입니다. 어느 쪽이든 **DART 연결을 하지 않고** `norm_name`으로 식별합니다.
- **해외 기업을 가려내는 확실한 필드가 아직 없습니다.** `market`은 DART가 출처라 해외 시장 값이 없고, `entity_kind`의 `해외`도 9곳뿐입니다(엔비디아·TSMC·ASML이 전부 `기업`으로 들어가 있습니다). **「해외 기업」이라고 단정해 표시하지 마세요.**
- 시장 지표(`market_of`)는 **시세가 있는 417곳만** 있습니다. 나머지는 빈 응답이 정상입니다.
- 전체 필드 목록과 실제 채움률은 **데이터 사전**에 있습니다.

## 8. 데이터 갱신 — 무엇을 얼마나 자주 다시 받나

수집원마다 **바뀌는 속도가 다릅니다.** 주가는 하루에 한 번 확정되고, 재무는
분기에 한 번, 유통주식수는 1년에 한 번 바뀝니다. 그래서 하나의 주기로 묶지 않고
**항목별로 나눠** 돌립니다.

| 항목 | 주기 | 명령 | 비용 | 서비스 중 실행 |
|---|---|---|---|---|
| 주가·거래량·등락률 | **매일** 장 마감 후 (18:00) | `batch.build.market_data` | 0원 | 가능 |
| 공시 목록 | **매일** (07:00) | `batch.build.disclosures` | 0원 | 가능 |
| 재무 | **분기** (3·5·8·11월 중순) | `batch.build.financials` | 0원 | 가능 |
| 유통주식수 | **연 1회** 사업보고서 이후 | `batch.build.market_data --shares-only` | 0원 | 가능 |
| 사업 개요 | **연 1회** 사업보고서 이후 | `batch.build.business_overview` | 0원 | 가능 |
| 뉴스 수집·추출 | **수동** (아래 참고) | `batch.ops.run_companies` | 기업당 약 90원 | **불가** |
| 정합성 감사 | 주 1회 | `batch.audit.graph` 등 | 0원 | 가능 |

### 왜 「서비스 중 실행 가능」이 갈리나

**PostgreSQL만 건드리는 배치는 서비스 중에 돌려도 됩니다.** 시세·재무·공시는
표에 `UPSERT`만 하므로 조회와 충돌하지 않습니다.

**Neo4j를 건드리는 배치는 서비스 시간 밖에서만** 돌립니다. 뉴스 추출은 마스터
그래프에 노드와 엣지를 직접 씁니다. 돌리는 중에 조회하면 절반만 반영된 그래프를
보게 됩니다.

### 뉴스만 자동화하지 않는 이유

Google News RSS가 **연속 호출을 차단**합니다. 차단되면 `gnews`가
`data/state/google_block.json`에 남기고, `run_companies`가 **12시간이 안 지났으면
시작 자체를 막습니다**(`exit 3`). 언제 풀리는지 구글이 알려주지 않아
경과 시간으로만 판단할 수 있고, 하루 처리량은 대형사 기준 2곳쯤입니다.

**우회는 하지 않습니다** — IP 교체·프록시·라우터 재부팅·UA 위장 전부 안 씁니다
(실측상 UA는 효과도 없습니다 · 10절 참고). 그래서 뉴스만은 사람이 보면서 돌립니다.

```
종료 코드 3   구글 차단 — 12시간 뒤 재시도
종료 코드 5   회선 오류 — 네트워크 확인
```

### 모든 배치가 증분입니다

같은 명령을 다시 돌려도 이미 받은 것은 건너뜁니다. 중간에 끊겨도
**처음부터 다시 하지 않습니다.**

```
market_data        (stock_code, trade_date) 충돌 시 UPSERT
financials         이미 있는 (corp_code, 연도, 기준) 건너뜀
business_overview  (corp_code, bsns_year) 충돌 시 UPSERT
listed_shares      corp_code 있으면 건너뜀 (--shares-only 로 강제)
뉴스               이미 처리한 기사 URL 건너뜀
```

### 온디맨드 갱신은 하지 않습니다

사용자가 기업을 열 때마다 새로 받는 방식은 **쓰지 않습니다.**

- **주가는 이미 최신입니다.** 장중 실시간 시세는 무료로 못 구하고, 마감 후
  확정 종가면 하루짜리 화면에는 충분합니다.
- **뉴스는 즉시 못 받습니다.** 한 기업 확장에 수집→필터→추출→정규화까지
  수 분이 걸리고 90원이 듭니다. 화면이 기다릴 수 없는 시간입니다.
- **DART는 원래 느립니다.** 사업보고서는 1년에 한 번 나옵니다. 온디맨드로
  받아도 어제와 같은 값입니다.

대신 **화면이 언제 받은 값인지 밝힙니다.** 시세는 `trade_date`,
재무는 `bsns_year`·`fs_div`, 관계는 `last_seen`과 신선도 판정이 함께 나갑니다.

> 「갱신 버튼」이 필요해지면 **뉴스 확장에만** 붙이는 게 맞습니다.
> 백엔드가 요청을 큐에 넣고, 배치가 서비스 시간 밖에 처리한 뒤 알림을 보내는
> 방식입니다. 화면에서 즉시 끝나는 일이 아니라는 걸 사용자에게 알려야 합니다.

「이 기사가 관련 있나」·「이 둘이 같은 회사인가」 같은 판정은 mini로 합니다.
다만 **대명사를 풀어야 하는 판정**(「이 회장」이 누구인가)은 mini로 안 돼서 4o를 씁니다.

# 1) DART — 마스터·재무·지분·임원·공시·제품·거래처

### 확정된 수집 절차 (2026-08-02)

**표준 설정 = 5년 · 월별분할 · 상한 240.** `run_companies`의 기본값에 박아 뒀다.
바꾸면 그 기업만 연결 밀도가 달라져 **다른 기업과 위험도를 비교할 수 없다**
— 리스크 파급이 연결 수에 직접 반응하기 때문이다(허브 감점 `40/(40+차수-1)`).

**64개사 확장은 2026-08-13에 끝났습니다**(901엣지 · 5,708원). 아래는 기업을
새로 늘릴 때의 절차입니다.

```bash
# ⓪ 넣기 전 — 시드가 기존 노드에 붙는지 확인 (무료·1분)
python -m batch.audit.graph          # 「시드 추가 시 노드가 갈리는 기업: 0곳」이어야 한다

# ① 확장 — 밸류체인 우선순위로 자동 정렬
#    ★하루에 2~5곳이 한계다. 구글이 막으면 12시간 뒤에나 다시 된다.
python -m batch.ops.run_companies --plan 5           # 5곳씩, 며칠에 나눠
python -m batch.ops.finalize                         # 5곳 끝날 때마다

# ② 다 끝나면 사람이 본다
python -m batch.audit.spot_check --source news
```

### 정기 갱신 (8절 표 참고)

```bash
# 매일 — 장 마감 후. PostgreSQL만 건드리므로 서비스 중에 돌려도 된다
python -m batch.build.market_data --months 1
python -m batch.build.disclosures

# 분기 — 재무제표 공시 후
python -m batch.build.financials

# 연 1회 — 사업보고서 공시 후 (3~4월)
python -m batch.build.market_data --shares-only
python -m batch.build.business_overview
```

> **왜 5곳씩인가** — 5년·월별이면 기업당 60개 질의라, 52곳을 한 번에 돌리면
> 3,000개가 넘어 구글이 막는다(실측: 심텍 480개 질의 전량 503).
> 막히면 `exit 3`으로 끝나고 **대장에 기록하지 않아** 나중에 다시 돌 수 있다.

> **속도가 실제로 효과가 있었다 — 그리고 503을 맞을수록 나빠진다** (2026-08-04~06)
>
> | 질의 간격 | 결과 |
> |---|---|
> | 0.4초 | 5,000회 던지고 차단 |
> | 0.8초 | 400 · 408 · 392 · 368질의에서 차단 (**4회 연속**) |
> | 1.2초 | 1,072질의 · 62분 · **차단 0회** (3곳 연속 완주) |
>
> 그런데 그 뒤로 한 번에 얻는 질의가 계속 줄었다. 원인은 **누적 503 횟수**다:
>
> ```
> 08-04   3,840질의   503  1회
> 08-05  ~1,300질의   503 19회 이상   ← 15분마다 재시도하는 루프를 돌린 날
> 08-06     152질의   503  1회
> ```
>
> 차단당한 클라이언트가 15분마다 다시 두드리는 건 봇의 전형적 행동이라,
> **자동 재시도 루프는 만들지 않는다.** 기본값을 2.5초로 올리고, 기업 사이에도
> 3분을 쉰다(`--pause`) — 몇 시간을 쉼 없이 같은 속도로 두드리지 않기 위함이다.
>
> **회피는 하지 않는다** — IP 로테이션·프록시·라우터 재부팅으로 IP 갈아치우기,
> 브라우저 User-Agent 위장. 실측상 UA는 **효과도 없다**(크롬·사파리·UA없음 전부 같은 503).
> 차단은 IP 기준이므로 UA를 바꿔도 달라지지 않는다.
>
> **네이버로 갈아타는 것도 안 된다** — 실측 대조(유진테크): 네이버가 2,164건을
> 가져왔는데도 구글이 찾은 41건 중 **12건(29%)만** 겹쳤다. 놓친 것이 하필
> 「유진테크 수주공시 — 공급계약 241.4억원」 같은 **공급계약 기사**고, 네이버가
> 더 가져온 2,152건은 대부분 시황·종목나열 기사였다. 원인은 **날짜 범위가 없어
> 최신 쪽에 쏠리는 것** — 2019년 공시가 최신 1,000건 안에 못 들어온다.
>
> **막는 것은 속도 제한이 아니라 「봇 탐지」다** — 503 본문을 열어 보면 구글의
> `/sorry` 페이지다(브라우저에서 CAPTCHA가 뜨는 그 화면):
>
> ```
> HTTP 503  ·  Content-Type: text/html
> "We're sorry... but your computer or network may be sending automated
>  queries. To protect our users, we can't process your request right now."
> ```
>
> 따라오는 성질이 셋이다.
> **① 정해진 할당량이 없다** — 트래픽 패턴을 보는 휴리스틱이라 같은 질의 수라도
> 통과하기도 막히기도 한다(오늘 삼성전자 21,324건은 통과, 이오테크닉스는 390질의에서 차단).
> **② `Retry-After`가 없다** — 언제 풀리는지 구글이 알려주지 않는다. 아래 「12시간」은
> 실측에서 뽑은 값이지 구글이 준 숫자가 아니다.
> **③ IP·네트워크 단위다** — "your computer or **network**". 회선 전체가 걸린다.
>
> 애초에 Google News RSS는 **공식 API가 아니다**(키도 쿼터도 없다). 그럼에도 쓰는
> 이유는 네이버 API의 `start` 상한 1,000 때문에 과거를 못 훑기 때문이다
> (실측: `"삼성전자"` 1,000건 → 커버 0일).
>
> **「이제 풀렸나」를 질의해 보고 판단하지 말 것** — 구글은 막혀 있어도 소량은
> 통과시킨다. 실측(2026-08-03): 탐침 4회가 4회 다 200을 받아 재수집을 시작했는데
> **390질의째 다시 503**이 나 22.8분을 버리고 0건으로 끝났다. 적은 표본은
> 「아직 막혔다」만 증명할 수 있고 「안전하다」는 증명하지 못한다.
> 근거로 쓸 수 있는 건 **경과 시간**뿐이다:
>
> | | |
> |---|---|
> | 07-31 차단 → 08-03 성공 | 약 2일 (삼성전자·한미반도체 통과) |
> | 08-03 05시 차단 → 07:33 재시도 | 2.5시간 — **부족했다** |
> | 하루 처리량 | 대형사 기준 **2곳쯤**에서 막힌다 |
>
> `gnews`가 503을 `data/state/google_block.json`에 남기고, `run_companies`가
> 12시간이 안 지났으면 `exit 3`으로 **시작 자체를 막는다**(`--ignore-block`로 강행).

> **끊기면 이어받는다 — 앞선 질의를 다시 쓰지 않는다** (2026-08-03)
>
> 이오테크닉스 재수집이 두 번 다 **같은 자리**에서 끊겼다:
>
> ```
> 1차  2026-08 → 2022-07   400질의   차단
> 2차  2026-08 → 2022-06   408질의   차단
>         ↑ 둘 다 여기서 시작
> ```
>
> 매번 처음부터 시작하니 이미 쓴 400질의를 또 쓰고 또 같은 자리에서 막힌다 —
> **2022-05 이전에는 영영 못 닿는다.** 480질의를 한 번에 던질 이유가 없으므로,
> 기간을 끝낼 때마다 `data/state/collect/`에 저장하고 다음 실행이 이어받는다:
>
> ```
> 1회차  2026-08 → 2022-06   408질의  💾 저장
> 2회차  2022-05 → 2021-09    72질의  ✅ 완주
> ```
>
> 같은 480질의 · 같은 기사 · **손실 0**. 기간 단위를 늘리거나 질의어 묶음을 줄이는
> 것과 달리 아무것도 포기하지 않는다(그 둘은 실측상 기사를 놓친다 — DB하이텍
> 2026-Q1: 분기 31건 vs 월 합집합 33건). 저장은 **기간 단위**다 — 한 기간의 8묶음이
> 다 돌아야 「봤다」고 할 수 있어서, 묶음 중간에 저장하면 나머지를 건너뛴다.
>
> ```bash
> python -m batch.ops.collect_state              # 어디까지 갔나 · 남은 질의
> python -m batch.ops.collect_state --clear 이오테크닉스   # 처음부터 다시
> ```

> **비용은 상한이 아니라 예상치를 본다** — 추출량은 상한이 아니라
> 「관련 판정을 통과한 기사 수」가 정한다. 29개사 중 상한을 채운 건 3곳뿐이다.
> `run_companies`가 둘 다 찍는다.

`finalize`가 도는 순서(개별 실행도 가능):

```bash
# ① 회귀확인 — 프롬프트를 고쳤다면 여기서 먼저 걸린다 (150원·30초)
python -m batch.audit.selftest                 # 추출기·검증기 양쪽 쏠림 검사

# ② 정리 — 노드·엣지·근거를 제자리로 (대부분 0원)
python -m batch.repair.node_names              # 이름이 불량한 노드 복구
python -m batch.repair.event_names             # 사건 이름 다시 짓기
python -m batch.repair.node_identity           # 정규화키 재계산 → 중복 병합
python -m batch.repair.products                # 제품 표기 통일
python -m batch.repair.edges                   # 엣지 정규화·클러스터링
python -m batch.repair.subtypes                # subtype 수렴
python -m batch.repair.executive_titles        # 근거에서 직위 복원
python -m batch.repair.stake_subtypes          # 최대주주/자회사 라벨 교정
python -m batch.repair.evidence                # 근거 청크 중복 병합 → 고아 삭제
python -m batch.repair.event_sources           # 사건에 관련 기사 목록 채우기
python -m batch.repair.press_names             # 언론사명을 URL 도메인 다수결로 복구
python -m batch.repair.business_units          # 공장·사업부를 모회사에 매달기 ★위험 전파
python -m batch.repair.orphan_nodes            # 엣지 0인 노드 표시 + 검색에서 제외
python -m batch.build.stub_profiles            # stub 정체 한 줄 (신규분만)
python -m batch.build.company_vectors          # 기업 카드 임베딩 (변경분만)

# ③ 검사 — 무엇이 틀렸나 (지우지 않고 표시만)
python -m batch.audit.grounding --llm --apply --all --source news
python -m batch.audit.grounding_fulltext       # 의심분을 기사 전문으로 다시
python -m batch.repair.retypes                 # 유형오류 교정 (매트릭스 통과분만)
python -m batch.audit.dart --apply             # DART 필드 범위 + 원문 대조 (0원)
python -m batch.audit.relations --scope all    # 방향·대칭·양방향·사건성
python -m batch.audit.freshness                # 종료된 관계 (뉴스 + DART 재적재)
python -m batch.audit.graph                    # 구조 무결성
python -m batch.audit.coverage                 # ★무엇을 아직 안 봤나

# ④ 사건 분류 · 진행현황
python -m batch.repair.event_types             # event_type 11종 + is_risk
python -m batch.ops.status --write-doc         # ※ finalize가 마지막에 자동 실행
```

> **진행현황 문서는 `finalize`가 갱신한다** — 따로 칠 필요 없다.
> 예전엔 사람이 기억해서 쳐야 했는데 **일주일을 놓쳤다**(2026-08-02에서 멈춘 채
> 재수집 15곳·확장 12곳이 반영되지 않음). 「기억해서 돌리는 절차」는 반드시 빠진다.

### 사람이 읽어야 하는 것
```bash
python -m batch.audit.spot_check --source news  # 표본 심층검사
python -m batch.audit.queries                   # 실제 질의로 서비스 가능성 확인
python -m batch.repair.name_overlap             # 이름 겹침 자동 분류 → 남는 것만
python -m batch.repair.person_merge --dry-run   # 동명 Person 병합 후보
python -m batch.ops.lookup <검색어>              # 근거 원문 조회 CLI
```

**`name_overlap`·`person_merge`는 스스로 고치지 않는다.** 합치기·쪼개기는
되돌리기 어렵고 어느 쪽이 맞는지는 근거를 봐야 안다. 사람이 확인한 것만
코드 안 `CONFIRMED_*` 목록에 적어 넣고 `--apply`로 적용한다.

설계 근거·실측·운영 규칙은 **[데이터 수집 방법서](BizNode_데이터수집_방법서.md)** 참조.

## 10. 폴더 구조

**`batch/`는 동사로 나뉜다** — 만든다 / 고친다 / 검사한다 / 돌린다.
파일 이름에 `build_`·`fix_`·`audit_` 접두어를 붙이지 않는다. 디렉터리가 그 역할이다.

```
batch/
  build/     수집·적재 — 데이터를 **만든다**
             graph · disclosures · business_reports · sales_customers
             company_detail · major_reports · news · financials · corp_master
             ownership · subtype_taxonomy · all
  repair/    교정 — 이미 들어온 것을 **고친다** (대부분 LLM 없이 0원)
             node_names · node_identity · edges · subtypes · products
             event_names · event_types · evidence · executive_titles
             stake_subtypes · segment_units · misclassified_edges · retypes
  audit/     검사 — 무엇이 틀렸나 **본다** (지우지 않고 표시만)
             grounding → grounding_fulltext   ← 2단: 저장 문장 → 기사 전문
             dart          DART 전용 (필드 범위 + 원문 XML 대조)
             relations · graph · freshness · coverage · spot_check
             selftest      ★검사기 자체의 회귀 확인
             queries       실제 질의로 서비스 가능성 확인
  ops/       운영 — **돌린다·본다**
             finalize · run_companies · pilot_company · status · lookup · refilter

pipeline/    라이브러리 (CLI 없음)
  extractors/  dart/ · news/ — 수집·파싱
  importer/    정규화 → staging → Neo4j 적재 · 개체해소(ER)
  normalizer/  이름·관계·제품·subtype 정규화
  news/        수집·필터·라우터·트리플 추출
  validators/  matrix.py — 노드-엣지 허용 매트릭스 ★적재 전 최종 방어선
  vectorstore/ ChromaDB 래퍼
  ontology.py  엣지 12종 정의 — 추출기·검증기가 **같은 문장**을 쓴다
  freshness.py 관계 신선도 판정

app/
  core/        설정 · DB 커넥션
  services/    graph_service.py — 신선도·근거 필터 조회 · 파급 계산
  api/         (미구현)

data/
  company_list/ 시드 64개사
  raw_reports/  사업보고서 원문 (재파싱 캐시 · audit.dart가 원문 대조에 씀)
  documents/    공시 원문
```

**의존 방향은 한 방향이다** — `batch/` → `pipeline/` → `app/core`.
`pipeline/`은 CLI를 갖지 않고, `batch/`는 서로를 import하지 않는다
(예외: `ops/finalize`가 다른 배치를 **서브프로세스로** 실행).
